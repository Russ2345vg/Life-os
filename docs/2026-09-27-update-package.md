# Пакет обновлений LifeOS — 27 сентября 2026

Статус: пакет перешёл в реализацию по запросу пользователя. Внесены правки формы
подготовки ко сну, доступности действий из карточки цели и плашки повторения.
Модель потребностей подготовлена как проект и ещё не утверждена. Версия выпуска не назначена.

Цель пакета: сделать связь действий с целями и личными потребностями понятной,
улучшить обозначение повторений и устранить два сбоя без визуального перегруза.

## Состав и порядок

| Порядок | Задача                                                    | Результат                                                                          |

| 1       | Сохранение дополнительного действия в вечерней подготовке | После сохранения действие появляется и остаётся после повторного открытия          |

## 1. Дополнительное действие в вечерней подготовке

**Сообщённый симптом:** пользователь заполняет дополнительное действие, нажимает
«Сохранить», но действие не появляется. Причина не подтверждена.

При диагностике установить точный экран и способ добавления. Кандидат в текущем
интерфейсе — подготовка ко сну `#/v2/sleep`; это предположение, а не установленный факт.
Отдельно проверить сохранение записи и обновление видимого списка.

Критерии приёмки:

- Валидное действие появляется в выбранной группе после успешного сохранения.
- После перехода на другой экран и перезагрузки запись сохраняется.
- Повторное нажатие во время сохранения не создаёт дубликаты.
- При ошибке видна причина, введённый текст остаётся доступным для исправления.
- Работают добавление и редактирование, существующие пункты не меняются побочно.

Предварительные точки исследования: `SleepPreparationPage.tsx`,
`SleepScheduleService.ts`, соответствующее хранилище и тесты.

## 2. Не все действия видны в целях

**Сообщённый симптом:** раздел целей показывает не все ожидаемые действия.
Причина и конкретное место — карточка в списке либо детальная страница — пока не установлены.

Проверить связь с целью, фильтры, статусы, сворачивание, выбор следующего действия
и представление повторяющихся серий. Компактное представление допустимо, если
полный состав доступен и пользователь понимает, что именно скрыто.

Критерии приёмки:

- Все связанные активные действия доступны из цели, включая действия без даты.
- Следующее действие легко найти; его отдельное представление не воспринимается как потеря.
- Выполненные действия доступны отдельно и учитываются согласованно со счётчиками.
- Фильтры и сокращение списка обозначены; полный список можно открыть.
- Представление серии не скрывает другие самостоятельные действия.
- Новое связанное действие появляется после сохранения и остаётся после перезагрузки.
- Удалённые и архивные записи обрабатываются по существующему контракту.

Предварительные точки исследования: `PlannerCatalog.ts`, `PlanningContext.tsx`,
`plannerCatalogModel.ts`, `PlannerGoalList.tsx`, `PlanningGoalDetail.tsx`.
В каталоге и представлении целей уже есть незакоммиченные изменения;
перед реализацией необходимо учитывать актуальный diff.

## 3. Плашка повторяющейся задачи

Классификация: визуальное улучшение существующего UI-компонента.
Компонент `RecurrenceBadge.tsx` уже существует, подпись формируется через
`recurrenceLabel` в `actionSelection.ts`; новый параллельный компонент не нужен.

Требования к будущему дизайну:

- С первого взгляда понятно, что действие повторяется и с какой периодичностью.
- Название действия остаётся главным; длинные подписи не ломают строку на мобильном.
- Разные типы повторения получают понятные подписи из существующих правил.
- Состояния серии различимы там, где они доступны пользователю.
- Значение не передаётся одним цветом; сохраняются читаемость и доступность.
- Один компонент используется согласованно в затронутых списках и деталях.

Перед проектированием: изучить актуальный экран, shared components, CSS-каскад
и эффективные токены; зафиксировать desktop/mobile baseline, прочитать дизайн-правила
и определить дизайн-контракт. Конкретные форма, цвета и композиция здесь не утверждаются.

## 4. Потребности целей и действий направлений

Классификация: новая функция существующих страниц с возможным изменением предметной модели.

Пользовательский принцип: каждая цель и каждое действие поддерживают какую-либо
потребность; интерфейс помогает понять эту связь без визуального перегруза.
При проектировании различать ожидаемый результат цели и потребность, ради которой
этот результат нужен. Например: результат «создать финансовый резерв» может поддерживать
потребность в безопасности. Это пример, а не назначение потребностей пользовательским данным.

До реализации определить:

- Что означает потребность: свободное описание, справочник или сочетание обоих подходов.
- Где хранится связь и как потребность направления соотносится с потребностями целей и действий.
- Может ли действие наследовать потребность цели и когда нужно собственное уточнение.
- Как задаётся потребность самостоятельного действия без цели.
- Как использовать существующее поле цели «Почему важно» (`whyImportant`), не создавая
  дублирующих источников смысла и не теряя уже введённый текст.
- Как постепенно заполнить существующие данные без блокировки повседневного планирования.

Критерии приёмки:

- Для цели и действия можно понять, какую потребность они поддерживают.
- Наследуемая и явно заданная связь не противоречат друг другу и имеют понятные правила изменения.
- Основные списки сохраняют привычную плотность; подробности раскрываются по необходимости.
- Нет повторяющихся наборов меток у каждого уровня и обязательных больших описаний в строках.
- Существующие записи открываются и редактируются без потери данных.
- Назначение потребностей существующим записям остаётся решением пользователя.

Итог этого этапа проектирования: согласованная смысловая модель, примеры на нескольких
целях и действиях, дизайн-контракт и спецификация в `docs/design/features/`.
Визуальное решение готовится по актуальному приложению с проверкой desktop/mobile.

## Проверки при реализации

- Для каждого бага: воспроизведение → подтверждённая причина → регрессионный тест → исправление.
- Для повторений: существующие проверки расписания и рендера, визуальная проверка desktop/mobile.
- Для потребностей: проверки выбранной модели, наследования, сохранения и совместимости старых записей.
- Ближайшие тесты: `PlanningGoalDetail.test.tsx`, `plannerCatalogModel.test.ts`,
  `SleepPreparationPage.test.tsx`, `SleepScheduleService.test.ts`.
- Targeted-команды: `npm run test:target -- <путь к тесту>`; при изменении общего
  контракта — `npm run test:fast`; после стабилизации кода — `npm run verify`.
- При browser-риске — scoped E2E затронутого сценария через `npm run test:e2e -- <файл>`.
  Полный E2E назначается только по условиям Testing Stage Gate, а не по факту объединения задач в пакет.

## Фактический результат этапа

- Обычное добавление и переименование пункта сна сохраняются после перезагрузки.
  Сообщённый сбой обычного сохранения не воспроизведён. Подтверждена и исправлена
  потеря введённого текста при ошибке записи; повторное отправление формы во время
  сохранения блокируется. По согласованному изменению новые пункты появляются сразу
  в текущей незавершённой подготовке и в будущих ночах. Выполненные пункты, прошедшие
  и завершённые ночи сохраняются; переименование применяется со следующей ночи.
- Карточка цели показывает число открытых и выполненных действий и ссылку на полный
  состав; при существующих действиях предлагает выбрать следующий шаг.
- Плашка повторения оформлена как компактная нейтральная метка, проверена на desktop/mobile.
- Потребности внедрены как необязательный текст с наследованием направление → цель → действие;
  подробности раскрываются по необходимости, собственный текст имеет приоритет.
- [Спецификация потребностей и визуальные материалы плашки](design/features/2026-09-27-needs-and-recurrence.md).

Продуктовые проверки и итоговый gate фиксируются в отчёте задачи. Этот документ
не является подтверждением готовности релиза всего dirty worktree.
