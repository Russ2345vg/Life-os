# Прикладной слой Decision

## Назначение

Прикладной слой координирует сценарии работы с решениями, не дублируя инварианты агрегата
`Decision`. Изменения выполняются командами `CreateDecisionDraft`, `PlanDecision`,
`RescheduleDecision`, `RestoreDecision`, `UpdateDecisionDetails` и `CancelDecisionSafely`.
Чтение решений на дату выполняет запрос `GetDecisionsForDate`.

Команды возвращают `Result<Decision, DomainError>`. Известные ошибки передаются вызывающему коду с
предметным кодом; неожиданные технические ошибки не маскируются.

## DecisionRepository

Порт `DecisionRepository` объявлен в прикладном слое и предоставляет три операции:

- `findById` возвращает решение или `null`;
- `findByDate` возвращает новый массив всех решений выбранной даты;
- `save` создаёт или обновляет единственную запись по `EntityId`.

Порт не зависит от React и механизмов браузерного хранения.

`InMemoryDecisionRepository` — временный инфраструктурный адаптер. Он хранит объекты только в
памяти процесса, не создаёт событий и не изменяет состояние решений. Архивированное решение
остаётся доступно через `findById` и `findByDate`; исключение архивных записей из конкретного
интерфейса будет отдельной фильтрацией. Данные исчезают после перезапуска приложения.

## Лимит главных решений

На одну `DayDate` разрешено не более трёх активных главных решений. Место в лимите занимают только
неархивированные решения, у которых одновременно:

- `kind = main`;
- `status = planned` или `status = in_progress`;
- `plannedDate` совпадает с проверяемой датой.

Черновики, дополнительные, подтверждённые, отменённые и архивированные решения место не занимают.
Проверяемое существующее решение исключается из подсчёта по идентификатору.

Правило реализовано в `MainDecisionLimitPolicy`, потому что требует просмотра нескольких
агрегатов. Оно проверяется при планировании, переносе и восстановлении главного решения. При трёх
занятых местах команда возвращает `decision.main_limit_reached` до изменения агрегата.

## Команды

`CreateDecisionDraft` получает текущее время через `Clock`, идентификаторы решения и события через
`IdGenerator`, создаёт один `Decision.createDraft` и сохраняет его. Черновик не планируется
автоматически, и дневной лимит при его создании не проверяется.

`PlanDecision` находит черновик, при выборе вида `main` проверяет лимит, вызывает `Decision.plan` и
сохраняет тот же объект. Главное решение требует `ExpectedResult` и порядка от 1 до 3.

`RescheduleDecision` сначала проверяет допустимость переноса, затем для главного решения проверяет
лимит новой даты. После успешной проверки вызывает `Decision.reschedule`; идентификатор решения не
меняется, а счётчик переносов увеличивается. Дополнительные решения дневным лимитом не ограничены.

`RestoreDecision` работает только с отменённым решением. Главное решение восстанавливается на
новую дату лишь при свободном месте; дополнительное — без проверки лимита. Отказ не изменяет
состояние решения.

`UpdateDecisionDetails` работает только с неархивированным `planned`-решением. Команда принимает
строки названия и ожидаемого результата, создаёт предметные значения, вызывает
`Decision.updateDetails` и сохраняет решение только при содержательном изменении. Вид, позиция,
дата и состояние не редактируются. Для главного решения пустой ожидаемый результат запрещён, у
дополнительного его можно очистить.

`CancelDecisionSafely` отменяет только неархивированное решение в состоянии `planned` или
`in_progress`. Перед предметным вызовом команда читает связанные `LifeAction`: состояния `draft`,
`ready` и `in_progress` блокируют отмену, а `completed` и `cancelled` не блокируют и не изменяются.
При допустимой отмене фиксируется причина «Отменено пользователем», и сохраняется только решение.

## Запрос на дату

`GetDecisionsForDate` получает данные через `DecisionRepository`, копирует массив и сортирует его:
сначала главные решения по `order`, затем дополнительные. Подтверждённые и отменённые решения не
скрываются автоматически. Запрос не изменяет решения и исходный массив репозитория.

## Ошибки

- `decision.not_found` — решение с переданным идентификатором отсутствует;
- `decision.main_limit_reached` — на дату уже назначены три других активных главных решения;
- `decision.cannot_edit` — решение не находится в редактируемом состоянии `planned`;
- `decision.cannot_cancel` — решение не находится в отменяемом состоянии;
- `decision.actions_unfinished` — отмену блокирует хотя бы одно незавершённое связанное действие;
- ошибки `decision.*` предметной модели — нарушен инвариант или недопустим переход агрегата.
