Дата: 29.09.2026. Активный worktree: `D:/LifeOS-App`.
Запрос: выяснить сбой аккаунта и предложить улучшение входа/синхронизации.
Пользователь уточнил: «Не получается войти». Текст ошибки и устройство пока не указаны.
Статус: аудит завершён; причина конкретного пользовательского сбоя **не подтверждена**.
Исполняемый продукт, сервер, аккаунт, настройки и пользовательские данные не изменены.

## Подтверждённые проблемы

### 1. Очистка native auth session несовместима с установленным SDK

`TauriSupabaseAuthStorage.nativeSlotForSupabaseKey` не поддерживает
`sb-…-auth-token-user`. Установленный `@supabase/auth-js` безусловно удаляет этот ключ
в `GoTrueClient._removeSession`, после удаления основного token и до `SIGNED_OUT`.

Изолированная проверка с настоящим установленным SDK и mock native invoke воспроизвела
`Unsupported technical authentication storage key.` при local sign-out; сетевых запросов
не было. Основной session slot к этому моменту уже удалён.

Затрагивает Windows/Android при выходе или очистке невалидной сессии. Свежий прямой
password login не вызывает этот метод, поэтому этот дефект нельзя объявлять причиной
каждого отказа входа. Исправление потребует согласованного TS/native allowlist и отдельного
технического slot; существующий session slot и ограничения доступа сохраняются.

### 2. Вход ошибочно применяет политику создания пароля

`SupabaseAccountAuth.signIn` вызывает `requirePassword` с диапазоном 12–128 символов.
`AccountSyncPage.PasswordField` также устанавливает `minLength={12}` для current-password.
Изолированный probe подтвердил: существующий пароль из 9 символов отклонён как
`account.password_invalid`, provider вообще не вызван.

Для создания/смены пароля политика остаётся строгой. Для входа проверяется заполненность,
а существующие credentials проверяет provider. Это возможная причина только при наличии
такого пароля у пользователя; длина и сам пароль не запрашивались.

### 3. Ошибки входа теряют причину

`SupabaseAccountAuth.mapProviderError` различает на sign-in только `invalid_credentials`.
Probe подтвердил: ответ `email_not_confirmed` превращается в
`account.auth_unavailable` / «Сервис аккаунта временно недоступен».
Rate limit и другие ошибки также попадают в общий fallback.

Нужна безопасная классификация без сырого server message: неверные credentials,
неподтверждённая почта, временное ограничение попыток, timeout/сеть, недействительная сессия,
общая недоступность. UI должен предлагать действие, соответствующее причине. Пароли,
токены, OTP и recovery material не попадают в сообщения или диагностические логи.

### 4. Повторный вход может использовать старую серверную привязку

`AccountSyncService.signIn` записывает новую auth session, оставляя старые
`deviceId/spaceId/membershipStatus/configured`. Следующий `load` видит active/configured
и запускает `finishRecoveryConvergence` до восстановления/перепривязки устройства.
SQL `20260922010000_sync_07_accounts.sql` требует точного совпадения session id.

Изолированный probe воспроизвёл последовательность: old ready installation → новый
password sign-in → сохранён новый session id при старом active device → `load` пытается
sync без вызова `recover`. Смоделированный отказ server binding выходит в ошибку загрузки.
Реальный server round-trip и пользовательский аккаунт не использовались.

Нужен явный переход повторной авторизации и подтверждение привязки перед sync. Сохраняются
локальные данные, очередь, native encryption keys и обязательное server session binding.
Имеющийся recovery умеет replacement device; он должен вызываться по верному состоянию,
а не из-за произвольного сбоя sync. Семантику reauthentication необходимо зафиксировать
отдельным контрактом до изменения состояния или миграции.

## Дополнительные пробелы по коду

- `withStorageTimeout` ограничивает только `/storage/v1/`. Auth request не имеет deadline
  приложения; это риск зависшего busy, **не воспроизведённый пользовательский hang**.
  Ограничивать нужно настоящий fetch и чтение ответа через abort. Один `Promise.race` не
  подходит: поздний ответ может сохранить сессию после показанного timeout. Должны быть
  проверены поведение retry SDK, cleanup и возможность нового ручного входа.
- Password reset отправляет письмо; включены PKCE и `detectSessionInUrl: false`.
  Поиск не обнаружил `exchangeCodeForSession`, recovery callback или native deep-link handler.
  Завершение сброса пароля в установленном приложении не подтверждено. Нельзя показывать
  «пароль восстановлен» после одной отправки письма.
- Browser preview показывает активную форму, хотя backend входа вне Tauri недоступен.
  При будущем UI-патче доступность должна быть явно отражена до отправки формы.

## Рекомендуемое обновление

Пользовательский результат: вход завершается понятным состоянием; отказ объясняет следующий
шаг; синхронизация начинается только при подтверждённой сессии и доверии устройства;
локальная работа сохраняется при проблемах сети или повторной авторизации.

Варианты:

| Вариант                                       | Результат и цена                                                                                     |
| --------------------------------------------- | ---------------------------------------------------------------------------------------------------- |
| Исправить только показанную ошибку            | Быстро после получения текста ошибки; остальные подтверждённые дефекты остаются                      |
| Укрепить текущий account flow — рекомендуется | Исправляет диагностику, завершение операций и привязку; сохраняет существующие sync/crypto контракты |
| Перестроить auth/sync                         | Существенно больше scope и риск миграции; текущие факты не обосновывают замену engine                |

Порядок для рекомендуемого варианта:

1. Получить текст ошибки, устройство/версию и воспроизвести конкретный пользовательский отказ.
2. Исправить auth adapter/storage: отдельные правила входа и нового пароля, совместимость SDK,
   безопасные причины отказа, bounded auth requests. Добавить regression tests до исправления.
3. Зафиксировать и реализовать повторную авторизацию: authentication, device trust и convergence
   имеют разные состояния. До корректной привязки encrypted sync не стартует; local data не очищается.
4. Завершить reset-password через проверенный native callback/PKCE; покрыть повторный/истёкший
   callback и offline. Не ослаблять verification или хранение secrets.
5. Отобразить доступность входа, ошибку и предлагаемое действие; показать последнюю успешную
   синхронизацию и очередь из текущих источников. UI-патч проходит design gate на существующей
   account page и shared controls; новый крупный экран пока не предлагается.
6. Проверить актуальные установленные Windows/Android: вход, restart, истёкшая сессия,
   повторный вход, recovery, offline/reconnect, обмен данными. Публикация отдельным этапом.

Это предложение, не approved design и не реализованное обновление.

привязка пользователя не проверены; причина конкретного сбоя остаётся открытой до текста ошибки.
