# Планирование времени LifeOS — дизайн и технический контракт

**Решение пользователя:** 28.09.2026 пользователь ответил «давай» на предложение
большого обновления с [интерактивным макетом календаря](../../design/references/2026-09-27-time-planning/preview.html)
и [описанием объёма](../../design/features/2026-09-27-time-planning-proposal.md).
Направление и композиция календаря приняты за основу. Реализация таймера и отчёта
проходит отдельную визуальную проверку внутри этого обновления, поскольку их экран
не был показан в календарном макете.

## Цель и границы

Пользователь назначает существующему действию длительность и, по желанию, точное
время, видит выполнимость дня/недели, ведёт рабочую сессию и сравнивает план с
фактом. Все экраны показывают то же действие, а не копию календарного события.
Повседневный вход остаётся простым: действие можно создать без даты, длительности,
времени и цели. Новых мини/макси-режимов, автоматического перепланирования,
внешнего календаря, облачного AI и новых зависимостей нет. Пользователь фиксирует
накопленные локальные обновления в GitHub сам; этот пакет не коммитится и не
публикуется агентом.

Работа делится на три независимых, последовательно пригодных к использованию
результата: (1) расписание и загрузка, (2) рабочие сессии, (3) план/факт.
Каждый имеет свой план и gate. В интерфейсе обновление выглядит как одна связная
функция. Конечный gate включает совместимость и полную E2E-регрессию, поскольку
изменяются общие persistence/sync-контракты.

## Визуальный контракт

Раздел — «Действия». Оболочка, навигация, типографика и каскад берутся из текущего
PlannerWorkspace/PlannerCalendar. Графитовая поверхность, общий jade для выбора и
основного действия, золото только для приоритета, зелёный только для подтверждённого
успеха, красный для ошибки. Мотив — спокойная рабочая сетка; визуальный центр —
расписание выбранного дня/недели. Desktop: неделя и узкая контекстная колонка.
Mobile: выбранный день, переключатель дат, действия без времени ниже сетки; без
горизонтального скролла. Кнопки не менее 44 px, назначение времени доступно без
перетаскивания. Для форм используются существующие PlannerSheet и controls.

Loading сохраняет геометрию сетки, empty предлагает назначить время существующему
действию, error называет сбой и даёт повторить загрузку, success подтверждает
сохранение/отмену. Конфликт показывается текстом на уровне действия, а не только
цветом. Для необычного экрана работы с таймером отдельный макет готовится до его
UI-реализации; нельзя считать этот документ его визуальным утверждением.

## Источник состояния и модель планирования

`LifeAction.plannedDate` остаётся единственной канонической календарной датой.
Добавляются необязательные поля:

- `estimateMinutes: number | null` — оценка действия без точного окна, целое
  положительное число не больше 1440;
- `scheduledStartMinute: number | null` и `scheduledDurationMinutes: number | null`
  — единый плановый блок в местных минутах выбранного дня, полуоткрытый интервал
  `[start, start + duration)`. Оба заданы вместе или оба `null`; начало от 0 до
  1439, длительность положительная, конец не позже 1440. Блок требует plannedDate.

Оценка и длина зарезервированного блока различаются: 90 минут предполагаемой
работы могут быть разбиты на блок 60 минут, но в первой версии у действия не
более одного блока. Часы представлены wall-clock минутами и датой; фактическое
время сессии хранится как UTC-моменты. Плановый блок не является обещанием,
что работа действительно началась. Часовой пояс устройства определяет
отображение календарной даты и границ отчёта, как в текущем LifeOS; смена пояса
не переписывает сохранённые минуты. Блок не пересекает полночь.

Отсутствующие поля старой записи читаются как `null` без переписывания.
`SetLifeActionPlan` при переносе даты сохраняет время суток блока на новой дате;
при снятии даты атомарно убирает блок. Receipt отмены переноса сохраняет прежний
блок и восстанавливает его с проверкой версии и занятости. Завершение, архив и
корзина сохраняют исторические поля, но новые изменения расписания допускаются
только для открытых draft/ready. Повторение создаёт экземпляр с датой, но без
автоматически навязанного времени и оценки. Ручной перенос экземпляра сохраняет
его recurrence metadata.

Возврат завершённого действия сохраняет дату, блок и оценку. Подготовленное действие
возвращается в ready с прежними ожидаемым результатом и временем подготовки, обычное —
в draft. Факт завершения снимается; запись остаётся валидной для повторного чтения.
Проверка занятого окна выполняется до записи вместе с изменением вкладов и журнала.

Локальная команда назначает/снимает время через application-порт и
JournalUnitOfWork. UoW в одной write-транзакции проверяет expectedVersion и
пересечение с другими открытыми плановыми блоками выбранной даты с учётом
изменений этой транзакции. Смежные интервалы разрешены. Текущий конфликт
показывается как «Это время занято. Выберите другое окно». Undo не вытесняет
чужой блок. Сессия и факт выполнения не создают нового планового блока.

Sync и восстановление пишут записи в обход UoW: импортированный удалённый
конфликт сохраняет оба действия и помечает пересечение в календаре и обзоре.
Локальное редактирование одного действия не блокируется посторонним уже
импортированным конфликтом. Пользователь разрешает его переносом одного блока;
автоматический перенос и потеря одного из действий запрещены. Аналогично две
активные сессии, возникшие на разных устройствах, видимы как конфликт и требуют
ручного завершения одной; локальный старт ещё одной блокируется.

Автоматический materialize существующего повторения тоже сохраняет прежнее окно
при возобновлении или изменении расписания, явно показывает пересечение и оставляет
загрузку доступной. Новые ручные назначения и возврат выполнения/корзины остаются строгими.

## Доступное время

Доступные часы — явная настройка пользователя по дням недели, а не константа
макета. Пока она не задана, приложение показывает сумму назначенных минут и
пересечения, но не процент загрузки и не фиктивное «свободно 6 часов».
Значение — `availableMinutes` 1…1440 для каждого указанного дня недели; отсутствие
значения означает «не задано», а не ноль. Пользователь вводит _чистое_ доступное
время уже после обычных перерывов. Уточнение календарных свободных окон
строится только из фактических блоков внутри видимого временного диапазона; оно
не утверждает, что пользователь доступен во все не занятые часы.

Настройка хранится отдельно от `LifeAction` как один versioned planning record,
доступный через application-порт. Существующий `user_settings` предназначен для
вечернего ритуала и не становится параллельным хранилищем календарного состояния.
Новый record/store регистрируется в snapshot/recovery и sync; версия IndexedDB
меняется только на этом этапе и сопровождается тестом upgrade из v27. Если этот
этап отложен, UI не показывает расчёт доступных часов как готовую функцию.

Нагрузка выбранного дня = сумма длительностей блоков и оценок дел без времени.
Неизвестная оценка помечается отдельно и не приравнивается нулю. Предупреждение
о превышении — информационное и не мешает сохранить допустимый блок.

## Рабочая сессия

Факт хранится в уже существующей `ActionSession`, `actionSessions` и journal/UoW.
Новая application-композиция добавляет порт чтения сессий, команды start/pause/
resume/stop и запрос текущей сессии. Старт допускает открытое draft/ready действие
и не вызывает `LifeAction.markInProgress`: тот принадлежит старому lifecycle,
требует ready, даты и ожидаемого результата. Завершение сессии не завершает
само действие. `ActionSession.complete` с `completed` означает окончание работы,
с `interrupted` — её прерывание; обе сессии остаются фактами рабочего времени.

Одновременно локально не более одной running/paused сессии; существующая проверка
UoW сериализует вкладки. Повторные pause/resume/stop и optimistic-version race
не создают лишних событий. UI восстанавливает сессию после перезагрузки из
IndexedDB, показывает расчёт из `workedDurationAt(now)` и позволяет закрыть
старую незавершённую сессию. Удаление/архив действия не удаляет историю часов;
новый старт на недоступном действии отклоняется.

Для исторически устойчивого отчёта новая сессия сохраняет необязательный
`goalIdAtStart`, считанный из свежего действия в момент старта. Старые сессии
без снимка цели остаются в отчёте по действиям и в общей сумме, но не
приписываются задним числом текущей цели. Неизвестная цель показана явно.

## План и факт

Новый application query агрегирует оценки/блоки из LifeAction и рабочие
интервалы ActionSession, не записывая кэш метрик как вторую истину. Дневной и
недельный отчёты разделяют «назначено», «фактически отработано», «выполнено» и
«без оценки». Паузы вычитаются. Сессия через полночь делится по локальным
границам календарных дней; на каждой части вычитаются пересекающиеся паузы.
Смена цели позднее не меняет `goalIdAtStart`. Удалённая цель не стирает факт:
он виден без перехода в её карточку. Не завершённая сессия показывает время
на текущий момент, не создавая фиктивного completed-факта.

## Хранение, синхронизация и восстановление

LifeActionRecord остаётся v1 с необязательными полями; IndexedDB v27 не
повышается только ради этих полей. Mapper валидирует заданные значения и читает
отсутствующие как `null`. Записи sync v1 без новых полей сохраняют локальные
известные поля при merge, явный `null` очищает их, а `plannedDate:null` очищает
также устаревший блок. Новые snapshot включают поля; **точное** восстановление
старого snapshot очищает новые поля, а не сохраняет современные значения через
merge. Новые optional поля ActionSession и planning settings проходят аналогичную
проверку sync/recovery и отказа от невалидных записей. Чужие и уже сохранённые
пользовательские записи не переписываются миграцией для установки defaults.

## Проверки и выпуск

Каждый этап: red/green targeted tests → при общем domain/application контракте
`npm run test:fast` → один `npm run verify` после стабилизации. Browser-риски:
scoped E2E календаря, Today, повторений, таймера и отчёта на desktop/mobile.
Миграция нового settings store, snapshot/restore и cross-device sync проверяются
отдельными интеграционными тестами. После объединения этапов — полный
`npm run test:e2e`: затронуты общие данные нескольких сценариев и sync/recovery,
так что один scoped-flow не доказывает отсутствие межсценарной регрессии.
Перед ним объяснить фактический общий контракт и убедиться, что verify зелёный.

Работа остаётся в активном LifeOS worktree; никакого Git commit/push.
