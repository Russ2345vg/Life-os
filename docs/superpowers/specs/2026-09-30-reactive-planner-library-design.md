# Реактивное обновление данных LifeOS: первый этап

Дата: 30.09.2026. Статус: первый этап реализован; результаты фиксируются в verification report.

## Цель и граница

После сохранения действия открытый экран получает актуальные данные автоматически. Чтение
повторяется только для затронутых частей экрана; серия событий объединяется. Фоновое обновление
сохраняет открытые формы, введённый текст, фильтры и прокрутку.

Первый потребитель — `PlannerLibraryWorkspace`: действия, цели, входящие, фокус и представления
библиотеки, включая календарь и время. Эти представления используют один существующий loader,
поэтому заменить только список действий, не затронув их чтение, было бы искусственным разделением.
Корневой loader «Сегодня», `PlanningContext` и материализация повторений пока сохраняются.

Это изменение внутренней логики обновления существующего интерфейса. Новых страниц, controls,
CSS и визуальной композиции нет; отдельный визуальный макет не нужен. При реализации необходима
проверка текущего интерфейса на desktop/mobile до и после подключения.

## Контракт изменения

- FEATURE → выборочное реактивное чтение данных библиотеки планирования.
- USER GOAL → видеть результат сохранения без ручной перезагрузки и потери текущего ввода.
- EXISTING LOGIC → application-команды и существующие repositories остаются источником данных.
- PAGE/COMPONENT ARCHETYPE → текущий `PlannerLibraryWorkspace` и его дочерние представления.
- SECTION COLOR → текущие tokens и cascade; новых акцентов нет.
- MAIN VISUAL CENTER → текущий список/форма/календарь выбранного представления.
- COMPONENTS TO REUSE → существующие формы, списки, loading, error и retry.
- MOBILE BEHAVIOR → текущая компоновка; обновление не сбрасывает фокус и открытые controls.
- APPROVED REFERENCE → новый reference не требуется; при реализации снять browser baseline.
- TEST SCOPE → application state machine, IndexedDB integration, scoped desktop/mobile E2E.

## Что уже существует

- `LifeOsIndexedDb.subscribeCommits` сообщает изменённые stores после успешного завершения
  транзакции. Abort и readonly-чтение не должны создавать событие обновления.
- `IndexedDbSyncStatusSource` уже использует эти события, но отсутствует при недоступном sync.
  Реактивность локальных данных нельзя связывать с наличием аккаунта или настройкой сервера.
- Сейчас библиотека при обновлении вызывает семь readers через `Promise.all`. Повторные загрузки
  приходят из команд, revision-параметров, sync subscription и резервного опроса страницы времени.
- `PlannerFocus.get(today)` вызывает `PeriodPlanning.load()`, который может импортировать legacy
  focus и записать данные. Это не чистое чтение; первая загрузка может вызвать дополнительный проход.
- События database локальны одному экземпляру `LifeOsIndexedDb`. Изменения другой вкладки или
  другого подключения сами по себе через эту подписку не приходят.
- Выход из аккаунта удаляет и открывает базу через тот же объект приложения. `deleteDatabase`
  не создаёт обычное событие изменения store. Экран аккаунта размонтирует библиотеку.

## Архитектура

Поток: application-команда → commit IndexedDB → infrastructure adapter → application-модель
чтения → React subscription. UI продолжает выполнять предметные изменения через команды.

`CommittedPlannerChanges` — небольшой application-порт с `subscribe(listener): unsubscribe`.
Он передаёт только имена изменённых коллекций, без записей, персональных данных и sync status.
`IndexedDbPlannerChangeSource` отображает существующие store names в этот контракт. Нового
глобального event bus, подключения базы и зависимости не требуется.

`PlannerLibraryReadModels` — фабрика в application instance. `create(today)` создаёт сессию для
открытого workspace. Фабрика хранит только активные сессии для cleanup; снимки между экранами
не сохраняются. Создание сессии и `getSnapshot()` не выполняют I/O и не подписываются на события.

Снимок содержит `data: PlannerLibraryData | null`, `refreshing: boolean`, `error: Error | null`.
Данные включают семь срезов: goals, directions, spheres, actions, ideas, focus, timeCapacity.
Spheres объединяются из active и archived; отсутствие optional timeCapacity даёт семь `null`.
Снимок имеет стабильную ссылку до изменения состояния; незатронутые срезы сохраняют ссылки.
Контейнеры readonly; потребители не изменяют сохранённые domain objects.

### Зависимости срезов

| Событие коллекции                                                                                                                          | Какие readers библиотеки повторить |
| ------------------------------------------------------------------------------------------------------------------------------------------ | ---------------------------------- |
| `directions`                                                                                                                               | directions                         |
| `spheres`                                                                                                                                  | spheres                            |
| `inboxIdeas`                                                                                                                               | ideas                              |
| `timeCapacity`                                                                                                                             | timeCapacity                       |
| `goals`                                                                                                                                    | goals, focus                       |
| `lifeActions`                                                                                                                              | actions, focus                     |
| `focusPeriods`, `planningPeriods`, `periodMemberships`, `periodDecisions`, `recurrenceRules`, `contributionLinks`, `progressContributions` | focus                              |
| Прочие stores, включая sync metadata и `actionSessions`                                                                                    | ни одного                          |

Focus консервативно зависит от всех девяти stores, которые читает текущий planning repository:
goals, lifeActions и семь planning-коллекций из таблицы. Это также сохраняет восстановление после
исправления повреждённой записи в одной из этих коллекций. Оптимизация `PlannerFocus.get` —
отдельная работа. Например, событие lifeActions вызывает actions и focus; внутри focus возможны
физические чтения goals. Обещание «вообще не читать цели при изменении действия» здесь неверно.

### Очередь и публикация

1. Первый subscriber подключает источник событий до начального чтения и помечает все срезы dirty.
2. Синхронная серия событий объединяется через microtask и множество dirty-срезов.
3. В одной сессии выполняется не более одного batch чтений. Все его promises должны завершиться,
   включая ошибочные, прежде чем начинается следующий batch.
4. Новые события во время чтения остаются в очереди. Если изменился читаемый срез, результат batch
   отбрасывается, а выбранные срезы возвращаются в dirty для повторного прохода вместе с новыми.
5. Успешный batch публикуется целиком; до первого полного чтения `data` остаётся `null`.
   Это атомарная публикация результата batch, а не обещание общей database snapshot isolation
   для семи независимых query. После прекращения изменений очередь должна сходиться к актуальным данным.
6. Для конечной серии событий во время одного чтения нужен один объединённый следующий проход.
   Дальнейшие записи во время этого прохода могут потребовать следующих; фиксированного лимита «два» нет.
7. Ошибка сохраняет последний успешный `data`, возвращает неуспешный batch в dirty и останавливает
   автоматическое повторение. Следующий commit или явный `refresh()` возобновляет чтение.
   Неизвестная ошибка получает текст: «Не удалось загрузить данные. Повторите попытку.».

`refresh(slices?)` явно инвалидирует переданные срезы; без аргумента — все семь. Это retry и
резервное обновление. `whenSettled()` ожидает уже запланированную работу, не инвалидируя всё заново.
Оба Promise завершаются после обработки очереди либо ошибки; ошибка чтения отражается в snapshot,
а не превращает уже сохранённую команду в отклонённую. Без subscriber методы не запускают чтение.

### Lifecycle и защита данных

- Последний unsubscribe отключает источник, очищает снимок/очередь и меняет generation.
  Поздние результаты не публикуются, ожидающие Promise завершаются без запуска новой работы.
- Повторный subscribe той же сессии после cleanup допустим и начинает свежую загрузку: это нужно
  React StrictMode. Для физически незавершённого старого чтения отмена не обещается; оно не может
  обновить новую generation. Лимит одного batch действует внутри активной generation.
- Смена today или application services создаёт новую сессию. Ошибка старого запроса также не
  может заменить состояние новой сессии.
- `libraryReads.close()` окончательно закрывает активные сессии до существующего sync/database
  cleanup. Фабрика после close не позволяет ни создать, ни активировать ранее созданную сессию.
- После ухода в аккаунт библиотека не хранит снимок. Возврат после purge начинает чтение пустой
  или заново синхронизированной базы, даже если application instance остался прежним.
- Общий кэш между маршрутами не вводится. Если он потребуется позже, сначала нужен контракт
  reset-start/reset-settled для приостановки чтения и очистки данных при смене аккаунта.

## Интеграция с существующим экраном

Hook `usePlannerLibraryReadModel` использует `useSyncExternalStore` и стабильную сессию для пары
factory/today. В library удаляются собственные loader, sequence, копия timeCapacity, подписка
`useSyncContentChanged` и повторные чтения по QuickAccess/date/workTime revisions.

Команды, busy guard, local command error и success notice остаются. После команды сохраняется
`planningContext.refresh()`, затем вызывается `whenSettled()`. Ошибки чтения и команды различаются:
успешное сохранение с неудачным refresh не предлагается повторять как неудачную запись.
Ошибка команды имеет приоритет при отображении; retry очищает её и вызывает `refresh()`.
При фоновом чтении текущие дочерние формы не размонтируются и не получают новый `key`.

Страница времени сохраняет нынешний 5-секундный и focus/pageshow/visibility fallback, вызывая
`refresh()` всей модели. `usePlannerWorkTime` и 1-секундный визуальный tick остаются без изменений.
Это сохраняет существующую свежесть при записи через другую вкладку. Нулевые idle reads и
мгновенные межвкладочные обновления не являются результатом первого этапа.

## Глобальные ограничения

- Один существующий database и набор application-команд; без новых зависимостей и `any`.
- Database version, stores, IDs, record/wire/snapshot formats и миграции не меняются.
- Account, purge, sync transport, routing и startup semantics не меняются.
- `PlanningContext`, root Today loader, recurrence materialization и `usePlannerWorkTime` не переписываются.
- Кэш существует только в активной сессии открытого `PlannerLibraryWorkspace`.
- Резервное обновление страницы времени каждые 5000 мс и по visibility/focus/pageshow сохраняется.
- Главный агент пишет изменения в активном worktree; предсуществующий dirty baseline сохраняется.
- Commit, push, релиз и изменения пользовательских данных не входят в этот этап.

## Измеримый результат и следующие этапы

На стабильной загруженной модели commit timeCapacity вызывает один capacity reader и ноль остальных;
commit directions — только directions; commit lifeActions — actions и focus. Событие неизвестного
store не вызывает чтений. Синхронная серия одинаковых событий не создаёт параллельных повторов.
Отдельно проверяются ввод в форме, обработка ошибки, StrictMode, смена даты и remount после purge.

До/после на изолированных данных 100 и 1000 действий фиксируются число вызовов library readers и
время до отображения результата. Время — диагностический замер, не нестабильный CI-порог.
Физические DB-чтения focus и работа root/PlanningContext учитываются отдельно; результаты
библиотеки нельзя выдавать за ускорение всего приложения. Диагностические замеры сохранены в verification report.

После приёмки этого этапа можно отдельно спланировать Today/PlanningContext и разделение чистого
чтения с materialization. Межвкладочные уведомления и сокращение polling требуют отдельного
контракта свежести. Расширение кэша на весь application потребует account reset lifecycle.

## Проверка

Application tests проверяют наблюдаемые снимки и вызовы readers через управляемые promises без
sleep. IndexedDB tests — commit/abort, локальную работу без sync, legacy focus и purge/remount.
Browser tests — действующие формы и списки, отсутствие потери ввода, desktop/mobile и соседние
сценарии времени. Полный E2E не нужен при сохранении указанной границы; общий verify выполняется
один раз после реализации. Для текущего документа достаточно проверки формата, ссылок и diff.
