# Утренний блок — дизайн первой рабочей версии

## Цель и границы

Создать внутри `Распорядок → Утро` устойчивый каркас утренней подготовки: старт утра, вода, обзор физической активации, проверка времени главного Действия и единая CTA следующего шага. Патч не включает библиотеку упражнений, подходы, таймеры, историю или аналитику.

## Архитектура

Поток остаётся `UI → Presentation/Read Model → Application → Domain → Repository`. Новый `MorningCycle` хранит только собственные факты утра и связан с существующим `Day` по `dayId` и `dateKey`. `Decision`, `LifeAction`, `TomorrowPlan` и `RoutineBlock` не дублируются.

Готовность, прогресс и следующий шаг вычисляет один application read model. React не содержит копию бизнес-правил и не пишет в IndexedDB напрямую.

## Доменная модель

`MorningCycle` содержит:

- `id`, `dayId`, `dateKey`, `version`;
- `startedAt`;
- `waterCompletedAt` и опциональный объём `waterAmountMl` со значением 250 мл в этой версии;
- `physicalStatus`: `notConfigured`, `ready`, `inProgress`, `done` или `skipped`;
- `physicalUpdatedAt`;
- `updatedAt`.

Команды начала утра, воды и пропуска физической активации идемпотентны. Повторное выполнение не создаёт новую запись и не меняет исходное время выполнения.

## Главное Действие

Источник выбирается детерминированно:

1. `TomorrowPlan.firstAction` для выбранной даты;
2. при его отсутствии — первое доступное Действие первого активного главного Решения по `order`;
3. завершённое найденное Действие остаётся валидным и не требует повторного выполнения утром.

Конкретное время берётся из самого раннего непропущенного эффективного `RoutineBlock` выбранной даты с assignment `existingAction` на найденное Действие. Планирование открывает существующую форму создания блока, предзаполненную действием и категорией `work`; пользователь задаёт интервал. Отдельный календарь не создаётся.

## Read model и следующий шаг

`GetMorningOverview` загружает `Day`, `MorningCycle`, `TomorrowPlan`, Решения, Действия и эффективные блоки распорядка. Он возвращает четыре компактных статуса, центральный прогресс, `ready` и `nextStep`.

Порядок `nextStep` единственный для всего интерфейса:

1. `startMorning`, если утро не начато;
2. `water`, если вода не выполнена;
3. `physical`, если физическая активация не завершена и не пропущена;
4. `scheduleMainAction`, если найденное незавершённое Действие не имеет интервала;
5. `defineMainAction`, если Действие не найдено;
6. `goToDay`, когда условия готовы.

Прогресс вычисляется из четырёх равных условий: утро начато, вода выполнена, физическая активация завершена/пропущена, главное Действие запланировано или уже завершено. `ready` является вычисляемым состоянием, поэтому не рассинхронизируется после внешнего изменения `RoutineBlock`.

## UI

Для `ROUTINE_SECTION.morning` обычный список блоков заменяется `MorningBlockPage`. Остальные вкладки сохраняют текущее поведение.

Экран содержит:

- заголовок и подзаголовок из задания;
- ряд из четырёх компактных карточек: Подъём, Стакан воды, Физическая активация, Главное Действие дня;
- центральную карточку готовности с прогрессом и кнопкой `Продолжить утро` либо `Перейти к дню`;
- подробную карточку воды;
- обзор физической активации с точкой входа будущего модуля и доступным `Пропустить сегодня`;
- карточку главного Действия с интервалом или кнопкой существующего планирования.

CTA использует только `nextStep` read model. Для визуальных переходов она прокручивает/фокусирует нужную карточку; изменяющие шаги вызывают application-команды. Кнопка выбора упражнений показывает понятное сообщение, что модуль будет подключён следующим патчем, без silent failure.

## Даты, persistence и ошибки

Изменяющие команды разрешены только для текущей даты. Явно выбранная дата управляет read-only просмотром. IndexedDB получает store `morningCycles` с уникальными индексами `byDayId` и `byDateKey`; обновления используют optimistic version check.

Каждая команда имеет loading, блокировку повторного клика и один из исходов: успех, понятная бизнес-блокировка либо техническая ошибка с повтором. Ошибка загрузки не превращается в бесконечный spinner.

## Responsive и accessibility

Карточки используют существующие токены LifeOS. Desktop — компактная сетка, 1024 px — адаптивные две колонки, 390/360 px — одна колонка без horizontal scroll. Сохраняются `focus-visible`, `aria-live`, доступные подписи, disabled/aria-busy и `prefers-reduced-motion`.

## Проверки

TDD покрывает инварианты `MorningCycle`, идемпотентность команд, IndexedDB round-trip и уникальность записи, выбор главного Действия, поиск интервала, progress/nextStep, completed-action сценарий и presentation-контракты. Ручной браузерный QA проходит старт, воду, reload, физический пропуск, планирование, готовность, desktop и mobile.

Полный gate: `npm run typecheck`, `npm run lint`, `npm run test`, `npm run build`, `npm run format:check`, `git diff --check`.
