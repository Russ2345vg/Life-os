# Модульный каркас LifeOS

Статус: первый этап реализован по разрешению «делай»; остальные этапы остаются самостоятельными планами.
Дата: 30.09.2026. Рекомендация выбрана после read-only исследования активного worktree.

## Цель

Добавлять и развивать предметные разделы через явные application-контракты, сохраняя локальные
данные, транзакции и единственный sync runtime. Пользователь продолжает пользоваться текущими
экранами и сценариями; успех измеряется уменьшением связанности и совместимостью поведения.
Классификация: внутренний архитектурный рефакторинг, без нового UI и бизнес-правил.

## Подтверждённое исходное состояние

- Слои Domain/Application/Infrastructure/Presentation уже разделены; ESLint ограничивает их зависимости.
- `LifeOsApplication` наследует `PlannerServices` из `PlannerWorkspace.tsx`; общий API зависит
  от presentation-owned декларации. `PlannerLibraryServices` и `ScenarioService` также объявлены в UI.
- `MemoryServices`, `PlanningServices`, `BalanceServices` уже принадлежат Application.
- `createLifeOsApplication` вручную собирает все сервисы; Memory создаётся в одной общей фабрике.
- JournalUnitOfWork и mutation capture уже сохраняют связанные изменения и outbox транзакционно.
- Общий sync registry, runtime bindings, dependency ordering и проверки полноты уже существуют.
- `PlannerWorkspace` выполняет общую загрузку нескольких подсистем. Изменение стратегии загрузки
  имеет отдельные критерии и не входит в извлечение модулей.

## Решение

Одна локальная программа с предметными модулями, публичными application-интерфейсами и явными
фабриками в App. Существующий composition root остаётся точкой связывания и владельцем lifecycle.
Каждый модуль получает зависимости через параметры; общие Clock/CurrentDateProvider/IdGenerator,
database и sync runtime создаются один раз на application instance.

Первая версия стандарта — существующий `MemoryServices` плюс конкретная
`createMemoryModule(dependencies): MemoryServices`. Общий контейнер плагинов, динамическое
обнаружение и универсальная базовая сущность не нужны для этого результата.

### Владение

| Область        | Ответственность                                                                |
| -------------- | ------------------------------------------------------------------------------ |
| Domain         | Предметные сущности, даты, идентификаторы и инварианты                         |
| Application    | Публичные операции модуля, сценарии, запросы и порты                           |
| Infrastructure | Репозитории, storage/sync registration, snapshot и native/browser adapters     |
| App            | Выбор адаптеров, module factories, startup order и освобождение общих ресурсов |
| Presentation   | Узкие view-контракты на основе application API, компоненты и состояние формы   |

Временный плоский application API сохраняется для совместимости вызовов. Его интерфейсы
переносятся в Application без переименования методов; следующий раздел не обязан дублировать
сборку Memory или зависеть от её внутреннего repository.

## Последовательность самостоятельных этапов

### 1. Контракты и первый модуль

Перенести `PlannerLibraryServices`, `PlannerServices` и `ScenarioService` в Application;
UI использует эти типы, при необходимости сохраняя type-only re-exports для текущих callers.
В `LifeOsApplication` использовать существующий `MemoryServices` вместо повторного описания
конкретных классов. Выделить `createMemoryModule` в App. Добавить исполняемую проверку,
запрещающую возвращать presentation imports в public API и module factories.

Готовность: существующие методы/optional поля совместимы, Memory сохраняется/читается/импортируется
из дневника через composition, restart и режим выключенной записи проходят проверки.
Подробности: [план первого этапа](../plans/2026-09-30-modular-lifeos-phase-1.md).

### 2. Долговечные данные Memory

Выделить эквивалентный `MemorySyncRegistration` в
`src/infrastructure/sync/memory/MemorySyncRegistration.ts`, подключаемый существующим
`LIFE_OS_SYNC_REGISTRY`. Проверить связь registration → реальный store → runtime binding.
Metadata описывает current schema, deletion, dependencies и attachments; это не второй реестр.

Исторические миграции и manifest старых snapshot остаются самостоятельными контрактами:
snapshot до v31 законно не содержит Memory, v31 без Memory неполон. Исполняемую политику
`PILOT_BINDINGS.memory_event` и media recovery не переносить заодно с metadata: там сохраняются
локальные фото, receiver-local version, tombstones и orphan-safe diary references.

Готовность: состав/порядок registry, wire payload, old snapshot restore и фото после delete/restore
совместимы. Выключение записи новых воспоминаний не исключает их данные из хранения или sync.
Перед реализацией этому этапу нужен отдельный короткий план на актуальный diff.

### 3. Распространение шаблона

После принятого Memory этапа выделять Diary, затем согласованные группы Planning/Balance/Sleep.
Для каждого определить операции, зависимости и lifecycle по примеру первой фабрики.
Границы транзакций целей/действий/вкладов сохраняются; UI-вкладка сама по себе не определяет модуль.
Каждый перенос — самостоятельный проверяемый патч с существующими scenario tests.
Account/Sync сохраняет собственную композицию и security-контракты.

### 4. Проверка результата

Архитектурные ограничения автоматически проверяются; новые модули подключаются явно.
Изменение одного модуля требует изменения его реализации/регистрации и явного подключения,
а не ручного копирования его публичных методов в несколько UI/application интерфейсов.
После этого отдельно оценить маршрутную загрузку и обновление read models по замерам.
Ускорение UI не заявляется результатом одного переноса файлов.

## Ограничения первого этапа

- Существующие Domain rules, record formats, IDs, даты, версия IndexedDB и история миграций сохраняются.
- Native auth, sync engines, crypto и сетевые запросы не меняются.
- Один database и существующие общие adapters; фабрика Memory не вызывает open/close и не запускает фоновые задачи.
- `memoryEnabled ?? (VITE_LIFEOS_MEMORY_ENABLED === 'true')` вычисляется один раз в root и передаётся boolean.
- Запись по умолчанию выключена; чтение старых Memory остаётся доступным. Флаг не удаляет stores.
- Текущие методы, optional поля UI services и маршруты сохраняют совместимость.
- Предсуществующий dirty worktree сохраняется. Главный агент пишет код, review read-only.
- Новых зависимостей, Git commit/push, публикации и изменения пользовательских данных нет в этом плане.

## Приёмка и проверка

Уровень 1: lint/typecheck подтверждают направление зависимостей и совместимость API.
Уровень 2: composition tests подтверждают общий источник времени/данных, diary import и restart.
Уровень 3: этап 1 использует Memory persistence tests; этап 2 добавляет существующие
sync/snapshot/recovery tests для затронутых долговечных контрактов.
Уровень 4: scoped Memory + Today E2E desktop/mobile при извлечении общей композиции.
После стабилизации один `verify`; успешные стадии не повторять без причины.
Полный E2E нужен только при реальном изменении общего startup/routing/storage контракта,
которое не покрывается выбранными сценариями, либо при отдельной подготовке релиза.

Первый этап реализован; фактические проверки и ограничения описаны в
[отчёте приёмки](../../architecture/2026-09-30-modular-lifeos-phase-1-verification.md).
Этапы 2–4 не включены в этот патч.
