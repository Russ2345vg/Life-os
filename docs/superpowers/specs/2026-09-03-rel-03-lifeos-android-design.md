# REL-03 — LifeOS Android v1.0.1 Design Specification

**Status:** Approved in conversation on 2026-09-03; awaiting repository-spec review  
**Release:** LifeOS v1.0.1  
**Working tree:** `D:\LifeOS-App`  
**Primary artifact:** installable Android APK  
**Companion artifact:** refreshed Windows NSIS installer v1.0.1

## Goal

Package the existing LifeOS React/TypeScript/Vite application as a real Android
application with Tauri 2, without creating a second frontend or redesigning the
product. The Android build must expose the existing sections, including Goal
Album, and retain browser-backed data across a full application restart.

## Existing system and authoritative sources

- The existing React application remains the only UI and product implementation.
- `src/app/ApplicationShell.tsx` and the existing presentation modules remain the
  authoritative UI composition and navigation.
- Existing domain, application, infrastructure, IndexedDB, and localStorage
  contracts remain authoritative and are not duplicated for Android.
- `package.json` is the release-version source used by Tauri through
  `src-tauri/tauri.conf.json`.
- The current desktop identifier `com.lifeos.desktop` is retained for REL-03 to
  avoid an unrelated Desktop identity migration.
- The generated Tauri Android wrapper lives under `src-tauri/gen/android` and is
  treated as platform packaging, not as a second application.

## Design contract

```text
FEATURE
→ REL-03 Android packaging of the existing LifeOS application

USER GOAL
→ Install and use the same LifeOS on Android, including Goal Album

EXISTING LOGIC
→ Unchanged domain/application logic and IndexedDB/localStorage persistence

PAGE/COMPONENT ARCHETYPE
→ Existing responsive ApplicationShell and current LifeOS pages

SECTION COLOR
→ Existing section accents; no new visual language

MAIN VISUAL CENTER
→ Unchanged for every existing screen

COMPONENTS TO REUSE
→ Existing shell, mobile navigation, pages, dialogs, forms, and Goal Album

MOBILE BEHAVIOR
→ Existing single-column layouts, mobile menu, bottom navigation, and safe areas;
  only blocking compatibility corrections are allowed

APPROVED REFERENCE
→ YES — the current application and LifeOS design rules

TEST SCOPE
→ Android launch, core navigation, Goal Album, keyboard/dialog behavior,
  force-stop persistence, one final LifeOS verification gate, APK build, and
  Windows NSIS rebuild
```

## Chosen approach

1. Install only the Android prerequisites absent from the workstation.
2. Use Android Studio Stable with its bundled JetBrains Runtime as the supported
   Java environment.
3. Install the SDK packages required by Tauri and the generated Gradle project.
4. Add the four Rust Android compilation targets required by Tauri.
5. Set the unified LifeOS version to `1.0.1` in package metadata and Rust package
   metadata.
6. Run the standard `tauri android init` workflow in the existing Tauri project.
7. Launch the application on an Android emulator and perform real interaction QA.
8. Produce a universal debug-signed APK for personal installation.
9. Run one final bounded verification cycle and rebuild the Windows NSIS artifact.

This approach deliberately avoids Capacitor, a separate native application, a
second frontend, and hand-maintained parallel business logic.

## Toolchain baseline

The intended supported baseline is:

- Android Studio Stable: Quail 4 / 2026.1.4 or the current stable revision exposed
  by the official installer at implementation time;
- Android Studio bundled JBR for `JAVA_HOME`;
- Android SDK Platform 36;
- Android SDK Build Tools 36.0.0;
- latest compatible Platform Tools and Command-line Tools;
- Android Emulator plus a Google APIs x86_64 API 36 system image;
- the stable side-by-side NDK revision required by the generated Tauri/Gradle
  project; its exact installed revision is recorded in the final report;
- Rust targets:
  - `aarch64-linux-android`
  - `armv7-linux-androideabi`
  - `i686-linux-android`
  - `x86_64-linux-android`

Environment variables are configured to the actual installed locations:

- `JAVA_HOME` → Android Studio JBR;
- `ANDROID_HOME` and `ANDROID_SDK_ROOT` → the Android SDK root;
- `NDK_HOME` → the selected side-by-side NDK revision.

No dependency or platform package is installed before confirming it is absent.

## Version and identity

- `package.json`: `1.0.1`.
- `package-lock.json`: root/package version `1.0.1`.
- `src-tauri/Cargo.toml`: package version `1.0.1`.
- `src-tauri/tauri.conf.json`: continues to derive its version from
  `../package.json`.
- Tauri identifier: `com.lifeos.desktop`, unchanged.
- Android `versionCode` is derived by Tauri from semantic version `1.0.1`.

## Android project ownership

`src-tauri/gen/android` is generated by Tauri and may contain Gradle, manifest,
resource, and Android Studio project files. Changes inside it are limited to:

- output from the standard Tauri generator;
- generated-project settings required for a successful supported build;
- package metadata, icons, or compatibility settings derived from existing LifeOS
  configuration.

No product logic is moved into the generated Android project.

## UI and mobile behavior

REL-03 reuses the existing responsive implementation. There is no redesign.
Compatibility changes are permitted only if runtime QA reveals a blocker such as:

- inaccessible navigation or controls;
- content obscured by system safe areas or the software keyboard;
- dialogs that cannot be completed on a phone-sized viewport;
- an Android WebView-specific startup or scrolling failure.

QA uses representative phone viewports, including approximately `390×844` and
`360×800`, and covers:

- application startup without a blank screen;
- mobile menu and bottom navigation;
- opening the primary existing sections;
- opening Goal Album from the normal LifeOS interface;
- existing Goal Album create/edit or equivalent ready interactions;
- dialogs/forms with the Android software keyboard;
- portrait layout, scrollability, focus visibility, and safe-area handling;
- browser/WebView console or runtime errors visible during the flow.

Any emulator data created for QA is test data only and does not modify the user's
Desktop LifeOS storage.

## Persistence contract

The existing IndexedDB and localStorage adapters remain unchanged unless an
actual Android WebView incompatibility is reproduced. Persistence validation is a
real restart scenario:

1. create or change recognizable test data in the Android application, including
   Goal Album data;
2. confirm it is visible;
3. fully force-stop the Android package;
4. relaunch the package without clearing application data;
5. confirm the same data remains available.

Process death must not be simulated by merely hiding and showing the window.

## Build and signing artifacts

The Android deliverable is a universal APK built with Tauri's debug signing for
personal installation. A production Play Store keystore, AAB, Play Console
release, and store distribution are outside REL-03.

The final APK is copied to a stable, versioned location under Tauri's ignored
target tree:

`D:\LifeOS-App\src-tauri\target\android\LifeOS_1.0.1.apk`

The Windows companion deliverable remains an NSIS current-user installer and is
expected under:

`D:\LifeOS-App\src-tauri\target\release\bundle\nsis\LifeOS_1.0.1_x64-setup.exe`

The final report records the actual resolved paths and byte sizes rather than
assuming these names.

## Verification strategy

Development uses only focused diagnostics needed to reach a working application.
After implementation stabilizes, run one final reasonable verification cycle:

1. targeted checks for files actually changed;
2. one LifeOS full gate because this release covers mobile UI, navigation, and
   persistence (`npm run verify:full`, or its documented equivalent if a bounded
   command is unavailable);
3. final Android APK build;
4. launch the final Android build and repeat the restart-persistence check;
5. final Windows Tauri production build and installed-application smoke check.

Do not repeat an already green suite without an intervening relevant code change.
If a bounded test hangs, localize the last scenario and investigate that scenario
instead of restarting the entire suite repeatedly.

## Acceptance criteria

REL-03 passes only when all of the following are true:

- the same LifeOS frontend launches as an Android application;
- primary navigation and existing sections are usable on a phone-sized screen;
- Goal Album is present and its existing interactions work;
- IndexedDB/localStorage data, including Goal Album test data, survives a full
  Android application restart;
- an installable debug-signed `LifeOS_1.0.1.apk` exists and its size is reported;
- a refreshed Windows NSIS v1.0.1 installer exists and its size is reported;
- no Android-only fork of product logic or UI was introduced;
- all final verification results and genuine limitations are reported accurately.

## Explicit non-goals

- iOS;
- updater or auto-update infrastructure;
- cloud sync, server work, or new backend services;
- Google Play/AAB/store release;
- production Android signing-key creation;
- new product features or broad refactoring;
- redesign of Goal Album or other LifeOS sections;
- MSI packaging.

## Known release limitation

The approved APK is debug-signed and intended for direct personal installation.
It is not a production store artifact and cannot be promoted to Google Play
without a separately managed production signing identity and store release work.
