# REL-02 — LifeOS Desktop Foundation / Tauri 2 Design

**Date:** 2026-09-02  
**Release base:** LifeOS v1.0.0  
**Status:** Approved in chat; implementation pending  
**Scope:** Windows desktop foundation only

## Goal

Package the existing React, TypeScript, and Vite LifeOS application as a local Windows desktop
application with Tauri 2. The existing frontend, navigation, business behavior, and browser-backed
data model remain the source of truth. REL-02 adds a desktop host and Windows packaging; it does not
redesign or reimplement LifeOS.

## Baseline

- The active repository is `D:\LifeOS-App` at the LifeOS `v1.0.0` release base.
- The working tree was clean before design work.
- `npm run build` completed successfully before the integration began.
- The application is composed in `src/app`, renders the existing `ApplicationShell`, and uses
  browser history/hash state for the Routine deep-link flow.
- Domain data is stored in IndexedDB through `LifeOsIndexedDb`; local UI preferences use guarded
  localStorage adapters.
- No approved standalone LifeOS application-logo asset exists in `public` or `src`.
- Rust/Cargo and Microsoft C++ Build Tools are not currently available on the machine.

## Design Contract

```text
FEATURE
→ REL-02 — LifeOS Desktop Foundation / Tauri 2

USER GOAL
→ Run the existing LifeOS as an installable local Windows application

EXISTING LOGIC
→ React/Vite, current navigation, IndexedDB, and localStorage remain authoritative

PAGE/COMPONENT ARCHETYPE
→ Existing ApplicationShell hosted inside the native Tauri WebView

SECTION COLOR
→ Unchanged

MAIN VISUAL CENTER
→ Unchanged

COMPONENTS TO REUSE
→ The complete existing LifeOS interface; no new React component

MOBILE BEHAVIOR
→ Unchanged; the desktop window relies on existing responsive breakpoints while resizing

APPROVED REFERENCE
→ NO — REL-02 introduces no new UI composition

TEST SCOPE
→ Actual Tauri development launch, navigation and resize QA, one final LifeOS verification cycle,
  production NSIS build, packaged-app launch, and native restart persistence QA
```

## Chosen Approach

Use a core-only Tauri 2 shell around the current Vite output.

- Add the Tauri CLI as an exact npm development dependency and retain its resolved version in
  `package-lock.json`.
- Add a minimal Rust crate under `src-tauri` using Tauri core and `tauri-build`, with exact resolved
  crates retained in `src-tauri/Cargo.lock`.
- Do not add `@tauri-apps/api` because the frontend invokes no native commands.
- Do not add filesystem, shell, process, updater, networking, dialog, or persistence plugins.
- Do not create a second frontend or a Tauri-specific React entry point.

This approach has the smallest runtime and permission surface. A plugin-ready shell was rejected
because it grants unused capabilities. A separate desktop frontend was rejected because it would
duplicate the existing source of truth and violate REL-02.

## Tauri Project Structure

`src-tauri` contains only the files needed for the Windows desktop crate:

- `Cargo.toml` — Rust package metadata and Tauri dependencies;
- `Cargo.lock` — reproducible resolved Rust dependency versions;
- `build.rs` — `tauri_build::build()`;
- `src/main.rs` — native entry point and Tauri builder;
- `tauri.conf.json` — product, build, window, security, and bundle configuration;
- `.gitignore` — generated Cargo output exclusion;
- `icons/` — the standard temporary Tauri icon set generated by the official tooling.

Mobile project generation is not run. Android/iOS files, mobile targets, and mobile scripts are not
created.

## Frontend Integration

Tauri consumes the existing Vite application:

- `beforeDevCommand`: `npm run dev`;
- `devUrl`: `http://localhost:5173`;
- `beforeBuildCommand`: `npm run build`;
- `frontendDist`: `../dist`.

Vite receives only the Tauri-recommended development-server settings needed for a deterministic
desktop launch: fixed port `5173`, `strictPort: true`, no cleared terminal output, and optional use
of `TAURI_DEV_HOST`. These settings do not change the production bundle or application behavior.

The root package exposes `npm run tauri dev` and `npm run tauri build` through the standard
`tauri` npm script. Existing `dev`, `build`, and verification scripts stay authoritative.

## Window Contract

The single native window has:

- product and title `LifeOS`;
- native Windows decorations and no browser address bar;
- initial logical size `1440 × 900`;
- minimum logical size `800 × 600`;
- resize, minimize, maximize, and close enabled;
- centered startup;
- non-transparent background;
- normal system DPI scaling through Tauri/WebView2 logical pixels;
- application URL `index.html` in production.

No custom title bar, overlay, tray, splash screen, or additional desktop toolbar is introduced.
The existing responsive layout remains responsible for smaller window widths.

## Navigation

LifeOS keeps its current in-memory section navigation and hash-based Routine routes. Tauri loads
the production `index.html`, while route fragments and `history.pushState` remain inside the same
document. No router library, server fallback, or navigation rewrite is added.

Native QA verifies that the main sections open and the Routine hash route survives ordinary
navigation and resize without a blank screen or console error.

## Persistence

REL-02 does not migrate or transform data.

- `LifeOsIndexedDb`, its database name `lifeos`, version `19`, stores, records, and migrations remain
  unchanged.
- Existing localStorage keys and adapters remain unchanged.
- A stable reverse-DNS Tauri identifier, `com.lifeos.desktop`, is introduced and must not be renamed
  casually in later releases.
- The Windows WebView scheme setting is fixed to the default non-HTTPS scheme. Future changes to
  the identifier or `useHttpsScheme` require an explicit data-compatibility stage because they can
  change the WebView storage location.
- Incognito/private data mode is disabled.

Native restart QA uses a disposable marker through an existing LifeOS workflow for IndexedDB and
an existing preference for localStorage. The application process is closed, restarted with the
same desktop identity, and both values are confirmed through the UI. QA markers may be removed
after evidence is recorded; no existing browser profile data is imported or modified.

## Security

The desktop wrapper exposes no custom Tauri commands and no plugin permissions. The frontend does
not receive global Tauri access. Remote URLs are not configured as application content. Filesystem,
shell, process, updater, clipboard, and system integrations are absent.

The Tauri configuration declares no permissions beyond what is required to create and host the
single local window. If the generated Tauri 2 template requires a capability file, it will be
reduced to the smallest valid local-main-window capability and will not include filesystem, shell,
process, updater, or remote URL access.

The existing Vite application currently has no explicit CSP. REL-02 will not introduce an
unverified policy that could break existing styles or bundled modules. The absence of native
commands and plugins remains the primary privilege boundary for this stage; CSP hardening can be
handled as a separate tested security change.

## Versioning

The desktop product version is `1.0.0`. `package.json` remains the release-version source of truth.
`tauri.conf.json` points its `version` field to `../package.json`, which Tauri 2 supports as a
version source. Rust package metadata is initialized at `1.0.0`, but the Windows bundle version is
derived from the Tauri configuration and therefore from the root package.

Future releases update the root package version through the existing npm versioning workflow; the
Tauri bundle reads that value without an independent arbitrary desktop version.

## Icon

The repository contains UI glyph components and atmospheric images, but no approved standalone
LifeOS application-logo source. REL-02 therefore retains the standard temporary Tauri icon set.
No new logo is designed or inferred from presentation components. Replacing the temporary icon
requires a separately approved brand asset.

## Windows Packaging

The default bundle target is NSIS so the primary result is a Windows `-setup.exe` installer. The
installer uses the default current-user mode and does not require elevation at install time.

An MSI build is not required for REL-02. A successful NSIS `.exe` is the sole required installer
artifact, so the implementation does not spend time installing or diagnosing MSI-only tooling.

Code signing, publication, GitHub Releases, auto-update artifacts, and Microsoft Store packaging
are excluded.

## Prerequisites

The machine requires the official Windows Tauri prerequisites:

- Rustup with the stable MSVC host toolchain;
- Microsoft Visual Studio Build Tools with the `Desktop development with C++` workload;
- Microsoft Edge WebView2 Runtime if it is not already supplied by Windows.

The user approved installing Rustup and Visual Studio Build Tools for REL-02. WebView2 is installed
only if the native runtime check confirms it is missing. No Android SDK, NDK, Java mobile tooling,
or iOS tooling is installed.

## Error Handling

- A busy Vite port causes development startup to fail immediately through `strictPort` rather than
  connecting to an unrelated server.
- Frontend initialization keeps the existing loading and storage-error screens.
- Failure to initialize the native Tauri runtime is reported by the Rust entry point and exits the
  process; no silent fallback server is introduced.
- Build and bundle failures retain their command exit codes and are reported as blockers unless the
  failure is the explicitly optional MSI attempt.
- A missing WebView2 runtime is diagnosed at native launch and resolved only with the official
  runtime installer.

## Test Strategy

REL-02 is configuration and platform integration. The TDD configuration-file exception is used at
the user's explicit request: no synthetic test is added for `tauri.conf.json` when actual native
launch and production bundling validate the same contract more directly.

Implementation and verification avoid repeated broad cycles:

1. integrate the minimal Tauri files and install only confirmed missing prerequisites;
2. run `npm run tauri dev` and verify the separate native window, main-section navigation, and
   resize behavior;
3. run `npm run tauri build` and require an NSIS `.exe`;
4. after implementation succeeds, perform one final reasonable cycle consisting of
   `npm run build`, the existing `npm run verify` gate if it remains bounded, the production Tauri
   build, packaged-application launch, and IndexedDB/localStorage restart persistence QA;
5. finish with `git diff --check`, diff review, and status inspection.

A separate full E2E suite is not run solely for REL-02 because application functionality is not
changed. A separate MSI build is not run after NSIS succeeds.

Commands use bounded observation. A timeout or unverified native behavior is unresolved evidence,
not a pass.

## Expected Files

Create:

- `src-tauri/Cargo.toml`;
- `src-tauri/Cargo.lock`;
- `src-tauri/build.rs`;
- `src-tauri/src/main.rs`;
- `src-tauri/tauri.conf.json`;
- `src-tauri/icons/*` standard temporary Tauri icons;
- `src-tauri/.gitignore`.

Modify:

- `package.json` and `package-lock.json` for the exact Tauri CLI dependency and script;
- `vite.config.ts` for deterministic Tauri development-server settings;
- `eslint.config.js` to exclude Tauri-generated build artifacts from frontend linting;
- `.prettierignore` to exclude Tauri-generated build artifacts from frontend formatting checks;
- `README.md` for desktop prerequisites, development launch, build, and artifact location.

No Domain, Application, Infrastructure persistence, Presentation, or App composition file is
expected to change. If native testing disproves that boundary, implementation stops and the design
is revised before modifying product code.

## Acceptance Criteria

REL-02 passes only when current-tree evidence confirms all of the following:

1. The desktop product and window are named `LifeOS` and report version `1.0.0`.
2. Tauri 2 uses the existing Vite development server and production `dist` output.
3. Development mode opens LifeOS in a resizable native Windows window with no browser chrome.
4. Main LifeOS sections and the existing Routine navigation work after resizing.
5. No new product UI, business behavior, data schema, or migration is introduced.
6. No unused filesystem, shell, process, updater, remote, or plugin permission is enabled.
7. localStorage and IndexedDB values remain available after closing and restarting the native
   application with the same desktop identity.
8. The frontend build and one bounded existing verification gate pass on the current tree.
9. The production Tauri build succeeds and produces an NSIS `.exe` installer with a recorded full
   path, filename, byte size, and resolved Tauri versions.
10. MSI is skipped because NSIS is the approved and sufficient REL-02 artifact.
11. Android, iOS, updater, server, cloud synchronization, publication, push, and GitHub Releases
    remain untouched.

## Out of Scope

- Android and iOS;
- auto-updater;
- server or cloud synchronization;
- storage migration or a new database;
- redesign, new pages, sections, workflows, or business rules;
- tray behavior, global shortcuts, filesystem import/export, or shell integration;
- installer signing or publication;
- push, GitHub Releases, or deployment.
