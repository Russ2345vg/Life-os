# Архитектура LifeOS

## Назначение слоёв

### Domain

Предметное ядро: сущности, значения, инварианты и доменные события. Оно не знает о React,
браузере, хранилище и способах доставки данных. Реализованы модели `Day`, `Decision` и
`LifeAction`. Папка `action-session` зарезервирована для следующего этапа и пока не содержит
модели.

### Application

Сценарии использования, команды, запросы и порты, через которые сценарии получают внешние
возможности. Слой координирует предметную модель, но не содержит React-компонентов и не выбирает
конкретные инфраструктурные реализации.

### Infrastructure

Адаптеры к платформе и внешним механизмам. Этот слой реализует интерфейсы из
`application/ports`. На текущем этапе здесь находятся системные часы, поставщик локальной
календарной даты, генератор UUID и временный репозиторий дней в памяти.

### Presentation

React-страницы, компоненты, макеты и стили. Представление отображает состояние и передаёт
намерения пользователя прикладному слою. Оно не изменяет предметное состояние и хранилище
напрямую.

### App

Композиционный корень приложения. Здесь связываются представление, прикладные сценарии и
конкретные инфраструктурные адаптеры. Провайдеры должны оставаться механизмом сборки, а не местом
для предметной логики.

### Shared

Минимальные технические типы, не принадлежащие конкретной предметной области. Этот каталог не
должен превращаться в набор несвязанных универсальных абстракций.

## Направление зависимостей

Основное направление:

```text
presentation → application → domain
                      ↑
               infrastructure
```

`infrastructure` реализует порты, объявленные в `application/ports`, и при необходимости может
использовать типы `domain`. Композиционный корень `app` знает о конкретных реализациях и связывает
их.

Разрешено:

- `domain` → собственные модули и независимые технические типы;
- `application` → `domain`;
- `infrastructure` → `application/ports` и `domain`;
- `presentation` → `application`;
- `app` → все слои только для композиции.

Запрещено:

- `domain` → React, browser API, `application`, `infrastructure`, `presentation`, `localStorage`
  или IndexedDB;
- `application` → React-компоненты, `infrastructure` или `presentation`;
- `presentation` → конкретные адаптеры `infrastructure`;
- React-компоненты → прямое изменение предметного состояния или хранилища.

## Единственный источник состояния

Для каждого предметного факта существует один авторитетный источник состояния. Представление не
создаёт параллельную изменяемую копию предметной модели. Производные значения вычисляются из
авторитетного состояния, а инфраструктурные представления считаются проекциями или сохранённой
формой, но не вторым владельцем истины.

## Команды меняют состояние

Команда (`Command`) — единственная точка входа для будущего изменения предметного состояния.
Команда выражает намерение, прикладной обработчик координирует выполнение, предметная модель
проверяет инварианты, а результат изменения может быть зафиксирован как `DomainEvent`. Запросы
состояние не изменяют.

## LifeAction и техническое действие интерфейса

`LifeAction` — предметная сущность: конкретная работа ради проверяемого результата, состоящая из
одной или нескольких `ActionSession`. Клик, открытие панели, ввод текста и отправка формы —
технические действия интерфейса. Они не являются `LifeAction`, пока не выражают предметную работу
и не проходят через соответствующую команду.

## Доступ к данным

Представление и предметный слой никогда не обращаются к базе или локальному хранилищу напрямую.
Прикладной слой объявляет необходимый порт, инфраструктура реализует его, а композиционный корень
передаёт реализацию обработчику. `InMemoryDayRepository` — временный адаптер для проверок и не
является постоянным хранилищем.

## Разработка функций вместе с проверками

Каждая новая функция поставляется с проверками своего уровня: предметные правила — модульными
тестами без React и браузера, прикладные сценарии — тестами через подставные порты, адаптеры —
контрактными или интеграционными тестами, интерфейс — проверками наблюдаемого поведения. Перед
завершением изменения обязательны typecheck, lint, test, build и format:check.
