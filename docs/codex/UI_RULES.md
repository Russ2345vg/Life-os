# UI-правила LifeOS

## Источник истины

Для конкретной UI-задачи приоритет имеют утверждённый Figma node или приложенный референс, затем
существующий код и наблюдаемое поведение приложения. Нельзя объявлять визуальное соответствие по
одному чтению JSX/CSS.

Рабочий цикл:

```text
Figma/reference → current component → implementation → browser check → comparison → refinement
```

## Figma integration

- Figma plugin и MCP доступны и авторизованы (проверено 2026-08-24).
- Для чтения дизайна нужен реальный node-specific URL вида
  `https://figma.com/design/<fileKey>/<name>?node-id=<nodeId>`; `fileKey` и `nodeId` нельзя
  угадывать.
- Перед реализацией зафиксируй конкретный node, viewport, состояния и допустимые расхождения.
- Figma задаёт композицию и визуальную иерархию, но не подменяет доменные данные и команды LifeOS.
- После реализации всегда проверяй реальное приложение в браузере и повторно сравнивай с тем же
  node/reference.
- Не создавай, не изменяй и не публикуй Figma-файл без прямого задания пользователя.

При последней проверке 2026-08-24 основной Figma URL не был указан. Проверяй reference текущей
задачи: approved screenshot достаточен для rendered comparison; отсутствие основного Figma-файла
само по себе не блокирует такую работу. Для новых крупных или уникальных экранов необходимость
предварительного visual approval определяется New Feature Design Gate в `AGENTS.md`.

## Визуальный язык

- Общая природная атмосфера и постоянные поверхности из дымчатого стекла по [эталону](../design/references/2026-09-09-shared-glass/new-direction.png).
- Золото означает приоритет, выбранное состояние и главный акцент.
- Зелёный означает подтверждённое или успешно завершённое состояние.
- Красный используется только для ошибок и destructive-действий.
- Фиолетовый не используется как постоянный акцент.
- Минимальное свечение, спокойные тени, тонкие границы и контурные иконки.
- Компактные блоки и высокая информационная плотность без декоративного перегруза.
- Иерархия создаётся типографикой, отступами и уровнями поверхности.

## Подтверждённые токены

Токены определены в `src/presentation/styles/tokens.css`. Имена --color-* ссылаются на общую семантическую палитру. Разные декоративные акценты разделов отменены; status colors сохраняются.

| Токен                  | Значение                |
| ---------------------- | ----------------------- |
| `--color-background`   | `#101619`               |
| `--color-surface`      | `#1b2225`               |
| `--color-text`         | `#f3f4f3`               |
| `--color-text-muted`   | `#b6c0c7`               |
| `--color-border`       | `rgba(218,226,229,.18)` |
| `--color-accent-gold`  | `#edbc8c`               |
| `--color-accent-green` | `#62a86b`               |
| `--color-error`        | `#e58484`               |

Шкала отступов: `0.25rem`, `0.5rem`, `0.75rem`, `1rem`, `1.5rem`, `2rem`, `3rem`.

Радиусы:

- `--radius-small: 0.5rem`;
- `--radius-medium: 0.875rem`.

## Типографика и поверхности

- Основной font stack: Inter → system UI → Segoe UI → sans-serif.
- Основной текст использует `--color-text`, вторичный — `--color-text-muted`.
- Панели, меню и шапка используют общие glass tokens, тонкую границу и общий radius. Blur не должен менять containing block fixed dialogs; при отсутствии поддержки используется плотный fallback.
- Не хардкодь новый цвет или размер, если существующий токен выражает тот же смысл.

## Интерактивность и доступность

- Базовая минимальная высота кнопки — `2.75rem`.
- Общий `focus-visible` — золотой outline `2px` с offset `2px`.
- Нельзя удалять outline без эквивалентного видимого focus-state.
- Disabled-state должен быть визуально отличим и блокировать повторное действие.
- Icon-only controls требуют доступного имени.
- Не ломай keyboard navigation, семантику формы и порядок фокуса.
- Уважай настройку уменьшенного движения; не добавляй обязательную анимацию.

## Responsive

- Документ имеет минимальную ширину `20rem`; horizontal overflow страницы скрыт.
- В CSS реально используются пороги `64rem`, `60rem`, `48rem`, `40rem`, `30rem`, `26rem` и
  более узкие component-specific breakpoints.
- Нижние панели и мобильные overlays учитывают `env(safe-area-inset-bottom)`.
- Проверяй минимум desktop и затронутый mobile layout; для крупных изменений используй
  `1600×900`, `1280×720`, `390×844` и `360×800`.
- На mobile CTA не перекрывает контент, активное поле можно доскроллить, touch targets остаются
  доступными.

## Browser QA

Для UI-изменения обязательно:

1. открыть реальное приложение;
2. пройти изменённый сценарий;
3. проверить loading, empty, success, disabled и error states, если они применимы;
4. проверить desktop и нужные mobile-размеры;
5. проверить browser console на критические ошибки;
6. сравнить с исходным Figma/reference.

Если browser QA не выполнен, отчёт должен явно говорить: `Требуется ручная визуальная проверка`.
