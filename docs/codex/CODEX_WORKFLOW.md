# Рабочий процесс Codex для LifeOS

Этот документ дополняет корневой `AGENTS.md`. Он описывает, как формулировать задачи, когда
подключать проектные навыки и агентов и какими доказательствами завершать работу.

## Перед началом

1. Подтверди корень активного worktree и прочитай `git status --short`.
2. Зафиксируй одну цель, критерии приёмки, что не должно измениться и разрешённые Git-операции.
3. Прочитай `AGENTS.md`, затем относящиеся к задаче файлы из `docs/codex`.
4. Для неоднозначной задачи сначала используй `lifeos-task-intake`; не начинай реализацию, пока
   неизвестны источник истины и границы изменения.
5. Главный агент остаётся единственным автором файлов. Субагенты исследуют или проверяют и
   возвращают evidence-based отчёты.

## Новая функция

В запросе укажи пользовательский результат, предметные сущности, входные состояния, критерии
приёмки, визуальный источник и явные ограничения. Рабочая последовательность:

```text
lifeos-task-intake → brainstorming → согласованный дизайн → план → тест контракта → реализация
→ целевые проверки → полный quality gate → независимый review
```

Перед кодом главный агент должен найти существующую сущность, application-команду, read model и
ближайшие тесты. `lifeos-architect` подключается read-only, если ownership состояния или граница
слоёв неочевидны. Новая предметная операция проходит через application-команду, а не через прямое
изменение состояния в React.

Пример запроса:

```text
Добавь <результат> для <пользователя>. Источник состояния: <сущность/команда>.
Не менять: <модули>. Приёмка: <наблюдаемые сценарии>. Сначала покажи дизайн и план.
```

## Исправление ошибки

Опиши точный симптом, шаги воспроизведения, ожидаемый и фактический результат, среду и последние
известные изменения. Используй `lifeos-bug-repair` и систематическую диагностику:

```text
воспроизведение → локализация границы → первопричина → падающий regression-тест
→ минимальное исправление → соседние проверки → quality gate
```

`runtime-debugger` может read-only воспроизвести зависание, browser/persistence failure или
проблему процесса. Он не исправляет код. Нельзя увеличивать timeout или менять тест только ради
зелёного результата без подтверждённой причины.

## Изменение интерфейса

Передай конкретный Figma node URL или утверждённый референс, route/раздел, обязательные состояния,
viewports и допустимые расхождения. Используй `lifeos-ui-fidelity`:

```text
Figma/reference → current component → implementation → browser check → comparison → refinement
```

`ui-auditor` проводит read-only проверку композиции, responsive, keyboard/focus, accessibility и
browser evidence. Главный агент вносит согласованный патч. Для значимого UI-патча проверяй
desktop и затронутые mobile-размеры, основной сценарий и console/page errors.

Если реальный node или rendered comparison недоступен, результат обязан содержать фразу
`Требуется ручная визуальная проверка`. Сейчас дополнительно действует ограничение:
`Требуется создать/указать основной Figma-файл LifeOS`.

## Сложная архитектурная задача

Сначала попроси `lifeos-architect` составить карту владельцев состояния, зависимостей, контрактов и
минимального набора файлов. Если UI и тестовое покрытие можно исследовать независимо, главный агент
может параллельно запустить `ui-auditor` и `test-reviewer`. Каждый получает непересекающийся
read-only вопрос; их выводы сводит главный агент до реализации.

Не разрешай конкурентную запись в один worktree. `runtime-debugger` используется отдельно только
для воспроизведения и первопричины. После реализации `final-reviewer` независимо читает требования,
итоговый diff, status и свежие результаты gate.

## Финальная проверка

Используй `lifeos-quality-gate`. Сначала запусти целевой тест и `npm run typecheck`, затем полный
набор из `docs/codex/TEST_MATRIX.md`:

```bash
npm run typecheck
npm run lint
npm run test
npm run test:alpha
npm run test:e2e
npm run build
npm run format:check
git diff --check
git diff --stat
git status --short
```

`npm run test` уже является one-shot командой `vitest run`. При подозрении на зависание используй
`npm run test -- --reporter=verbose` с внешним наблюдением; не запускай голый `vitest` и не меняй
timeout без диагноза. Успех подтверждается свежим exit code и сводкой текущего дерева.

## Роли, модели и права

| Роль               | Модель          | Усилие | Sandbox          | Назначение                                          |
| ------------------ | --------------- | ------ | ---------------- | --------------------------------------------------- |
| Главный агент      | `gpt-5.6-sol`   | high   | workspace-write  | План, единственная запись, проверки и handoff       |
| `lifeos-architect` | `gpt-5.6-sol`   | high   | read-only        | Архитектура, ownership и границы патча              |
| `ui-auditor`       | `gpt-5.6-terra` | high   | read-only        | UI, responsive, accessibility и browser evidence    |
| `runtime-debugger` | `gpt-5.6-terra` | high   | workspace-write* | Воспроизведение и диагностика runtime/test failures |
| `test-reviewer`    | `gpt-5.6-terra` | high   | read-only        | Покрытие, flakiness и доказательства gate           |
| `final-reviewer`   | `gpt-5.6-sol`   | high   | read-only        | Независимый финальный вердикт                       |

\* Текущая версия CLI не поддерживает отдельный diagnostic sandbox. Инструкции роли запрещают ей
редактировать проект; главный агент обязан проверить status после её запуска.

Сильная модель используется для основного решения, архитектурных границ и финального допуска.
Более экономичная модель достаточна для ограниченного аудита UI, тестов и воспроизведения.

## Активация project config

`.codex/config.toml`, project agents и `.codex/rules/safety.rules` применяются только после доверия
к конкретному worktree. Для нового пути выдай trust через Codex UI либо после отдельного разрешения
добавь в глобальный `%USERPROFILE%\.codex\config.toml`:

```toml
[projects.'c:\lifeos-codex-upgrade']
trust_level = "trusted"
```

Не меняй глобальный config автоматически. Desktop-плагины и CLI marketplace — разные поверхности:
перед установкой проверяй реально доступные skills/tools и не устанавливай дубликаты.

## Запрещено

- открывать старые LifeOS/Obsidian-копии или переносить из них код;
- выдавать полный доступ, расширять сеть или устанавливать зависимости без необходимости;
- использовать destructive Git, выполнять push или менять чужие незакоммиченные файлы без
  разрешения;
- давать нескольким агентам право одновременно изменять один worktree;
- принимать старые логи, чужое утверждение или другой commit за свежую проверку;
- объявлять визуальное соответствие без Figma/reference и browser comparison;
- начинать следующий этап задачи без подтверждения, если пользователь ограничил scope этапом.
