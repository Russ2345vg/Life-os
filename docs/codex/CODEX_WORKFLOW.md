# Рабочий процесс LifeOS с Astra

Практические сценарии для [AGENTS.md](../../AGENTS.md). Политика находится в нём,
команды и диагностика — в [TEST_MATRIX.md](TEST_MATRIX.md). Этот файл читай при выборе
workflow, делегировании или настройке Codex. Архивные планы и логи не определяют текущие возможности.

## Контекст по задаче

| Когда нужен контекст                            | Источник                                                                                               |
| ----------------------------------------------- | ------------------------------------------------------------------------------------------------------ |
| Неясно, где реализация или владелец состояния   | [PROJECT_MAP.md](PROJECT_MAP.md), затем конкретные модули и ближайшие тесты                            |
| Выбор проверок или диагностика зависшего runner | [TEST_MATRIX.md](TEST_MATRIX.md)                                                                       |
| Новый UI                                        | Полный [LifeOS_DESIGN_RULES_v1.md](../../LifeOS_DESIGN_RULES_v1.md) и New Feature Design Gate в AGENTS |
| Правка/аудит существующего UI                   | Browser baseline, текущие компоненты/CSS и [UI_RULES.md](UI_RULES.md)                                  |
| Обоснование существующего решения               | Релевантная запись в [DECISIONS.md](DECISIONS.md)                                                      |
| Известное ограничение                           | Соответствующий раздел [KNOWN_ISSUES.md](KNOWN_ISSUES.md), затем актуальная проверка                   |

Не читай всю карту и историю перед локальной правкой с известным местом реализации.
Принятые решения и актуальные результаты проверок используй повторно.

## Постановка и продолжение задачи

Достаточный шаблон запроса:

```text
Результат: что пользователь сможет сделать.
Границы: какие части приложения менять и что сохранить.
Приёмка: 2–4 наблюдаемых сценария.
Референс для UI: актуальный экран или утверждённый макет.
Выполни реализацию и необходимые проверки до результата.
```

Для bugfix добавь шаги воспроизведения, ожидаемый/фактический результат и среду.
Отсутствие поля шаблона не блокирует ясную задачу: найди контекст в проекте.

Небольшой задаче достаточно плана в сообщении. Для многоэтапной работы используй один план
в `docs/superpowers/plans/` со ссылкой на specification. При передаче или длительной паузе
обнови в нём цель, принятые решения, оставшиеся шаги, результаты проверок и релевантный diff/commit.
Не создавай параллельные STATUS/CONTEXT/HANDOFF-файлы с тем же состоянием.

Независимые задачи с записью запускай в отдельных worktree. Исходную ветку и нужные
незакоммиченные изменения учитывай до создания: worktree сам по себе не переносит dirty patch.
Внутри одного worktree главный агент остаётся единственным автором; проверки общих портов
и ресурсов координируются даже между worktree.

## Подключение навыков и review

Явно названный пользователем навык применяется к запросу. Остальные выбирай по конкретной
потребности; установленные навыки и плагины не образуют обязательную цепочку.

| Ситуация                                                                              | Что подключать                                                                                    |
| ------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------- |
| После чтения контекста остаётся существенная неопределённость цели, scope или приёмки | `lifeos-task-intake`; ясная или просто срочная задача не требует отдельного intake                |
| Конкретный дефект, failure, hang или регрессия                                        | `lifeos-bug-repair`; диагностика сама по себе не разрешает исправление                            |
| Визуальная реализация или аудит экрана                                                | `lifeos-ui-fidelity`; baseline до проектирования, findings без правок при read-only запросе       |
| Завершение патча или запрос оценки его готовности                                     | `lifeos-quality-gate`; используй уже полученные актуальные доказательства                         |
| Существенный неразрешённый продуктовый/архитектурный выбор                            | Brainstorming по этому выбору, без повторного интервью по принятому дизайну                       |
| Межслойный, persistence, security или уникальный UI-риск                              | Независимый read-only review нужного контракта; небольшую линейную правку проверяет главный агент |

Общие workflow-навыки применяются в рамках AGENTS. Они не дают новых полномочий на Git/публикацию
и не требуют заново согласовывать разрешённую работу. Не редактируй установленный plugin cache:
устойчивые правила находятся в worktree и проектных навыках.

## Роли и усилие рассуждений

Проектный default в [.codex/config.toml](../../.codex/config.toml) — `gpt-6-astra`, `medium`
для обычных задач. Для сложной диагностики, архитектуры и миграций выбирай `high`, а для особенно
трудной задачи — `xhigh` через доступные настройки клиента. Агент не должен утверждать, что
переключил текущую модель/effort, если менялся только файл конфигурации.

| Роль               | Когда делегировать                                              |
| ------------------ | --------------------------------------------------------------- |
| `lifeos-architect` | Неясен владелец состояния или безопасная граница слоёв          |
| `ui-auditor`       | Нужен независимый rendered review, responsive или accessibility |
| `runtime-debugger` | Нужна отдельная локализация browser/persistence/process failure |
| `test-reviewer`    | Неочевидны покрытие общего контракта или достоверность gate     |
| `final-reviewer`   | Нужен независимый финальный вердикт по значимому патчу          |

Передавай один вопрос, нужные файлы, запрет записи и ожидаемое доказательство. Не поручай повторный
полный поиск уже исследованного вопроса. Конфигурации ролей — в [.codex/agents/](../../.codex/agents/);
их закреплённые модели и `high` сохранены. Фактические доступные модели/роли определяет среда.
У `runtime-debugger` sandbox допускает запись для диагностики, но инструкции запрещают менять
проект; после его работы проверяй status. Не запускай конкурирующие тестовые процессы/серверы.

## Активация и оценка настройки

Project config загружается для доверенного проекта и может переопределяться параметрами запуска;
синтаксический разбор TOML не доказывает применение клиентом. В новой задаче проверь выбранные
Astra и `medium`. Уже открытая задача может сохранить прежние настройки; при необходимости
выбери effort в клиенте. Глобальная конфигурация, sandbox, сеть и разрешения этим изменением
не затрагиваются. Подробнее: [Config basics](https://learn.chatgpt.com/docs/config-file/config-basic).

Ускорение проверяй на сопоставимых небольших задачах: время до проверенного результата,
количество исправлений после review и выполненные проверки. Для прямого сравнения `medium/high`
нужны одинаковые исходный commit, запрос, среда и изолированные worktree. Не сравнивай повторный
прогон с готовым решением против первого исследования и не запускай два тяжёлых gate одновременно.
Несколько таких замеров позволят выбрать default; проценты ускорения без замеров не заявляй.

Рекомендация сокращать дубли инструкций и загружать детали по задаче соответствует
[руководству OpenAI для Astra](https://developers.openai.com/blog/rethinking-skills-and-prompts-for-gpt-6-astra).
