# Рабочий процесс LifeOS с Astra

Этот документ дополняет корневой `AGENTS.md`. Он описывает, как формулировать задачи, когда
подключать проектные навыки и агентов и какими доказательствами завершать работу.

Настройка обновлена 2026-09-07 по
[рекомендациям OpenAI для Astra](https://developers.openai.com/api/docs/guides/latest-model#prompting-best-practices).
Политику задаёт `AGENTS.md`, команды и выбор проверок — `TEST_MATRIX.md`. Архивные планы, логи и
снимки плагинов служат историей; текущие возможности определяются активной средой и файлами проекта.

## Перед началом

1. Подтверди корень активного worktree и прочитай `git status --short`.
2. Зафиксируй одну цель, критерии приёмки, что не должно измениться и разрешённые Git-операции.
3. Прочитай `AGENTS.md`, затем относящиеся к задаче файлы из `docs/codex`.
4. Для неоднозначной задачи сначала используй `lifeos-task-intake`; не начинай реализацию, пока
   неизвестны источник истины и границы изменения.
5. Главный агент остаётся единственным автором файлов. Субагенты исследуют или проверяют и
   возвращают evidence-based отчёты.

Если задача ясна, выполняй её до результата. Сначала самостоятельно найди доступный контекст;
уточняй только выбор, который существенно меняет результат или полномочия. Завершение intake
или плана не требует новой реплики. Согласованные дизайн, scope и разрешения сохраняются.
Вопрос пользователя о статусе не отменяет исходную цель: ответь кратко и продолжи работу.
Остановись на явно заданной границе этапа или реальном блокере. До нового разрешения подготовь
доступную независимую часть результата для review.

## Применение навыков

Явно названный пользователем навык прочитай и применяй в рамках запроса. Остальные выбирай по
пользе для задачи; не загружай все связанные руководства заранее. Общие навыки Superpowers
применяются с учётом конкретных правил LifeOS:

- brainstorming нужен для существенного продуктового или архитектурного выбора; используй уже
  известные требования и утверждённые решения без повторного интервью;
- для небольшой правки достаточно краткого плана в сообщении; многоэтапную реализацию фиксируй
  в `docs/superpowers/plans/`, ссылаясь на существующую specification;
- новые функции получают проверки поведения, bugfix — проверку первопричины; для документации
  и agent config применяй отдельную строку матрицы, без тестов на совпадение текста;
- успешные проверки повторяй при изменении их входных условий, новом риске или failure;
- review и finishing-навыки не дают отдельного разрешения на commit, merge, push или публикацию;
- при реальной остановке из-за навыка укажи ссылку на `SKILL.md`, точную цитату и применимость.
  Явные указания пользователя имеют приоритет в рамках системных правил и разрешений среды.

Не редактируй установленный plugin cache ради проектных соглашений. Устойчивые правила LifeOS
хранятся в этом worktree и его проектных навыках; обновление общего пакета не должно их стирать.

## Новая функция

В запросе укажи пользовательский результат, предметные сущности, входные состояния, критерии
приёмки, визуальный источник и явные ограничения. Рабочая последовательность:

```text
цель → дизайн-контракт → план → тест поведения → реализация → целевые проверки → применимый gate
```

Перед кодом главный агент должен найти существующую сущность, application-команду, read model и
ближайшие тесты. `lifeos-architect` подключается read-only, если ownership состояния или граница
слоёв неочевидны. Новая предметная операция проходит через application-команду, а не через прямое
изменение состояния в React.

Пройди New Feature Design Gate из `AGENTS.md`. Для стандартной формы из существующих компонентов
при ясных критериях покажи определённый контракт и продолжай реализацию. Для нового крупного
раздела, уникального сценария, непокрытой архетипом композиции или явного запроса визуального
утверждения подготовь макет и дождись approval. Используй ранее approved reference без повторного
согласования. Независимый review нужен при существенном межслойном, persistence, security или
уникальном UI-риске; небольшую линейную правку проверяет главный агент.

Пример запроса:

```text
Добавь <результат> для <пользователя>. Источник состояния: <сущность/команда>.
Не менять: <модули>. Приёмка: <наблюдаемые сценарии>. Сначала покажи дизайн и план.
```

## Исправление ошибки

Опиши точный симптом, шаги воспроизведения, ожидаемый и фактический результат, среду и последние
известные изменения. Используй `lifeos-bug-repair` и систематическую диагностику:

```text
воспроизведение → локализация границы → первопричина → падающий regression-тест
→ минимальное исправление → соседние проверки → применимый gate
```

`runtime-debugger` может read-only воспроизвести зависание, browser/persistence failure или
проблему процесса. Он не исправляет код. Нельзя увеличивать timeout или менять тест только ради
зелёного результата без подтверждённой причины.

Если пользователь запросил только диагностику, результатом служат причина и доказательства;
это не разрешение менять продукт. Повторные прогоны timing-sensitive дефекта проверяют конкретную
гипотезу; весь suite автоматически не перезапускается.

## Изменение интерфейса

Передай конкретный Figma node URL или утверждённый референс, route/раздел, обязательные состояния,
viewports и допустимые расхождения. Используй `lifeos-ui-fidelity`:

```text
current browser baseline + components/CSS cascade → task reference → implementation → browser check → comparison
```

`ui-auditor` проводит read-only проверку композиции, responsive, keyboard/focus, accessibility и
browser evidence. Главный агент вносит согласованный патч. Для значимого UI-патча проверяй
desktop и затронутые mobile-размеры, основной сценарий и console/page errors.

Если rendered comparison недоступен, результат содержит `Требуется ручная визуальная проверка`.
Изображение, утверждённое для текущей задачи, является полноценным reference. Старое approval не делает исторический макет актуальным для всех будущих задач; применяй приоритет источников из AGENTS.md. До создания даже демонстрационного макета проверь текущую оболочку и эффективные стили. Отсутствие основного Figma-файла не
блокирует задачу с approved screenshot или аудит согласованности существующего UI. Read-only
аудит завершается findings; изменение интерфейса требует запроса на изменение.

## Сложная архитектурная задача

Если ownership или границы неочевидны, поручай `lifeos-architect` карту владельцев состояния,
зависимостей и контрактов, пока исследуешь другую часть задачи. Независимый UI-аудит или выбор
тестов можно поручить `ui-auditor` и `test-reviewer`. Каждый получает один конкретный read-only
вопрос, нужные файлы и ожидаемые доказательства. Делегируй при пользе для скорости или снижения
риска, а не ради заполнения ролей. Не дублируй весь поиск агента; спорные выводы проверяй точечно.

Не разрешай конкурентную запись в один worktree. `runtime-debugger` используется отдельно только
для воспроизведения и первопричины. После реализации `final-reviewer` независимо читает требования,
итоговый diff, status и свежие результаты gate значимого патча. Общие порты, тестовые процессы и
browser-серверы используй последовательно. Соблюдай более строгие ограничения среды. Если роль
недоступна, выполняй работу сам и отмечай отсутствие независимого review, когда он был нужен.

## Финальная проверка

Используй `lifeos-quality-gate`. Рабочий порядок проверок:

```bash
npm run test:target -- src/path/ChangedContract.test.ts
npm run test:fast              # если изменение затрагивает общий слой
npm run verify                 # один gate без E2E после стабилизации патча
```

`npm run verify` последовательно выполняет typecheck, lint, полный Vitest, self-tests тестовой
инфраструктуры, alpha, build, format и `git diff --check`; E2E в него не входит. Полный E2E
по умолчанию не запускается. Для локального browser-риска выбери scoped E2E по `TEST_MATRIX.md`.
Полный набор нужен только при прямом запросе, подготовке релиза/R12 или общем риске из раздела
«Когда нужен полный E2E» в `AGENTS.md`; R9/R10 сами по себе его не требуют. Перед полным запуском
объясни, почему scoped-проверок недостаточно. `npm run verify:full` выполняет verify, затем E2E;
если актуальный verify уже прошёл, запускай только необходимый E2E. В отчёте кратко укажи
выбранный объём и причину запуска или пропуска полного набора.
У этапов есть deadline; текущая npm-цепочка не имеет общего deadline
и останавливается на первом ненулевом exit code без retry.
Прямые `npm run typecheck`, `npm run lint`, `npm run build` и `npm run format:check` используют тот
же bounded process runner и также не могут ждать бесконечно вне `verify`.

Не дублируй этапы `verify` отдельно без диагностической причины. Для документации, навыков и
agent config без изменения продукта достаточно проверки синтаксиса, ссылок, формата своего
патча и решений на реалистичных сценариях. Dirty product code фиксируется отдельно: этот патч
не подтверждает готовность чужих изменений или релиза. Если проверка обнаружила постороннюю
ошибку, отрази её и не исправляй вне scope.

Managed E2E runner сообщает `N/total`, project и имя текущего теста при старте, печатает heartbeat
каждые 10 секунд и ограничивает test/action/navigation ожидания. При process timeout он читает
последнее progress-состояние, называет зависший тест и этап, после чего завершает только созданное
дерево Playwright/Vite/Node и проверяет освобождение своего порта.

`npm run test` — bounded one-shot команда. Для прогресса допустим
`npm run test -- --reporter=verbose`. Не запускай `vitest`/`npx vitest` без `run`, интерактивный
Playwright или `npm run dev` как gate. Если команда выглядит зависшей, не жди молча часами:
запиши stage, command, elapsed и последний output. Timeout с кодом `124` — failed/unresolved check;
локализуй причину через `test:target`, не увеличивай лимит без измерения. Занятый E2E-порт должен
быстро завершить проверку; освободи его владельца вручную, но никогда не убивай процесс по порту.
Успех подтверждается свежим exit code и сводкой проверенного scope. Успешный прогон на текущем
релевантном коде не устаревает от самого review или нового сообщения.

## Роли, модели и права

| Роль               | Модель          | Усилие | Sandbox          | Назначение                                          |
| ------------------ | --------------- | ------ | ---------------- | --------------------------------------------------- |
| Главный агент      | `gpt-6-astra`   | high   | workspace-write  | План, единственная запись, проверки и handoff       |
| `lifeos-architect` | `gpt-6-astra`   | high   | read-only        | Архитектура, ownership и границы патча              |
| `ui-auditor`       | `gpt-5.6-terra` | high   | read-only        | UI, responsive, accessibility и browser evidence    |
| `runtime-debugger` | `gpt-5.6-terra` | high   | workspace-write* | Воспроизведение и диагностика runtime/test failures |
| `test-reviewer`    | `gpt-5.6-terra` | high   | read-only        | Покрытие, flakiness и доказательства gate           |
| `final-reviewer`   | `gpt-6-astra`   | high   | read-only        | Независимый финальный вердикт                       |

\* Текущая версия CLI не поддерживает отдельный diagnostic sandbox. Инструкции роли запрещают ей
редактировать проект; главный агент обязан проверить status после её запуска.

Сильная модель используется для основного решения, архитектурных границ и финального допуска.
Более экономичная модель достаточна для ограниченного аудита UI, тестов и воспроизведения.
При переходе на Astra сохранено усилие `high`, а узкие роли остались на Terra. Фактически
доступные модели проверяй в текущих инструментах; не копируй устаревшее имя из старой сессии.

## Активация project config

Согласно [справочнику Codex](https://learn.chatgpt.com/docs/config-file/config-reference),
`.codex/config.toml` применяется для trusted project; явные параметры запуска могут переопределить
значения. [Файлы ролей](https://learn.chatgpt.com/docs/agent-configuration/subagents) могут отдельно
закреплять модель и effort. Синтаксическая проверка TOML не доказывает загрузку config клиентом.

При следующем запуске LifeOS проверь выбранную Astra. Для нового worktree проверь доверие к его
фактическому пути через Codex UI. Уже открытая задача может сохранять модель и определения ролей;
при необходимости выбери Astra в клиенте или начни следующую задачу после загрузки config.
Глобальный config, sandbox, сеть и разрешения не меняются ради переключения модели.
Desktop-плагины и CLI marketplace — разные поверхности: проверяй доступные skills/tools перед
установкой и не создавай дубликаты.

## Запрещено

- открывать старые LifeOS/Obsidian-копии или переносить из них код;
- выдавать полный доступ, расширять сеть или устанавливать зависимости без необходимости;
- использовать destructive Git, выполнять push или менять чужие незакоммиченные файлы без
  разрешения;
- давать нескольким агентам право одновременно изменять один worktree;
- принимать старые логи, чужое утверждение или другой commit за свежую проверку;
- объявлять визуальное соответствие без Figma/reference и browser comparison;
- начинать следующий этап задачи без подтверждения, если пользователь ограничил scope этапом.
