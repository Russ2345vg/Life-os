# «Память жизни» — спецификация первой версии

Статус: первая версия реализована в активном worktree. Пользователь разрешил реализацию
и 29.09.2026 явно утвердил макет сообщением «да утверждаю».
Дата: 29.09.2026. Публикация и проверка установленных Windows/Android-клиентов — отдельный этап.

## Цель и основной сценарий

Сохранять значимые события, фотографии и личные выводы, возвращаться к ним в ленте и видеть
содержательный итог года. Пользователь выбирает, что становится воспоминанием.

Сценарий: «Добавить воспоминание» → дата, название, текст, необязательное фото → сохранение →
событие в соответствующем месяце → при желании отметить «Главное» → открыть «Мой год».
Другой вход: выбрать сохранённый ответ дневника → «Сохранить в память» → отредактировать
предзаполненную форму → сохранить отдельное воспоминание.

## Объём первой версии

- Отдельный раздел «Память жизни», доступный рядом с дневником в desktop-навигации и через
  существующее меню «Ещё» на мобильном экране. На «Сегодня» новая большая панель не добавляется.
- Лента с группировкой по месяцам, выбором года, поиском по названию/тексту и фильтром типа.
- Типы: «Момент», «Достижение», «Поездка», «Решение», «Мысль». По умолчанию — «Момент».
- Добавление, редактирование, отметка «Главное», мягкое удаление и восстановление.
- Одна необязательная фотография на воспоминание. Это осознанное ограничение первой версии.
- Необязательная связь со сферой, направлением и целью; отображение понятного контекста.
- Ручное сохранение фрагмента дневника за день, неделю или месяц с переходом к источнику.
- «Мой год»: избранные события, достижения и хронология по месяцам на основе сохранённых
  воспоминаний. Текущий год доступен сразу, ждать декабря не требуется.
- Локальная работа без сети; текст и фото синхронизируются через существующую систему при
  настроенной синхронизации и выполненных условиях совместимости устройств.

Позднее: несколько фотографий в событии, видео/аудио, карта поездок, «в этот день», печатный
альбом/PDF, публичные ссылки. В первой версии нет фонового чтения галереи, автосоздания событий,
генерации биографии или анализа дневника внешним ИИ.

### Актуальная визуальная основа

канонический маршрут `#/v2/diary?period=week&date=2026-09-21`. Сняты исходные виды
1440×1000 и 390×844 в текущей задаче; данных пользователя не добавляли.
Проверка DOM: горизонтального overflow нет, зарегистрированных console errors нет.
Это baseline существующего дневника, а не визуальное утверждение нового раздела.

Каскад: global/tokens → planner-v2 → planner-master → planner-premium → diary.css → memory.css.
Вычисленные значения: `--gold-main: #81cfab`, `--surface-1: #11181b`, текст
`rgb(238, 243, 242)`, граница карточки `rgb(40, 52, 56)`, радиус 16 px;

### Утверждённая композиция

Сверху — заголовок, год и «Добавить воспоминание». Ниже — «Лента / Мой год», поиск и фильтры.
В ленте даты объединяют события по месяцам. Фото, если есть, сопровождает текст; отсутствие
фотографии не создаёт пустую рамку. Справа на desktop — компактная навигация по месяцам,
на mobile она становится обычным переключателем. Категории различаются текстом/иконкой,
а не отдельными декоративными цветами. Просмотр полной фотографии — внутри приложения.

Форма использует PlannerSheet, видимые подписи и явную кнопку «Сохранить»; ручной текст
поддерживает существующий Voice Input. Черновик защищён при закрытии панели, Back/Forward,
смене раздела и reload. Не сохранять пустую запись при открытии редактора.

Состояния: skeleton; первая пустая лента с CTA; пустой поиск со сбросом фильтров; ошибка
чтения с повтором; сохранение с disabled submit; конфликт версий с сохранённым черновиком;
успех; фото ожидает отправки/скачивания; ошибка фото с повтором; удалённая запись с восстановлением.
Текст события остаётся доступен, пока фотография передаётся.

## Предметный контракт

Новая независимая сущность `MemoryEvent`; не расширять смысл `JournalEntry` или `DiaryEntry`.
Одна запись дневника может дать несколько разных воспоминаний.

| Поле                  | Правило первой версии                                                     |
| --------------------- | ------------------------------------------------------------------------- |
| id                    | EntityId/UUID, стабилен при повторной попытке сохранения                  |
| occurredOn            | DayDate, обязательная локальная календарная дата, не позднее сегодня      |
| title                 | trim, 1–160 символов                                                      |
| body                  | trim, 0–10000 символов, plain text                                        |
| kind                  | moment / achievement / trip / decision / insight                          |
| isHighlight           | boolean, по умолчанию false                                               |
| context               | необязательные IDs и подписи сферы/направления/цели на момент выбора      |
| diarySource           | необязательные entryId, kind, periodStart, поле ответа и версия источника |
| photo                 | null или MemoryPhoto: dataUrl, mimeType, sizeBytes; максимум 5 MiB        |
| createdAt / updatedAt | ISO timestamp от Clock; не используются вместо даты события               |
| deletedAt             | null либо timestamp мягкого удаления                                      |
| version               | optimistic concurrency, проверяется атомарно репозиторием                 |

`MemoryPhoto` — чистый domain value; Domain не импортирует application attachment-типы.
На границе application/infrastructure он структурно совместим с `LocalSyncImage`.
В sync wire передаются метаданные и `syncAttachment`, а не открытые байты изображения.

### Даты, поиск и объём

Сортировка: occurredOn DESC, createdAt DESC, id DESC. Год определяется occurredOn, не временем
создания и не UTC-преобразованием. В один день допустимо несколько событий. Дата недели/месяца
из дневника — предложение `min(periodEnd, today)`; пользователь видит и может изменить её.
Первая версия требует точную дату; приблизительные годы и интервалы — дальнейшее расширение.
Domain проверяет корректность DayDate; запрет будущей даты проверяет application только при
создании или изменении occurredOn относительно CurrentDateProvider. Mapper, sync, чтение,
правка других полей и restore не отвергают уже сохранённую дату из-за часового пояса устройства.

Поиск: регистронезависимое вхождение в title/body; фильтры year/kind/sphereId/highlight/deleted
сочетаются через AND. Выдача порциями по 30 через «Показать ещё», стабильный составной курсор;
изменение фильтра сбрасывает курсор. Не загружать полноразмерные фото всей ленты одновременно.

### Дневник и связи

Команда доступна для непустого сохранённого ответа; сначала дождаться завершения autosave.
Если есть ошибка/несохранённый текст, сначала предложить сохранить дневник, не молча брать старый
вариант. Ответ заполняет body формы; заголовок, тип и дату пользователь проверяет перед submit.
Если выбранный текст длиннее 10000, предложить сократить его, не обрезать автоматически.

Сохранённый текст принадлежит воспоминанию и не меняется вслед за последующим редактированием
дневника. Это намеренный личный снимок, а не второе авторитетное хранилище дневника. Повторный
submit одного черновика идемпотентен; повторный явный выбор другого фрагмента допустим.
Удаление/архивирование исходного дневника, цели, направления или сферы не удаляет воспоминание.
Ссылка на недоступный источник отображается как недоступная, сохранённые подписи остаются.
Новая связь проверяется по текущим данным; существующие исторические связи не блокируют правку.

### Удаление и восстановление

В «Памяти жизни» есть фильтр «Удалённые» и команда «Восстановить». Удалённые события не входят
в обычную ленту/«Мой год». Первая версия не предлагает безвозвратное удаление или автоматический
срок очистки. Фото и защищённая ссылка сохраняются при мягком удалении; не применять к memory
безусловную очистку parent attachments. Восстановление возвращает событие и фотографию даже
после синхронизации/перезапуска. Глобальную корзину planner не реорганизовывать ради этой функции.
Remove/restore синхронизируются как обычный upsert полной записи с изменённым deletedAt.
Не использовать protocol operation `tombstone`: в существующей инфраструктуре он физически
удаляет parent record и помечает вложения удалёнными, что несовместимо с восстановлением.

### «Мой год»

Проекция существующих MemoryEvent за выбранный год: главные события, достижения, группы месяцев.
Один event может отображаться в тематическом блоке и хронологии, но уникальный счётчик учитывает
его один раз. События без isHighlight остаются в хронологии. Пустые месяцы не получают выдуманные
истории; нет общей оценки жизни. Изменения и восстановление события отражаются в обзоре сразу.
Не создавать вторую сохранённую копию событий/изображений или автоматически переписываемый текст.

## Хранение, фотографии и совместимость

Источник: MemoryRepository → новая IndexedDB store `memoryEvents`; индексы для даты, стабильного
порядка и фильтрации. Текущая версия базы подтверждена кодом: 30. При реализации выбрать следующую
свободную версию, сохранив уже подготовленные изменения других функций. Обновление additive,
без пересоздания существующих stores/пользовательских записей.

Уже есть attachment pipeline для goal/walk, по одному фото на родителя: регистрация, шифрование,
очередь, retry, материализация и snapshot recovery. Расширить его новым parent `memory_event`.
Существующий лимит — 5 MiB; для нового picker принимаются JPEG, PNG и WebP, проверяются реальные
байты/размер/MIME и возможность декодирования. Неподдерживаемый файл оставляет текст и прежнее
фото нетронутыми. EXIF-очистка, перекодирование и HEIC-конвертер в проекте не реализованы и
первой версией не обещаются; никакие координаты из EXIF не отображаются автоматически.

Bootstrap вложений имеет общий checkpoint для старых типов: новый тип требует отдельного
идемпотентного checkpoint. Recovery должен сохранять ещё не загруженное фото как
`syncSnapshotImage`, а подтверждённое облаком — защищённой ссылкой, как у существующих типов.
Старый snapshot без memory store остаётся валидным по версии; новый обязан содержать store.
Cloud recovery доступен только при настроенной активной синхронизации; это не универсальный
локальный экспорт/backup. Не обещать восстановление после очистки локального хранилища без копии.

Старый клиент отклоняет неизвестный sync entityType и останавливает pull на таком событии.
Поэтому выпуск делится на две поставки: A — чтение/хранение/sync/recovery нового типа с созданием
выключенным; B — включение раздела после проверки обновления всех подключённых устройств
пользователя. Новый store сам по себе не создаёт memory_event. Использовать default-off
`VITE_LIFEOS_MEMORY_ENABLED` только для доступности сценариев создания, не для регистрации
чтения/sync/recovery. Все entry points записи подчиняются одной проверке в application, не только UI.
Флаг не является автоматическим доказательством совместимости устройств. До выпуска B требуется
явная проверка Windows и телефона; если это нельзя подтвердить, поставка B остаётся отложенной.
Присоединение старого клиента после активации не поддерживается. Нельзя лечить проблему молчаливым
пропуском неизвестных событий. Обобщённый capability-протокол для массового rollout — отдельная задача.

## Проверяемый результат

1. Созданное офлайн событие находится после reload в правильном месяце/году.
2. Редактирование, поиск, фильтры, «Главное», удаление/восстановление дают согласованный результат.
3. Из дневника сохраняется проверенный пользователем фрагмент, источник и память независимы.
4. Двойной submit/повтор после сбоя не создаёт копий; конфликт не уничтожает черновик.
5. Фото доступно локально, затем на втором поддерживаемом устройстве; pending/retry понятны.
6. Замена фото, snapshot/restore и мягкое удаление не теряют событие или требуемое изображение.
7. «Мой год» учитывает только реальные не удалённые события выбранного года.
8. Desktop/mobile, клавиатура, screen reader labels, reduced motion и Правило №38 проверены.
9. Старые записи diary/goal/walk читаются, синхронизируются и восстанавливаются после расширения.
