# Прогулка перед закатом выбранного города

Дата: 11.10.2026. Статус: APPROVED — пользователь подтвердил дизайн 11.10.2026. Утверждённый технический план реализован; результаты и ограничения проверок зафиксированы в [отчёте](../../../artifacts/visual-qa/sunset-walk/README.md). Baseline: LifeOS 1.0.46, commit 77e35d354ec00d0b91d3b0e9031bc7aa775b87bd.

## Запрос и критерии успеха

Пользователь подтвердил город Борзя, Забайкальский край. Нужна возможность выбрать другой город. Начало прогулки и уведомление «Пора на прогулку» — за 15 минут до расчётного заката выбранного города на соответствующую дату. Правило действует во всех связанных представлениях прогулки, включая автопилот на завтра. Уведомления нужны на Android и Windows даже после закрытия LifeOS.

Это изменение нескольких контрактов: общая настройка местоположения, дата-зависимый расчёт и нативное расписание уведомлений. Существующие Walk/WalkPlan и RoutineBlock остаются источниками прогулочных записей; отдельный второй планировщик действий не создаётся.

## Подход

Рекомендуется локальный астрономический расчёт по координатам, дате и IANA timezone. Интернет требуется для поиска нового города; выбранное местоположение сохраняется. Расчёт на сегодня/завтра и последующие даты работает без ежедневного запроса к серверу. Альтернатива — внешний sunset API на каждую дату — добавляет зависимость от доступности сети и провайдера.

Основание расчёта: [NOAA/Meeus](https://gml.noaa.gov/grad/solcalc/calcdetails.html). Речь о расчётном закате, а не измерении видимого горизонта или погоды. В UI время отображается до минуты; начало равно этому времени минус 15 минут.

Поиск города через изолированный infrastructure adapter; рекомендуемый источник координат, региона и timezone — [Geocoding API](https://open-meteo.com/en/docs/geocoding-api). При реализации проверить условия использования существующего приложения; не вводить платный сервис или billing. Пользователь выбирает конкретный результат с регионом/страной, совпадение по названию не выбирается молча. Борзя должна быть доступна как встроенный подтверждённый default даже без сети.

## Единое владение настройкой и временем

- Настройка: выбранный город (stable provider ID, название, регион/страна, latitude, longitude, timezone), правило sunset-minus-15 и enabled state уведомлений.
- Настройка города общая для связанных экранов. Если она передаётся между устройствами, использовать существующую зашифрованную синхронизацию и её compatibility contracts; scheduling receipts и OS permissions всегда локальны конкретному устройству.
- Единый application query разрешает дату в `sunsetAt`, `walkStartAt`, подпись timezone и доступность расчёта. Presentation не вычисляет астрономию и не создаёт своё время.
- Сегодня, завтра и будущие прогулочные повторения получают собственный расчёт. Часовой пояс компьютера не подменяет пояс города; учитывается DST выбранного города.
- Исторические фактические времена прогулок сохраняются. Меняются связанные будущие планы и их представления, а не текст заметок.
- Связи определяются `LifeAction.walkPlan` и `RoutineBlock.assignment.kind === walk`. Уже импортированные действия без признака прогулки требуют явной связи с этим правилом; поиск по произвольному тексту не должен незаметно переписывать пользовательские действия.
- В autopilot sunset walk — фиксированный защищённый слот с сохранением пользовательской длительности. Запланированные встречи и остальные дела не передвигаются молча при изменении города; конфликт виден в preview/расписании.
- Смена города отменяет прежние будущие напоминания и актуальность старого preview, затем пересчитывает расписание по новой версии настройки.
- Если на дату в городе заката нет, automatic time отсутствует с объяснимым статусом. Выдуманное время и старый закат другого дня не используются.

## Напоминания при закрытом LifeOS

Browser timer не удовлетворяет запросу. Нужен application port нативного walk reminder gateway с отдельными адаптерами Android/Windows.

- Android: использовать системный AlarmManager и существующий подход к permissions, durable configuration, receiver/boot restore и notification channels. Прогулочное уведомление отдельно от sleep alarm; не менять поведение будильника.
- Windows: системная регистрация LifeOS и scheduled notifications. [Microsoft подтверждает доставку запланированного уведомления при неработающем приложении](https://learn.microsoft.com/en-us/windows/apps/develop/notifications/app-notifications/app-notifications-scheduled). Для распакованной NSIS-установки необходима проверка регистрации desktop identity и native integration.
- Расписание должно сохраняться вне WebView и восстанавливаться после перезапуска устройства. Доставка после закрытия не должна зависеть от открытой страницы, активного фокуса или запущенного React.
- Native implementation должен определить и проверить горизонт заблаговременного расписания и его пополнение при неработающем LifeOS. Ограниченную очередь нельзя выдавать за бессрочный scheduler. Предпочтительно системное фоновое пополнение с сохранённой настройкой, без постоянно открытого окна и сетевого расчёта заката.
- Одно уведомление на дату на каждом устройстве, независимо от числа отображаемых строк прогулки. Повторные reconcile/запуск/boot не создают дубли.
- Отключение reminders удаляет только собственные будущие notifications. Устройства не меняют разрешения и DND молча.
- UI показывает подтверждённый OS статус для текущего города/версии настройки. Ошибка или отсутствие доступа не отображается как «Запланировано».

Уведомления относятся к работающей ОС: выключенное устройство не может показать их в прошлом. Закрытие приложения и системный force-stop Android — разные состояния; требования платформы отразить в итоговых доказательствах.

## UI-контракт и границы

Добавить настройку города в существующем разделе прогулок и показывать дату, закат и начало прогулки в связанных планах. Переиспользовать текущие forms/panels, graphite/jade tokens и native controls. Отдельный декоративный экран не нужен. До UI реализации снять актуальный baseline desktop/mobile, прочитать существующие компоненты и computed cascade; дизайн-правила проекта уже читались в текущей сессии.

Вне scope: погода, GPS tracking, автоматическое определение поездок, изменение длительности прогулки, постоянный фиолетовый акцент, переделка заметок/истории, платные геосервисы, новая серверная система push. Публикация новой версии — по отдельной команде пользователя.

## Проверки перед завершением

1. Регрессии расчёта для Борзи по сезонам, нескольких городов и timezone/DST; правило ровно минус 15 минут, no-sunset и переход даты.
2. Совместимость настроек, смена города, offline сохранённое местоположение, stale preview, данные сегодняшнего и завтрашнего дня.
3. Scoped desktop/mobile E2E выбора города и общего времени в прогулках/распорядке/autopilot; keyboard, errors и overflow.
4. Native Android/Windows tests: schedule/cancel, duplicate reconciliation, boot restore и статус permissions.
5. Реальная проверка доставки после завершения процесса LifeOS на обеих платформах. Если физический Android недоступен, отдельно отметить NOT RUN и необходимые условия; сборка и browser screenshots не доказывают эту доставку.
6. Один полный verify из-за общих контрактов; один итоговый независимый read-only review. Полный browser suite нужен только при основаниях AGENTS.md.

До реализации разрешить в техническом плане compatibility города между устройствами, нативное пополнение очереди Windows и связь импортированных прогулочных действий. Не обещать готовую delivery до этих проверок.
