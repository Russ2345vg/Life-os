# Еженедельный обзор целей

Статус: DRAFT — цель и направление согласованы; конкретный макет ожидает утверждения.

## Задача пользователя

Видеть прогресс по целям и понимать, что менять. Основной сценарий: открыть «Цели → Обзор недели», увидеть учтённые результаты завершённой недели, выбрать цель с объяснимым сигналом, изменить план существующей командой и вернуться в обновлённый обзор.

## Дизайн-контракт

- FEATURE: новый пользовательский сценарий внутри «Целей».
- USER GOAL: понять изменения за неделю и принять конкретное решение о следующем шаге.
- EXISTING LOGIC: PlanningState, createGoalProgressReader, contributionIsEffective; существующие команды прогресса, срока, статуса и следующего действия.
- PAGE/COMPONENT ARCHETYPE: центр управления 8+4; один главный недельный итог, плотный список результатов и блок решений.
- SECTION COLOR: текущий мягкий нефритовый акцент; зелёный только для подтверждённо достигнутого результата.
- ATMOSPHERE: актуальные плотные графитовые поверхности страницы «Цели», без лесного фона и стеклянного hero.
- MAIN VISUAL CENTER: итог недели с фактами; никаких общих баллов продуктивности.
- COMPONENTS TO REUSE: PlanningProgress, PlannerGoalContext, PlannerGoalProgress для legacy, PlannerActionRow, PlannerSheet, EntityContextMenu, VoiceField/VoiceTextInput, текущие кнопки и tokens.
- MOBILE BEHAVIOR: один поток, компактная сводка, действия рядом с целью, без широкой таблицы; минимум 44 px. Блок общих решений ниже результатов.
- APPROVED REFERENCE: актуальная страница «Цели» в активном worktree (current-goals.png); переработанный макет PENDING. Старый вариант со стеклом отклонён пользователем.
- TEST SCOPE: чистая application-проекция, render tests, маршруты и возврат из форм, scoped E2E desktop/mobile, verify.

## Предлагаемый объём первой версии

Обзор внутри существующего раздела целей, адрес `#/v2/goals?view=review&week=YYYY-MM-DD`; параметр week нормализуется к понедельнику. Это предлагаемый контракт для реализации, пока не существующий маршрут. Глобальная навигация не расширяется. Вход — пункт «Обзор недели» в существующем переключателе «Представление» страницы целей; возврат — представление «Список».

По умолчанию последняя полностью завершённая неделя Пн–Вс в локальной календарной дате приложения. Можно перейти к прошлой или текущей неделе; для текущей показывать «Неделя ещё идёт», учитывать записи не позднее today. Будущие недели недоступны. Начало года и DST обрабатываются существующей календарной арифметикой automaticPeriod/addDays.

Первая версия показывает текущие активные цели; подпись «Активные цели сейчас» обязательна. При смене недели состав остаётся текущим, меняются записи периода. Архивированные, приостановленные и достигнутые не выдаются за цели, активные в прошлом: надёжной истории статуса в доступном read model нет. После паузы цель исчезает из этого обзора только после успешной записи с сообщением и ссылкой на неё. Отдельный исторический снимок и счётчик «достигнуто за неделю» в этот релиз не входят.

### Итог

Три независимых показателя: количество активных целей; цели с подтверждёнными не-initial записями результата выбранной недели; цели без валидного выбранного следующего действия сейчас. Это не разделение на взаимоисключающие категории. Ноль записи является записью. Количество выполненных задач не подменяет результат.

### Строка цели

Название и существующий контекст; текущий результат и target с единицей; учтённое изменение выбранной недели; число выполненных связанных действий отдельно; следующий шаг; дата последней записи. Numeric/count показывают текущий итог с явным «сейчас». Recurring показывает результат цикла, содержащего конец выбранной недели, с точными границами этого цикла. Для month подпись «Цикл: месяц» обязательна: сумма недели и результат месяца не смешиваются.

«За неделю: +1 книга» — сумма эффективных amount по effectiveDate в пределах недели, исключая initial. Backfill и исправления относятся к дате исходного результата; отменённые, voided и предыдущие completionKey исключены. В раскрытии показывать доступные source, reason, effectiveDate и updatedAt. Отдельную историю исправлений не обещать: текущий contribution не хранит previous amount или признак correction, а исторический Journal не загружается. Это пересчитанные доступные факты, не неизменяемый снимок. Итог не вычисляется разностью recurring cycles.

Если подходящих записей нет: «За неделю нет записей результата». Если сумма равна нулю при наличии записей: «Учтённое изменение: 0». Pending: «Есть неуказанные результаты» и переход к существующему вводу. При complete=false вместо подтверждённого итога — «Данные прогресса ещё неполные», без зелёного reached и без ложного нуля. Положительное число не окрашивать автоматически зелёным: at_most и exact имеют другой смысл улучшения.

Legacy measurement/progress: текущую информацию показывать существующим представлением; недельную количественную историю не выдумывать. Цель без измерения показывает этот факт и реальные связанные действия, а не 0%.

### Сигналы и решения

Сигналы рассчитываются относительно today и явно подписаны «Что пересмотреть сейчас», даже при просмотре прошлой недели.

1. Pending результат: указать значение в существующей форме.
2. Срок прошёл / сегодня / в следующие 7 календарных дней: точная дата; не утверждать, что цель провалена. День today+7 включается.
3. Следующее действие не выбрано или недоступно: различать наличие открытых действий и их отсутствие. Выбрать существующее либо создать с goalId. Текст goal.nextProgress показывать как записанный шаг, не как существующее действие.
4. Нет записей результата за выбранную неделю — нейтральный факт строки, не сигнал «застой».
5. «Последняя запись обновлена N дней назад» — только для измеряемой цели с эффективным числовым вкладом, по его updatedAt; порог 14 календарных дней. Initial-only: «После исходного значения новых записей нет». Не использовать Goal.updatedAt.

Сортировка целей в блоке решений: неуказанный результат, просроченный срок, срок в ближайшие 7 дней, отсутствие следующего шага, давняя запись; внутри — ближайший срок, затем название и id. Несколько причин одной цели объединяются. Без сигналов — «Сейчас нет подсказок для пересмотра», без обещания, что все цели идут хорошо.

Изменения остаются явными. «Обновить результат» открывает существующую корректировку: ясно различать поправку +/− и установку текущего значения, не менять семантику команды. Срок — GoalContributions.configure; пауза — UpdateGoal с expectedVersion; следующий шаг — SelectGoalNextAction или создание LifeAction. Никакого автоматического переноса, паузы или завершения. После сохранения обновить источник и обзор, вернуть выбранную неделю и фокус к строке/итогу. Cancel ничего не меняет; error сохраняет ввод, предлагает повтор. Пауза использует существующий version guard. Для редактирования срока потребуется ограниченное расширение configure: optional expectedVersion с атомарной проверкой в transaction до изменения measurement/dueDate, используемое обзором. Без этого stale форма способна перезаписать measurement; такой вариант реализации не принимается. Остальные существующие вызовы сохраняют контракт. Set-progress использует имеющийся контекст расчёта; ошибки и конфликты не скрываются.

## Архитектура и затрагиваемые модули

Новая GetWeeklyGoalReview application query поверх PlanningRepository.read и чистая проекция. Канонический reader создаётся один раз для всех целей. Расчёт процентов не дублируется в React. Число выполненных действий: уникальные текущие LifeAction с goalId этой цели, status=completed и локальной датой completedAt внутри недели; исключить archived. Это текущие сохранённые выполнения, а не полный исторический журнал; reopen исключает выполнение. Ссылки вкладов на другие цели не удваивают число прямых действий. PlanningProvider может отдавать проекцию из уже загруженного того же PlanningState, без независимого кеша предметных данных.

Presentation: новый WeeklyGoalReview, локальные стили, подключение в PlannerLibraryWorkspace, локальное расширение PlannerNavigation и возврат из существующих редакторов. Формы и команды переиспользуются; shared-компоненты меняются только при подтверждённой необходимости.

Infrastructure/Domain: новые stores, миграция, sync-типы и история не требуются. Исторический PlanningState.journal недоступен; PeriodDecision.resultAtDecision остаётся отдельным неизменяемым снимком решения и не подменяется обзором.

Авторитетные файлы: src/application/ports/PlanningRepository.ts; src/application/planner/GoalContributions.ts; src/domain/planner/CompletionContributions.ts; src/domain/planner/GoalMeasurement.ts; src/domain/planner/PlanningPeriod.ts; src/presentation/planner-v2/PlanningContext.tsx; PlanningProgress.tsx; PlanningGoalDetail.tsx.

## Состояния и доступность

Loading: геометрия итога и строк, role=status; не показывать ложную пустоту. Empty: нет активных целей → создать цель / перейти ко всем целям. Error: текст и повтор загрузки. Success: role=status после подтверждённой записи. Partial: сведения о pending/incomplete рядом с затронутой целью. Keyboard: предсказуемый порядок, visible focus, Escape и возврат фокуса в sheet. Reduced motion. Desktop 1280/1440, mobile 390/360/320; длинные названия и большие числа.

## Приёмка и проверки реализации

- Недели Пн–Вс, смена месяца/года, текущая неделя без будущих записей.
- Initial, missing initial, pending, подтверждённый ноль и отсутствие записей различаются.
- Reopen, voided, старый completionKey, correction, backfill и month/week recurring учитываются канонически.
- Legacy и цели без измерения не получают выдуманного процента.
- Нет ложного улучшения at_most/exact, нет дублирования данных.
- Недоступное/чужое/завершённое next action не считается выбранным.
- Сроки рассчитываются относительно today; прошлую неделю не смешивать с текущими сигналами.
- Query read-only; простой просмотр не создаёт период, decision или progress fact.
- Каждая корректировка сохраняется существующей командой; cancel/error/version conflict сохраняют данные.
- Возврат из формы сохраняет неделю; refresh и sync не оставляют устаревшие данные.

Targeted: новые query/render tests + GoalMeasurement/PlanningPeriod/PlanningProgressHistory/GoalContributions и PlannerNavigation. После стабилизации npm run verify, scoped E2E нового сценария и соседнего goal flow на desktop/mobile. Полный E2E по умолчанию не нужен: persistence и общий механизм routing не меняются; расширение одного маршрута покрывается scoped-набором. При выявленном общем риске решение пересмотреть согласно TEST_MATRIX.
