# Пункт 8: подтверждение будильника на телефоне и компьютере

Статус: дизайн и план одобрены пользователем 10 октября 2026 года; реализация добавлена в накопленные изменения. Результаты проверок фиксируются в отчёте задачи.
Пользователь выбрал отображение на обоих устройствах. Это расширение существующего
контракта данных `sleep_schedule`, а не только замена текста статуса.

## Пользовательский результат

На Android и Windows раздел «Сон и подъём» показывает:

- «Телефон подтвердил будильник на 07:15» с датой следующего сигнала и временем,
  когда подтверждение было получено от Android.
- «Изменения ещё не подтверждены» после изменения расписания или разового подъёма.
- «Нужны разрешения на телефоне», «Телефон не подтвердил постановку» или «Ошибка
  постановки» после соответствующего действительного ответа Android.
- При отсутствии ответа: понятное действие «Откройте LifeOS на Android и нажмите
  “Проверить статус”, затем дождитесь синхронизации аккаунта».

Дата обозначает получение/проверку ответа, а не неизвестное точное время первоначальной
установки в системном AlarmManager. Подтверждение постановки отдельно от проверки звука:
существующий пробный сигнал и отметка «Я услышал сигнал» сохраняются.
Windows самостоятельно никогда не создаёт подтверждение от телефона.

## Владелец состояния и канал

Использовать реальный `WakeAlarmStatus` из `TauriAndroidWakeAlarmGateway` после reconcile,
уже получаемый `SleepScheduleService.syncAlarm()`. Служба сохраняет необязательный
`androidAlarmReport` вместе с текущим SleepScheduleState и существующим record schema v1.
Report входит в уже зарегистрированный sync payload `sleep_schedule`. Новые серверные
таблицы, endpoints, ключи, разрешения аккаунта или службы Android не нужны.

Report содержит источник ANDROID, время проверки, идентичность проверенного расписания,
outcome CONFIRMED / DISABLED / PERMISSION_REQUIRED / ERROR / NOT_CONFIRMED,
подтверждённую версию настроек, ID и время фактического следующего сигнала. Это последний
известный ответ телефона, а не индикатор его текущего присутствия в сети.
Не передавать произвольный native error text или дополнительные сведения об устройстве.

Настройки и report — разные факты. Загрузка или синхронизация report не меняет время подъёма,
не выполняет подготовку и не подтверждает запись сна. Неподдерживаемый gateway на Windows
не перезаписывает report. Старые записи без поля читаются как «Нет подтверждения».

## Проверка актуальности

Идентичность расписания вычисляется однозначно из текущих настроек и конкретного следующего
occurrence: settings version/updatedAt, enabled, bedtime/wakeTime/timeZone, alarm sound,
quiet mode, ID/cycleDate/scheduledAt и relevant reminder suppression. Это идентификатор
сравнения, не криптографическая подпись.

CONFIRMED разрешён только для настоящего supported Android status SCHEDULED с нужными
разрешениями, совпадающими settings version, occurrence ID и точным scheduledAt.
Согласование и UI используют одну application-проверку вместо двух разных правил.
Во время async reconcile настройки могли измениться: перед сохранением report проверять
идентичность текущего repository state атомарно; запоздалый ответ не подтверждает новый план.

После изменения настроек, пропуска ближайшего подъёма или перехода к другому occurrence
прежний report остаётся историческим и явно не считается актуальным подтверждением.
При ошибке очередной проверки не оставлять зелёный актуальный статус от старого успешного
ответа. Время последнего известного ответа отображать явно, без обещания доставки сигнала.

## UI-контракт

FEATURE → обратное подтверждение реальной постановки Android.
USER GOAL → понять, дошли ли текущие настройки до телефона.
EXISTING LOGIC → SleepScheduleService, WakeAlarmGateway, sleep_schedule sync, AlarmStatusPanel.
PAGE ARCHETYPE → расширение текущей компактной status card.
SECTION COLOR → действующая Graphite/Jade; success/attention/error по смыслу.
MAIN VISUAL CENTER → текущий статус и одно следующее действие.
REUSE → AlarmStatusPanel, проверка статуса, permissions и пробный сигнал.
MOBILE → один столбец, touch controls ≥44px, readable timestamp.
REFERENCE → текущий экран раздела; отдельный визуальный архетип не вводится.

## Проверки и границы

Targeted domain/application tests: valid ack, missing permissions, mismatching version/ID/time,
new settings while reconcile pending, unsupported Windows does not forge or clear Android report,
failed record write/retry. Mapper/persistence tests: отсутствующее поле, Date round trip,
некорректные новые значения, сохранение existing settings/cycles/observations.
Sync tests: реальный capture/import sleep_schedule payload сохраняет report; импорт старых
настроек/неактуального report не создаёт текущий success. Scoped browser tests проверяют
Android-report → Windows read, даты/часовой пояс, stale/error/empty состояния на desktop/mobile.

Общий контракт и storage compatibility требуют test:fast и final verify. Полный E2E без
селекторов не требуется, если границы остаются в sleep flow и scoped tests не выявят
межсценарную регрессию. Физическая проверка Android отдельно при сборке/выпуске; browser
fixture не выдаётся за постановку настоящего телефона. Текущая задача накапливает изменения
для будущего общего выпуска; version, подпись и feed пока не меняются.
