# Общая аналитика LifeOS: обзор и детализация

**Дата:** 02.10.2026.
**Статус:** пользователь утвердил визуальную композицию «обзор → детализация» 02.10.2026 и
разрешил реализацию. Спецификация и интерактивный макет стали опорой для продуктового кода;
фактическая приёмка реализации выполняется отдельно.

## 1. Цель и сценарий

Пользователь хочет понимать общую картину жизни: результаты, время, баланс и тенденции.
Обзор должен связывать разделы LifeOS и позволять объяснить каждое число исходными записями.

Сценарий: открыть «Аналитику» → выбрать неделю или месяц → увидеть основные изменения →
выбрать показатель или день графика → посмотреть записи → открыть исходную сущность →
вернуться к тому же периоду и показателю. Аналитика не оценивает ценность жизни по числу задач.

Первый полезный релиз охватывает результаты, рабочее время, цели, баланс, состояние,
прогулки, подготовку ко сну и события памяти. Для каждой темы используется существующий
источник; отсутствие источника отображается отдельно от нулевого результата.

## 2. Проверенная основа и ограничения

Исследован только активный worktree `D:/LifeOS-App`. До начала работы он содержал изменения
в прогулках, синхронизации, целях, потребностях и planner. Эти изменения не принадлежат этому
этапу; их присутствие не является доказательством готовности к релизу.

| Источник               | Что доступно                                                            | Ограничение                                                                     |
| ---------------------- | ----------------------------------------------------------------------- | ------------------------------------------------------------------------------- |
| `LifeAction`           | Текущее выполнение, дата завершения, архив, удаление, связи, повторения | Не неизменный журнал всех исторических выполнений                               |
| `ActionSession`        | Датированные рабочие интервалы, паузы, цель на момент начала            | Только зарегистрированное время; не все 24 часа                                 |
| `ProgressContribution` | Вклады с датой, источником и значением                                  | Начальные значения, отменённые и ожидающие значения требуют отдельной обработки |

## 4. Структура первой версии

### Обзор

- Заголовок «Аналитика», переключатель недели/месяца, диапазон с переходами назад/вперёд.
- Четыре KPI: выполненные действия, учтённое время, цели с вкладом, средняя энергия.
- Главный график: время / действия / энергия; предыдущий период — приглушённая серия.
  Каждая серия названа текстом, значения доступны с клавиатуры и через список.
- «Что заметно»: не более трёх описательных наблюдений с переходом к доказательствам.
- «Внимание к сферам»: распределение учтённого времени по текущей классификации.
- «Движение к целям»: вклады за период и текущий прогресс отдельно. Единицы — по текущей
  конфигурации измерения цели, с явной подписью; историческая единица не гарантируется.
- «Состояние»: четыре шкалы дневника и число заполненных дней.
- «Восстановление и события»: прогулки, дни подготовки ко сну, события памяти.
- «О данных и расчётах»: определения, ограничения покрытия и правила исключения.

Обзор не содержит единого «индекса жизни», рейтинга человека или автоматически заданной нормы.
Рост часов не окрашивается как успех. Отдых и отсутствие записей не обозначаются ошибкой.

### Детализация

Маршрут `#/v2/analytics` с `period=week|month`, `date=YYYY-MM-DD`,
`topic=overview|results|time|goals|balance|state|rest|memory`, необязательным `day`.
Адреса добавлены в runtime; выбранные период, тема и день сохраняются в hash-маршруте.

Фильтр дня может только сужать выбранный период. Некорректная дата нормализуется через
существующий `DayDate`; неизвестная тема заменяется обзором; будущее не открывается.
Back восстанавливает период, тему, день и позицию просмотра. Переход к задаче использует
существующее открытие action panel, к другим сущностям — штатные маршруты.

Таблица или список показывает точные исходные записи, единицы и определение метрики.
Записи, составляющие KPI и график, происходят из того же снимка. Если источник уже удалён
после загрузки, показывается понятное состояние «Запись недоступна», без краша и догадок.

На mobile длинная помесячная ось разрежается до нескольких подписей; минимальная touch-zone
интерактивного дня 44×44. Если 28–31 точка не умещается, выбор конкретного дня происходит
через доступный список/селектор под графиком, а не через микроскопические области касания.

## 5. Периоды, сравнения и даты

1. Стартовый период — последняя полная неделя: это готовый итог для осмысления.
   Можно перейти к текущей неделе. Месяц — календарный, не планировочный `thirty_days`.
2. Неделя начинается в понедельник. Расчёт использует один `asOf` и локальную временную зону
   устройства на момент запроса, как текущие отчёты LifeOS. Зона явно доступна в объяснении.
3. Итоги текущего периода включают сегодняшний день до `asOf`, будущие дни не равны нулю.
   Для действий основная дата — `completedOn`, fallback — локальная дата `completedAt`.
4. Сравнение текущего периода использует только завершённые дни. Сравниваются первые N полных
   дней этого периода и первые N предыдущего. Подпись отдельно называет оба диапазона;
   сравнение может отличаться от общей KPI-суммы, включающей сегодня.
5. Если полных дней нет, сравнение отсутствует. Если предыдущий месяц короче,
   N ограничивается общим числом сопоставимых дней; обе даты показаны явно.
6. Завершённые месяцы сравниваются полными итогами с числом дней каждого месяца.
   Разницу сумм нельзя называть ростом продуктивности. В v1 предпочтительна абсолютная разница.
7. При отсутствии предыдущих записей — «Ранее записей не было», без деления на ноль.
   Для средних оценок сравнение только при минимум 3 заполненных значениях в каждом диапазоне
   по существующему контракту `compareDiaryAverages`.
8. Рабочие интервалы пересекаются с полуинтервалом периода, делятся по локальным полуночам;
   паузы исключаются. Учесть DST, границы месяца/года и открытую сессию, обрезанную по `asOf`.
   Единица исходной точности — миллисекунда; округление только при отображении, не по сессиям.
9. Просмотр прошлой недели не переносит текущую оценку баланса в прошлое. В недельном обзоре
   показывается распределение времени; исторические оценки — только отдельные доступные месячные
   снимки с явной подписью месяца. Не интерполировать отсутствующие месяцы.

## 6. Метрики и действительность

| Метрика            | Определение                                                                                                         | Что не входит                                                                               |
| ------------------ | ------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------- |
| Выполнено действий | Количество разных действительных выполнений в диапазоне, включая архив                                              | Удалённые, отменённые, повторно открытые; счёт не означает историческое исполнение плана    |
| Учтено времени     | Пересечение рабочих интервалов сессий с периодом без пауз                                                           | Общий `actualMinutes` дополнительно не прибавлять; прогулки не прибавлять к рабочим сессиям |
| Целей с вкладом    | Distinct `goalId` неудалённых целей среди действительных `completion/manual/backfill` с `amount !== null` в периоде | `initial`; отменённые вклады; `amount: null` — ожидает результата и не входит в KPI         |
| Энергия            | Среднее заполненных energy 1–5 завершённых дневных записей                                                          | Черновики и пропуски; у каждой средней собственный sample count                             |
| Время по сферам    | Сессия → `goalIdAtStart` → текущая сфера/направление цели; иначе «Без сферы»/недоступно                             | Не подставлять нынешнюю цель действия вместо сохранённой цели сессии                        |
| Прогулки           | Существующий `analyzeWalks`: завершённые, активная длительность, даты, пары оценок                                  | Удалённые; отсутствие пары не превращается в нулевой эффект                                 |
| Подготовка ко сну  | Отдельно дни `ALL_DONE` и `WITH_SKIPS`; пропуски показаны отдельно                                                  | `SKIPPED_TODAY` не считать завершённой подготовкой; не выводить «часов сна»                 |
| События            | Уникальные не удалённые MemoryEvent по дате события                                                                 | Не удваивать один и тот же Memory ID; не считать импортированный текст вторым выполнением   |

Нулевой числовой вклад — зарегистрированное значение; отрицательный вклад/коррекция может быть
действительным, но не обязательно означает улучшение. Цели без количественного измерения
показывают записи/выполнения отдельно, не получают выдуманный процент. Число целей с вкладом
и число продвинувшихся/достигнутых целей — разные понятия.

Неколичественные выполнения без `ProgressContribution` не входят в этот KPI. Если измерение
позднее выключили, действительные сохранённые вклады остаются фактами для счёта, но не получают
выдуманную единицу или процент. Действительность вклада проверяет `voided`, актуальную
`completionKey` и сохранённое завершение неудалённого действия. Изменение текущего
`ContributionLink` само по себе не отменяет уже сохранённый вклад.

Архив сохраняет результаты. Удаление и повторное открытие действия снимают его выполнение и
связанные недействительные вклады; повторное завершение относится к новой дате/completionKey.
Для predicate `contributionIsEffective` нужна отфильтрованная карта неудалённых действий:
он сам по себе не проверяет удаление. Самостоятельные сессии времени сохраняются даже при
недоступном действии; пользователь видит «Действие недоступно» и фактический интервал.

Отчёт пересчитываемый по действительным данным, а не замороженный аудиторский журнал.
Общий процент несопоставимых целей и свободные текстовые потребности не агрегируются в индекс.

## 7. Архитектура и владение

Направление: UI → Presentation → Application → Domain; Infrastructure реализует read-порт;
App собирает зависимости. UI не обращается к IndexedDB и не производит записи.

Предлагаемые модули для этапа реализации:

- `application/analytics/`: период, чистые проекторы, `GetAnalyticsOverview`, evidence и сравнения.
- `application/ports/AnalyticsSnapshotReader.ts`: один интерфейс согласованного чтения.
- `infrastructure/persistence/IndexedDbAnalyticsSnapshotReader.ts`: необходимые существующие
  stores в одной readonly-транзакции, существующие record mappers, завершение после commit чтения.
- `presentation/planner-v2/analytics/`: обзор, график, источник данных, детализация, загрузка/ошибка.
- `app/composition/`: подключение `analytics`; `PlannerNavigation`/`PlannerWorkspace` — один новый
  маршрут и пункт; текущие сценарии и навигационные механизмы не переписываются.

Снимок временный, существует только для запроса/страницы. Не вводить aggregate store, миграцию,
новый sync-формат или второй владелец предметных данных. Не получать «согласованный снимок»
через `Promise.all` отдельных транзакций: между чтениями может произойти запись другого экрана.
Сначала ставятся все IDB-запросы в одной транзакции, затем результат проецируется вне неё.

Переиспользовать чистые функции интервалов, вкладов, дневника, баланса и прогулок. Существующий
`buildWorkTimeReport` включает текущий план: в аналитику переносится его фактический расчёт,
а исторический план не выдаётся за snapshot.

Открытие аналитики не вызывает `planning.periods.load()` (метод может записывать состояние),
генерацию повторений, backfill, `balance.refreshSnapshots()` или сохранение дневника.
Нет прошлого balance snapshot — показать отсутствие данных.

В v1 запрос выполняется при открытии/смене периода и при явном обновлении. Изменения из других
экранов/устройств должны инвалидировать снимок через подходящий общий change source; одних
`CommittedPlannerChanges` недостаточно, потому что там нет всех сессий/дневника. Поздний ответ
старого периода не может заменить выбранный новый. `asOf` фиксирован на весь ответ.

Инвалидация помечает весь снимок устаревшим и показывает «Данные изменились — Обновить».
До обновления обзор и детализация продолжают использовать один старый снимок с его `asOf`;
после успешного обновления все блоки заменяются атомарно. Не обновлять отдельные карточки
данными новой версии, сохраняя старый evidence.

## 8. Состояния и доступность

- Loading: skeleton повторяет геометрию KPI/графика; `aria-busy`, без яркой анимации.
- Первый запуск: объяснение пользы и переход в «Сегодня». Не рисовать успешные нулевые показатели.
- Период без записей: сохраняется период, можно выбрать другой; это не ошибка.
- Частичные данные: доступные блоки работают, отсутствующая энергия отображается «—» и с CTA
  к дневнику. У каждого блока своё покрытие, а не общий вводящий в заблуждение процент полноты.
- Ошибка чтения: понятная ошибка и «Повторить»; ошибка не подменяется нулями. Если согласованный
  снимок не прочитан, не смешивать новый период со старыми частями.
- Success: готовый обзор; при явном retry/update короткое «Обзор обновлён».
- Disabled: переход к будущему периоду и повторный запрос в процессе загрузки блокируются.
- Табуляция, видимый focus, названия icon-only controls, график со списком-эквивалентом.
- Нет обязательной анимации; reduced motion; подписи и геометрия передают смысл без цвета.

1. **A01 — расчёты и контракт чтения.** Согласованный snapshot, периоды, 4 KPI, evidence,
   unit/integration fixtures для архивов, повторного открытия, неполных данных и границ дат.
2. **A02 — обзор.** Маршрут, навигация, KPI, главный график, состояния; реальные данные.
3. **A03 — детализация.** Выбор дня/показателя, исходные записи и сохранение контекста возврата.
4. **A04 — контекст жизни.** Баланс, цели, дневник, прогулки, подготовка ко сну и память;
   наблюдения только по проверяемым правилам, без причинных утверждений.
5. **A05 — приёмка.** Targeted/render, scoped E2E, один актуальный verify, desktop/mobile,
   клавиатура, console, comparison с approved reference и правило №38.

После первой версии отдельно планируются снимки первоначального плана, история классификации,
надёжный plan/fact и статистические связи. Новые источники/поля не добавляются скрыто ради графика.
Экспорт, конструктор виджетов, AI-интерпретации, внешняя телеметрия и новые разделы не входят в v1.

## 10. Приёмка реализации

1. KPI, график и evidence используют одни исходные записи и cutoff, с агрегацией своей метрики:
   счёт целей — distinct за период, энергия — среднее исходных заполненных оценок, не среднее
   средних. Время и выполнения суммируются по дням без повторного округления.
2. Архив не меняет счёт выполнений; reopen/удаление применяют описанные правила; время сохраняется.
3. Паузы и сессии через полночь считаются корректно; ручной агрегат не удваивает таймер.
4. Ноль, неизвестно, ожидающий вклад, отсутствие источника и ошибка различимы.
5. Текущий период сравнивается по законченным дням с подписанным диапазоном.
6. Смена периода/быстрые ответы/Back не смешивают данные и не сбрасывают контекст неожиданно.
7. Прочитанный отчёт не создаёт повторения, снимки, вклад или иные предметные записи.
8. На desktop 1600×900/1280×720 и mobile 390×844/360×800 нет горизонтального переполнения;
   график доступен без hover и без цвета; controls сохраняют touch targets и focus.
9. Ошибка одного запроса не удаляет данные; retry восстанавливает обзор.
10. Открытие/возврат в действующие разделы не ломает их flow.

План проверок кода: targeted расчёты и snapshot integration → при новом общем контракте
`npm run test:fast` → `npm run verify` → scoped `current.analytics.spec.ts` на desktop/mobile.
Порядок E2E относительно verify допускается менять для локальной диагностики. Полный E2E
автоматически не нужен: планируется добавление одного маршрута, а не переписывание routing/shell.
Если реализация выявит общий риск, объём пересматривается по `docs/codex/TEST_MATRIX.md`.

Для текущего документационного этапа достаточно проверки ссылок, форматирования, diff и browser
QA макета. Это не доказательство работы будущих аналитических расчётов или готовности продукта.
