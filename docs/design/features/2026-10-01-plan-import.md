# Импорт плана

Статус: определённый контракт стандартной формы, без отдельного visual approval.

## Цель и область

Загрузить подготовленный JSON-план с направлениями, целями и действиями, просмотреть его
и добавить в существующие данные одной командой. Личные планы не входят в исходный код.
Существующие записи не обновляются, не удаляются и не восстанавливаются из корзины.

## Дизайн-контракт

- Раздел: Цели; новая функция существующей страницы.
- Архетип: существующая форма в PlannerSheet; главный центр — содержание импортируемого плана.
- Атмосфера: текущая единая графитовая рабочая поверхность; jade для primary, золото только
  для приоритета. Общие токены и каскад planner-v2 → planner-master → planner-premium.
- Компоненты: PlannerSheet, planner-form, planner-form-actions, planner-muted, planner-error.
- Mobile: панель на доступную ширину, вертикальные строки, controls не меньше 44 px.
- Состояния: выбор файла, чтение/проверка, preview, сохранение, итог, ошибка с повтором.
- Предварительный просмотр: название, период, количества, направления, цели со сроками,
  раскрываемые действия с датами. Просмотр не изменяет предметные данные.
- Отдельный approved reference: не требуется для стандартной формы.
- Baseline: /#/v2/goals в активном worktree, desktop 1366×900 и mobile 390×844;
  system sans-serif, primary rgb(129, 207, 171), фон rgb(17, 24, 27).

## Формат и сохранение

`format: lifeos-plan`, `version: 1`, стабильный `id`, `title`, `startDate`, `endDate`;
массивы `spheres`, `directions`, `goals`, `actions`. Каждая запись имеет стабильный `key`.
Направления ссылаются на `sphereKey`, цели на `directionKey`, действия на `goalKey`.
Даты YYYY-MM-DD; дата действия означает день выполнения, а dueDate цели — срок результата.
Файл ограничен 1 MB, всего до 1000 записей. Неизвестные поля отклоняются.

До первой записи проверяется весь файл, уникальность ключей, ссылки, даты и Domain invariants.
Порядок: сферы → направления → цели → действия. Сферы с тем же нормализованным именем
переиспользуются. Прочие существующие сущности сопоставляются по стабильному ID импорта.
Если переиспользованный родитель архивирован, удалён или перемещён в другой контекст,
импорт останавливается с понятной ошибкой. Существующие значения не перезаписываются.
Стабильный ID импортированной сферы имеет приоритет перед связями направлений. Для ранее
переиспользованной сферы без импортного ID смена имени также вызывает остановку: автоматически
отличить переименование от переноса направления без отдельного журнала соответствий нельзя.

Import-scoped IdGenerator выдаёт стабильный entity ID, затем обычные event IDs. Используются
CreateSphere/CreateDirection/CreateGoal/CreateLifeActionDraft и production JournalUnitOfWork.
Атомарны отдельные существующие команды, не весь файл. При сбое возвращаются точные счётчики
и последняя ошибка; повтор продолжает импорт. ID conflicts не обходятся новым UUID.
Удалённые записи не восстанавливаются. После физического удаления повтор может создать их вновь.
Схема IndexedDB и общий механизм sync не меняются.

## Проверки

Targeted integration: preview без записи; весь файл проверяется заранее; повтор, reopen,
переименование, существующая сфера, конфликт родителя, удалённая цель, частичный сбой,
конкурентный импорт. Scoped E2E: загрузка/ошибка/preview/сохранение/reload/повтор desktop/mobile.
После стабилизации npm run verify. Полный E2E не нужен: схема и общие flows не изменены.
