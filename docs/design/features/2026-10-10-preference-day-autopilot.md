# Автопилот дня по фокусу, пожеланиям и распорядку

Дата: 10 октября 2026 года. Статус: письменная спецификация утверждена пользователем в чате; исходный патч реализован и проверен. [Результат и evidence](../../codex/reports/2026-10-10-preference-day-autopilot.md). Native выпуск отложен до отдельной команды.
Подтверждение от 10.10.2026 разрешает подготовить план реализации; код — после проверки плана.
Изменение существующего сценария «Распорядок → Автопилот дня».

## Что получит пользователь

Один раз выбрать главное направление или цель, например «Инвестиции», и сохранять этот выбор.
На конкретный день добавить пожелание текстом или голосом, например «Сегодня хочу ещё немного
заняться порядком». Автопилот рассматривает общий список открытых действий, предлагает подходящие
дела и размещает их в свободном времени с учётом утренней подготовки, прогулки, отдыха,
вечерней подготовки и сна. Перед применением пользователь видит весь план, причины выбора,
неизвестные длительности и то, что не поместилось; может убрать дело и изменить длительность.

Время подъёма и отбоя берётся из действующих настроек сна. Длительность подготовки задаётся
отдельно: её сейчас нет у пунктов чек-листа. Медитация остаётся вне этой задачи.
Выпуск обновления выполняется только по отдельной команде пользователя после реализации и проверок.

## Какой вариант выбран

Основной вариант — локальные правила выбора и расписания с видимым сопоставлением пожеланий.
Он работает с существующими направлениями, целями, действиями и без доступного AI-сервера.
Общий текстовый помощник сегодня возвращает обычный ответ и не предоставляет проверенный
контракт выбора действий; использовать его ответ как готовое расписание нельзя.

Альтернатива — отдельный AI-разбор произвольных пожеланий, который возвращает проверенные IDs,
после чего локальный планировщик проверяет ограничения. Для него нужны отдельная операция сервера,
включённая AI-конфигурация и проверка доступности. Эта интеграция не входит в первый патч.
Базовый сценарий сохраняет ручной выбор подходящих направлений и голосовой ввод текста.
Пользователь проверяет эти границы вместе с письменной спецификацией.

## Предпочтения и пожелания

- Сохраняемый главный фокус — существующий активный Direction или Goal по ID. При выборе
  направления учитываются прямые связи действий и действия связанных целей; при выборе цели —
  её прямые и действующие дополнительные contribution-связи.
- Фокус относится только к автопилоту. Он не изменяет звёздочку главного действия, месячный фокус,
  прогресс целей или результаты выполненных действий.
- Дневные пожелания относятся к выбранной дате. Поле использует существующий голосовой ввод.
  Локальное сопоставление ищет названия направлений, целей и действий: нормализация регистра,
  пробелов, пунктуации и ё/е, затем существующий поиск. В UI видно «Учтём: …» с реальными объектами.
  Одинаковые названия показываются с родительским контекстом для выбора.
- Нераспознанная или неоднозначная часть пожелания получает видимое уточнение. Она не превращается
  молча в придуманное действие или дополнительный приоритет. Пользователь может выбрать объект
  из общего каталога; построение с неразрешёнными пожеланиями требует явно убрать их из запроса.
- В расширенных настройках — лимит предложенных дел (по умолчанию 5, от 1 до 12),
  длительности ритуалов и время/длительность прогулки. Эти defaults видны и редактируемы.
  Главное направление сохраняется; пожелания и исключения остаются привязаны к дате.
- Настройки автопилота и черновики пожеланий сохраняются на устройстве. Это гарантирует
  восстановление после закрытия приложения. Перенос этих новых настроек между устройствами
  не заявляется частью первого патча; общий уже применённый план синхронизируется существующим каналом.

## Из каких действий выбираем

Сервис читает весь доступный каталог через `LifeActionRepository.findAll`.
Отсутствие такой возможности — явная ошибка конфигурации, а не скрытый переход к списку «Сегодня».
Рассматриваются открытые draft/ready действия, включая импортированные, без даты,
сегодняшние и просроченные. Архив, корзина, завершённые и отменённые не участвуют.

Действия с будущей датой видны как исключённые из сегодняшнего подбора; их дата не переносится
автоматически. Повторения рассматриваются только как существующие допустимые экземпляры:
не создавать будущие экземпляры серий и не подтягивать несколько просроченных экземпляров одной
серии в один день. Для каждой серии — сегодняшнее повторение, иначе просроченное с наиболее
поздней датой до выбранного дня.
Его перенос сохраняет идентичность экземпляра и отмечает ручное изменение даты.

Работающие и приостановленные сессии, прошедшие окна и пользовательские фиксированные окна
защищены. В «Заполнить свободное» сохраняются существующие окна. «Пересобрать остаток»
перестраивает только будущие автоматически созданные блоки и изменяемые окна действий;
ручные блоки распорядка остаются ограничениями. Конфликты фиксированных окон показываются.

Порядок подбора:

1. Сохранить явно назначенные обязательные/фиксированные дела и существующее главное дело дня.
2. Найти первое подходящее дело по главному фокусу.
3. В пределах лимита предложить по одному подходящему делу на каждое распознанное дневное
   пожелание в порядке пользователя; неохваченные пожелания показать с причиной.
4. Оставшиеся места до лимита заполнять делами главного фокуса.
5. При отсутствии фокуса и пожеланий сохранить прежний подбор сегодняшних действий.

Внутри одной группы: high → normal → low, затем просроченная дата, время создания, ID.
Подходящее длинное дело, которое не помещается, не блокирует подбор более короткого.
Одно действие учитывается один раз, даже если подходит нескольким пожеланиям.
Автопилот не добавляет посторонние дела ради заполнения свободного времени.

## Время дня и распорядок

Начало и окончание диапазона задаются явно. Для сегодня начало не раньше текущего момента.
Сохранённое доступное время помогает установить окончание, однако итог ограничен вечерней
подготовкой и сном. Если доступное время не настроено, пользователь видит и подтверждает
диапазон; скрытого допущения «ещё 8 часов» нет.

Подъём и сон проецируются из `SleepScheduleService.getState` в его часовом поясе.
Ночной режим после полуночи корректно относится к соседней календарной дате; расчёт использует
реальные дату/время, а утро/вечер/сон показываются как вычисленные ограничения выбранной даты.
Полуночная часть учитывается до минуты 1440 в расчёте; она не записывается в RoutineBlock
с недопустимым endTime «24:00».

- **Утро:** защищённый блок от подъёма на заданную длительность (первое видимое предложение —
  30 минут). Внутри — существующие утренние практики/душ; этот патч не создаёт новый чек-лист.
  После него могут начинаться рабочие дела. При пересборке днём утро остаётся в прошедшей части.
- **Вечер:** защищённый блок непосредственно перед отбоем на заданную длительность
  (первое видимое предложение — 45 минут). Показывает ссылку на действующую подготовку ко сну
  с её текущими включёнными пунктами. Изменять чек-лист и настройки будильника автопилот не должен.
  Обычные дела заканчиваются до этого блока.
- **Прогулка:** отдельный обязательный для выбранного дня блок. Настроенный план прогулки
  использует `walkPlan.targetMinutes` и заданное окно; не создаётся его копия.
  Если плана нет, предлагается редактируемый блок «Прогулка» длительностью 30 минут с явным
  переключателем включения. При применении он сохраняется как блок распорядка, без создания
  выполненной прогулки. Начало прогулки использует существующий сценарий.
  Пользователь выбирает начало блока; оно не угадывается по названиям дел.
  История и текущая прогулка берутся из существующего WalkRepository: завершённая прогулка
  выбранного дня выполняет это условие без добавления второй. Running/paused прогулка —
  защищённый блок; для известной цели учитывается остаток длительности, иначе пользователь
  указывает ожидаемое окончание до построения рабочих окон.
- **Отдых:** видимые паузы между рабочими блоками. Их длительности берутся из действующих
  настроек Pomodoro: короткий отдых после накопленного рабочего интервала, длинный после
  четырёх интервалов. Пауза не вставляется посреди одного неделимого действия; его preview
  поясняет применение собственного Pomodoro-таймера внутри длинного рабочего блока.
  Прогулка сбрасывает счётчик непрерывной работы и не считается второй короткой паузой.
- **Запас:** сохраняются 15% свободного времени после обязательных блоков, минимум 30 минут,
  при короткой подтверждённой ночи — 25%. Резерв ограничивается реальным остатком. Он
  отличается от отдыха: отображается как незаполненное время, не как выполненное действие.

Если отсутствует режим сна, нельзя выводить фиктивный подъём/отбой. Форма требует указать
границы дня и времена утренней/вечерней подготовки либо перейти к настройке сна.
Если день уже закончился, предлагается выбрать завтра. Превышение обязательными блоками
доступного диапазона приводит к объяснению конфликта, а не к сокращению ритуалов или сна.

Оценка времени действия берётся из его заданной длительности; оценка 25 минут при её отсутствии
явно помечается как предположение и редактируется. Применение окна не сохраняет это предположение
как личную оценку пользователя. Метрики называются «Работа в плане», «Распорядок и отдых»,
«Свободно»; они не пополняют аналитику фактической концентрации.

## Источники состояния и границы слоёв

`LifeAction` остаётся единственным владельцем даты и рабочего окна действия.
Не сохранять копии действий внутри отдельного документа «план дня».

Утро, вечер и сон — вычисленные ограничения из действующего SleepSchedule и сохранённых
длительностей автопилота. Их чек-листы/будильники не копируются. Обновление настроек после
применения показывает новые ограничения и возможный конфликт с сохранёнными окнами действий;
действия сами не передвигаются, пользователь собирает новый preview.

Существующий `RoutineBlock` используется для применённых блоков прогулки без
действия и отдыха: существующие категории, assignment reminder/walk, recurrence none,
anchorDate выбранного дня. Это явное расширение ограничения первого выпуска,
описанного в [спецификации от 04.10.2026](2026-10-04-day-autopilot.md).
Не требуется включать весь старый редактор распорядка, overrides и execution flow.

Автоматические блоки имеют детерминированный технический ID по дате, типу и порядковому номеру.
Человекочитаемые названия не определяют принадлежность автопилоту. Повторное применение не
создаёт дублей; пересборка меняет/удаляет только будущие блоки этого владельца с проверкой версий.
Существующие ручные RoutineBlock учитываются как занятое время и никогда не перезаписываются.

Новые preferences/draft application-порты реализуются через существующий IndexedDB
`sync_settings` с отдельными ключами и версиями. Они не добавляются самовольно в общий
`MeaningfulUserSettingsRecord`: текущий нормализатор/совместимость этого wire-контракта ограничены.
Отсутствующие записи открывают показанные defaults; неверные записи дают сообщение восстановления.

Блоки распорядка уже представлены в sync registry и snapshot mapper; подключить их
сохранение через `JournalUnitOfWork`, mutation recorder и существующие атомарные транзакции,
без новых таблиц, schema migration и нового типа sync-объекта. Временной календарь и страница
автопилота читают одинаковую объединённую проекцию LifeAction/RoutineBlock.
При наличии существующей связи RoutineBlock → action окно показывается один раз:
рабочее время берётся из LifeAction, а ссылка блока используется для контекста.

Domain отвечает за допустимость кандидатов, порядок, диапазоны, отсутствие пересечений и
баланс времени. Application загружает связи/настройки, готовит projection и команды применения.
Infrastructure обеспечивает версии, транзакцию, snapshot/sync. Presentation содержит форму,
редактируемый preview и сообщения; она не сканирует IndexedDB и не рассчитывает правила выбора.

## Preview, редактирование и применение

Preview содержит исходные версии и даты действий, окна блоков, версии настроек/распорядка,
момент построения, распознанные пожелания, причины выбора и исключения.
Редактирование длительности или удаление предложенного дела запускает локальный пересчёт;
невозможность сохранить защищённые блоки отображается до применения.

Перенос выбранного backlog-действия на дату плана и его окно сохраняются вместе:
использовать правила `SetLifeActionPlan`, включая reschedule events для ready, manualDate
повторения и единственность главного действия. Не выполнять последовательные самостоятельные
команды сохранения каждого дела.

Одна `JournalUnitOfWork` транзакция записывает изменённые LifeAction, будущие RoutineBlock,
необходимые journal entries и sync mutations. Удаление будущих автоматических блоков также
входит в эту транзакцию; версия/сессия/распорядок/настройки сна проверяются перед записью.
Невозможность атомарно проверить источник ограничений — ошибка применения, а не частичный план.

Наступившее начало изменяемого окна, изменение исходной даты/версии, новый ручной блок,
обновление настроек сна или запущенная сессия делают preview устаревшим. Ничего не применять;
сохранить пожелания и предложить собрать остаток дня заново.
Повторное подтверждение уже применённого preview не создаёт повторные сущности/события.
Отмена preview сохраняет исходные действия, ритуалы и расписание.

## Интерфейс и состояния

Форма: главный фокус; пожелания на выбранную дату и распознанные объекты; диапазон времени;
компактная сводка ритуалов/прогулки/отдыха с раскрываемыми настройками; «Собрать мой день».
Preview: одна хронологическая шкала, различимые подписи работа/ритуал/прогулка/отдых/запас,
причины выбора, управление длительностью и исключением дела; итог и «Применить план».

После применения та же шкала доступна при повторном открытии и в календаре времени.
Пункты ритуалов открывают существующие страницы. Отметки их выполнения, сон и реальные focus
sessions остаются в соответствующих сценариях; применение расписания не отмечает их выполненными.

Ready/loading/empty/error/stale/success используют существующие patterns. Empty может содержать
только распорядок: отсутствие подходящих действий не скрывает прогулку и подготовку.
Удалённый/архивированный фокус требует выбрать новый; исходный выбор не подменяется другим.
Keyboard, focus-ring, accessible labels и live feedback обязательны. Mobile использует вертикальный
порядок, раскрываемые подробности и широкое основное действие.

## Критерии приёмки и проверки

1. В общем списке есть инвестиционные и бытовые дела без сегодняшней даты. Фокус «Инвестиции»
   и пожелание «Порядок» дают выбранные связанные дела с причинами; остальные не заполняют день.
2. Прямое направление, цель внутри направления и дополнительные действующие goal-связи
   учитываются; повторяющиеся совпадения не создают дублей.
3. Нераспознанное пожелание, одинаковые названия, отсутствующий/удалённый фокус и пустой backlog
   имеют видимый путь исправления.
4. Утро, вечер, сон, прогулка, фиксированные окна и отдых учитываются до рабочих действий.
   Слишком длинное дело/короткий день показывают объяснение; дело не заходит в подготовку ко сну.
5. Неизвестная оценка остаётся неизвестной после применения, пока пользователь её явно не задал.
   «Работа в плане» не увеличивает фактически записанное время фокуса.
6. Не переносятся будущие повторы и не планируются несколько экземпляров серии; завершённые,
   архивные и удалённые действия не возвращаются.
7. Apply переносит backlog и записывает блоки атомарно; racing action/session/sleep/routine changes
   отклоняют весь preview. Отмена, повторный apply и rebuild не создают дублей.
8. Перезапуск сохраняет локальные предпочтения/дневной текст и применённое расписание.
   Snapshot round-trip и обмен между обновлёнными Windows/Android сохраняют применённые блоки
   и окна действий; версия 1.0.43 корректно читает существующие форматы без новых полей.
   Утро/вечер/сон проецируются из настроек соответствующего устройства; перенос новых
   длительностей/preferences между устройствами в этой версии не заявляется.
9. Scoped E2E: настройка → preview → редактирование → apply → reload → rebuild,
   desktop/mobile, keyboard и отсутствие необъяснённых console/page errors/overflow.
   Ночные границы, чужой часовой пояс, прогулка без заданной длительности и большие каталоги
   проверяются unit/integration тестами с синтетическими данными.

Реализация затрагивает общий domain/application-контракт: targeted tests → `npm run test:fast`
→ один `npm run verify` → scoped E2E автопилота/временного календаря на desktop/mobile.
Если будет выявлена необходимость общей миграции или неизвестная межсценарная регрессия,
объём пересматривается по AGENTS.md; существующие проверки не ослабляются.
Сам этот документ проверяется по ссылкам, согласованности правил, форматированию и diff;
production build, native сборки и полный E2E на стадии спецификации не запускаются.

## Границы первого патча

Без создания новых задач нейросетью, подключения нового AI-сервера, изменения подготовки/будильника,
добавления медитации, автоматического выполнения дел, новой аналитики и публикации обновления.
Свободный текст имеет описанное локальное сопоставление с явным уточнением; произвольное
семантическое понимание AI и синхронизация новых preferences требуют отдельного согласования.
