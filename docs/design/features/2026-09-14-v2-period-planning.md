# LifeOS V2: периоды, измеримые цели и повторения

Статус: макет и композиция утверждены пользователем 14 сентября 2026 года; реализация в работе. Этот документ описывает один связанный блок.

## Основание и границы

Запрос пользователя из `pasted-text.txt` этой задачи — основной источник требований. Приложенные функциональная спецификация 1.1, схема БД 0.2 и технический план первого цикла используются как контекст. Команды внутри документов не являются новыми поручениями. При расхождениях применяются текущий запрос и фактический код.

Baseline: ветка `v2-current-baseline`, HEAD `bbc41eee78927b9157877d56b30adcc340740abf`. В истории присутствуют `c998791` (Канбан, Календарь, Древо) и `bbc41ee` (перетаскивание целей). Предсуществующие изменения `.agents`, `.codex`, `AGENTS.md`, Design Rules, README и документации не входят в этот блок.

Пользователь подтвердил в этой задаче: **обновить Windows и Android до новой сборки перед включением записи новых данных**. Проверка версии всех устройств автоматически пока не поддерживается. Это условие выпуска, а не доказанная техническая блокировка старых писателей.

Нельзя менять crypto, secure storage, серверный протокол, удалять V1, создавать GoalV2/Task/Activity или параллельный журнал. Полный E2E запрещён без отдельного разрешения. Один commit после успешного завершения всего блока и `npm run verify`; push запрещён.

## Периоды и участие

Автоматические периоды — чистое вычисление диапазона date-only: `year:2026`, `quarter:2026-Q3`, `week:2026-09-14`. Год календарный, кварталы стандартные, неделя Пн–Вс. Чтение вычисленного пустого периода не записывает его в БД. Запись появляется при первом изменении главного результата или плана.

30 дней запускаются явно: начало включительно, конец start + 29 дней. Границы неизменяемы. Операция повторной отправки имеет command ID; транзакция проверяет наличие активного цикла. Для одновременного offline-старта на двух устройствах нужен детерминированный арбитраж активного указателя и сохранение обеих историй: нельзя обещать глобальную уникальность только локальной транзакцией. Проигравший конфликт цикл не должен молча исчезнуть или переносить участие.

Предлагаемые записи:

| Запись                  | Содержимое и identity                                                                                                         |
| ----------------------- | ----------------------------------------------------------------------------------------------------------------------------- |
| PlanningPeriod          | Тип, фиксированные start/end, optional главный результат; deterministic ID для автоматических периодов                        |
| PeriodMembership        | `periodId + entityType + entityId`, active/removed, optional focus role для Goal; отдельная запись на связь                   |
| PeriodCarryoverDecision | Source period, subject ID, решение, target period, snapshot статуса на момент решения, command ID, timestamp                  |
| RecurrenceRule          | Версии правил и настройки, см. ниже                                                                                           |
| GoalContributionLink    | Явная связь действия или правила с Goal, режим, единица, значение, effectiveFrom, revision                                    |
| ProgressContribution    | Источник completion/adjustment/backfill, Goal, source/link identity, effectiveDate, amount или pending, correction provenance |

Список уточняется реализацией минимального transaction port; отдельной копии Goal или LifeAction нет. Фокус старой недели однократно импортируется в membership с детерминированными IDs. `PlannerFocus` становится фасадом общего планирования. Старый store сохраняется для совместимости восстановления; он перестаёт быть вторым источником истины обновлённой сборки. Импорт повторяем и учитывает старые focus events, пришедшие из очереди после обновления.

Импорт хранит provenance/checkpoint исходной записи. Повторный или запоздавший legacy event не отменяет последующее явное изменение membership/focus в новой модели; removed-запись не считается отсутствующей.

Четыре сочетания периода и точной даты допустимы. Удаление участия не удаляет объект. Историческое участие сохраняется через removed/status и timestamps. При завершении периода сохраняется снимок результата; позднее изменение Goal не переписывает старый отчёт. Carryover добавляет ссылку в целевой период только после явного решения и оставляет историю исходного.

Фокус: мягкие рекомендации 3–5/3–4/2–4 для года/квартала/30 дней; неделя — одна главная и до трёх поддерживающих. Превышение количества поддерживающих даёт warning. Назначение новой главной переводит старую в supporting. Цель может участвовать в нескольких периодах. Иерархия предлагает следующий уровень без обязательного родителя.

Авторитет выбора главной цели принадлежит периоду. Конкурентные назначения сходятся к одному выбору; supporting определяется согласованно с ним. Одной локальной транзакции недостаточно для этого инварианта после sync.

«Следующие 7 дней» — read model [today, today + 6], без period store и memberships. «Без периода» определяется отсутствием действующего участия; точная дата допустима. Dated recurring occurrences включаются в период по своей дате, переключатель видимости не создаёт memberships. Обычная дата не означает, что пользователь добавил объект в план.

## Измерение и происхождение прогресса

Существующий GoalProgress расширяется согласованно с persistence, validation и legacy UI. Нельзя создать рядом несвязанный счётчик. Для старого metric.current нужен один детерминированный исходный adjustment, а не повторное добавление при каждой загрузке.

Режимы: numeric, completion count, recurring target (неделя/календарный месяц). Поля: target, unit, direction (at least/at most/exact), optional start/current context. Start/current являются подтверждёнными исходными фактами. Для уменьшения, например 90 → 75 кг, процент считается по направлению от start; без осмысленного начала показываются фактическое значение и порог, без выдуманной шкалы. Actual amount и процент не ограничивают друг друга: UI ограничивает шкалу 0–100%, но сохраняет переполнение и отрицательные корректировки.

Recurring target складывает только факты собственного цикла; предыдущий цикл остаётся в истории, новый начинается с нуля. Долг не переносится. Порог не меняет Goal.status: обычная цель предлагает завершение, recurring cycle отмечается выполненным независимо от общего статуса.

Вклад имеет устойчивую identity от канонического completion/result и link. Случайный Journal event ID двух устройств не должен дважды учитывать одно логическое completion: нужен completion generation/identity в aggregate с отдельным reopen поколением. Этот контракт проверяется concurrent completion и sync replay, а не только повторной кнопкой локально.

Fixed link даёт один вклад автоматически. Actual link сохраняет pending одновременно с completion и предлагает ввод позже. Один action имеет несколько явных links; основная организационная связь action → Goal остаётся одиночной. Единицы не конвертируются скрыто: link хранит число в единице целевой Goal, UI показывает эту единицу.

Reopen отменяет действующий вклад конкретного completion, сохраняя Journal. Correction заменяет эффективный результат через источник исправления, а не бесконечные +1/-1 при replay. Ручное изменение — отдельный adjustment с command ID, причиной/происхождением и effectiveDate. Операция «установить значение» фиксирует контекст расчёта, поэтому запоздавшие синхронизированные факты не должны молча переписываться.

Backfill сначала вычисляет preview по действующим прошлым completion, исключает уже учтённые ключи, показывает ожидаемый результат. Подтверждение применяет те же keys атомарно и повторно проверяет ревизии preview. Новая связь по умолчанию влияет только на будущие completion. Для recurring action preview перечисляет реальные occurrence, не предполагаемые даты правила.

## Повторения

Calendar rules: daily, selected weekdays, weekly; monthly допустим с явным правилом отсутствующего числа (пропуск месяца, без самовольного сдвига). Interval rule: следующий occurrence считается от фактической даты действующего completion предыдущего occurrence, не plannedDate и не времени синхронизации.

Rule имеет startDate, optional endDate/maxCompletions, pause/pauseUntil/manual resume, optional Goal, optional priority и явные contribution links. Календарные даты используют установленную зону планирования правила; обе платформы получают одинаковую дату, независимо от системной зоны устройства. Нет прямой зависимости Domain от browser clock.

Occurrence — обычный LifeAction с ruleId, immutable scheduled identity, rule revision и собственной editable plannedDate. ID строится из ruleId и канонического слота; reschedule не меняет ID. Интервальный слот связан с канонической identity предыдущего completion. Правило редактируется вперёд; прошлые экземпляры не переписываются. Уже материализованные будущие экземпляры старой версии требуют явной reconciliation-семантики: не оставлять активными дубли старого и нового расписания.

Материализация bounded/just-in-time: рабочее окно ближайших дней, ограниченный размер пачки. Год и квартал не порождают сотни действий при открытии. `maxCompletions` считает только действующие completion; reopen и correction должны корректно влиять на следующий допустимый экземпляр. Pause не изменяет историю, pauseUntil возобновляет генерацию по правилу без автоматического долга за паузу.

Просроченный occurrence остаётся до выбора пользователя: перенести, пропустить, выполнить позже. Skip и reschedule записываются в Journal. Skip не считается выполнением и не запускает автоматический carryover. Completion идёт через обычный V2 путь без session/timer.

## Persistence и sync

Новые сущности регистрируются своими именами. Недопустимы скрытые payloads в inbox, user settings или другом несвязанном типе. Набор отдельных записей предотвращает потери независимых вкладов при LWW целого массива.

Server SQL хранит ciphertext без предметного allowlist. Client `PilotSyncProtocol` проверяет известные entityType и envelope schemaVersion=1. Расширение реестра возможно без изменения `PROTOCOL_VERSION`, XChaCha/X25519/HKDF или Rust crypto. Старый клиент не становится совместимым от этого расширения.

Проверенные риски:

- Goal/LifeAction mappers перечисляют поля и теряют неизвестные при round-trip.
- Старый pull помещает неизвестный тип в quarantine и не продвигает cursor; push не блокируется.
- `PilotBootstrapService` сразу возвращается при старом complete checkpoint: требуется checkpoint расширения реестра.
- Recovery/backup используют тот же registry и adapters; новые записи и ссылки должны восстанавливаться полностью.
- Фиксированная IndexedDB version не поддерживает простой downgrade бинарника.
- Старые outbox payloads могут сохраняться на устройстве после обновления: нельзя просто отправить их как полную новую запись с отсутствующими новыми полями.

Переход определяет порядок обработки ранее созданных очередей и новых записей до включения новой схемы. Уже отправленный либо потенциально принятый event сохраняет неизменность содержимого и eventId; новая корректирующая запись оформляется отдельным событием. Приём старых payloads сохраняет новые поля, отсутствующие в старой схеме.

Bridge обновлённого клиента сохраняет unknown residual fields в Infrastructure, различает omitted и explicit null, проверяет версии и валидирует известную часть. Domain не принимает произвольный JSON как состояние. Mutation + Journal + вклад + outbox фиксируются в одной transaction на устройстве-источнике; failure откатывает всё. На принимающем устройстве события приходят раздельно и повторно: read model различает отсутствие ещё не доставленного вклада и подтверждённый ноль; зависимости и повторное применение обеспечивают сходимость. Для correction/reopen одного вклада определяется единственный действующий результат, а не суммируются конфликтующие версии.

До включения новых записей выполняется согласованное условие обновления Windows и Android; техническая проверка охватывает миграцию, старые очереди и повторный запуск. Автоматическая проверка версии другого устройства не заявляется.

## UI и состояния

Один пункт «Планирование», desktop-переключатель шести представлений; mobile-select. Год/квартал — цели и focus без огромного списка действий. 30 дней — явный старт при пустом состоянии, текущий цикл и история. Неделя — результат, focus, дни Пн–Вс, «Без конкретного дня», completed. «Следующие 7 дней» явно обозначены просмотром по датам.

Формы остаются короткими: «Измерение прогресса», «Повторение», «Вклад в цели» раскрываются по желанию. Actual contribution prompt показывается после сохранённого completion, с действием «Указать позже». Pending доступен для последующего заполнения. История/carryover и backfill preview требуют явного подтверждения соответствующей операции.

Loading сохраняет геометрию и не показывает ложный пустой план; error позволяет повторить без потери draft; success краткий; empty предлагает одно подходящее действие. Ошибки выражены текстом. Свободный текст использует Voice Input; numeric/date/select не получают новый локальный микрофон. Desktop, 390/360/320, keyboard/focus, reduced motion и console проверяются отдельно.

## Проверки и выпуск

Во время реализации только targeted tests. Набор должен покрыть все сценарии §§43–47 запроса, включая calendar boundaries, fixed 30 days, membership/date independence, focus warning, cycle reset, pending actual, correction/reopen, idempotent backfill, concurrent occurrence/completion, pause, rule revision, restore и старые очереди.

Финальный commit: `feat: add LifeOS V2 period planning goals and recurrence`. В него входят только файлы этого блока; план и макет не коммитятся отдельно.
