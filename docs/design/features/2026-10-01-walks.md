## 1. Пользовательский результат

Прогулка становится простым способом выйти из рабочего контекста, побыть на улице,
сохранить возникшие мысли и при желании вернуться с понятным следующим действием.
Сценарий: открыть раздел → начать без обязательной анкеты → гулять → завершить →
при желании сохранить наблюдение → найти прогулку и мысли в истории.

Предлагаемый принцип: сначала надёжный повседневный инструмент, затем осмысление и связи
с LifeOS, затем планирование и аналитика. Количество функций не должно усложнять быстрый старт.

Это развитие крупного раздела с новым пользовательским сценарием в текущей оболочке.
Для главного экрана и активной прогулки нужен отдельный утверждённый visual reference
до реализации их композиции. Этот документ задаёт требования, но не заменяет макет.

## 5. Требования к первому рабочему выпуску

### Быстрый старт

- Из обзора свободная прогулка запускается одним нажатием «Начать прогулку».
- По умолчанию секундомер, намерение `free`, тип `restorative`; это предлагаемые defaults.
- «Настроить» открывает намерение: свободно / восстановиться / подумать; таймер
  10, 20, 30, 45, 60 минут или своё целое значение 1–1440 минут.
- Типы `mindful`, `physical`, `phoneFree` остаются дополнительной настройкой, не второй
  обязательной классификацией рядом с намерением.
- Сфера, вопрос и три оценки состояния необязательны. Нулевое значение оценки допустимо;
  отсутствие оценки не превращается в ноль. Шкалы сохраняют существующий диапазон 0–10.
- В режиме размышления вопрос тоже необязателен: можно выбрать шаблон с готовыми
  подсказками или свободную мысль без заранее сформулированной темы.
- Нельзя подставлять фиктивный вопрос ради старого обязательного `reflectionQuestion`:
  контракт старта нужно явно ослабить для свободной прогулки и восстановления.

### Активная прогулка

- Состояния: идёт / пауза / завершена / прервана. Пауза не входит в активные минуты.
- Таймер показывает целевое и фактическое время; достижение цели не завершает прогулку автоматически.
- Время вычисляется из сохранённых timestamps и пауз, а не количества срабатываний `setInterval`.
- Переход в другой раздел, refresh и закрытие приложения не завершают прогулку.
- Если приложение закрыто без паузы, интервал учитывается до явного завершения.
  После длительного перерыва пользователь видит время и сам решает, завершить или прервать.
- Одна локально активная прогулка, включая паузу. Двойной старт не создаёт дубликат.
- Две автономные прогулки с разных устройств после sync сохраняются обе; интерфейс показывает
  конфликт и предлагает выбрать, какую продолжить, а остальные явно завершить/прервать.
  До выбора новый старт заблокирован. Глобальная уникальность offline не обещается.
  Текущий recovery отвергает второй active: до выпуска этот путь необходимо согласовать
  с remote apply и UI разрешения конфликта, сохранив обе записи без автоматического завершения.
- При переводе часов назад команда не записывает отрицательное время: показывает ошибку
  времени и сохраняет последнее подтверждённое состояние.
- Сохранение мыслей: текст до 500 символов, отметка времени, явный статус сохранения.
  При ошибке текст остаётся в форме, повтор не создаёт вторую запись.
- Голосовой ввод использует общую систему. Отказ в микрофоне оставляет клавиатурный ввод.

### Завершение и минимальная история

- «Завершить» сразу фиксирует факт и длительность. Анкета не является условием завершения.
- После этого можно добавить итог до 1000 символов, оценки после прогулки и
  субъективное «лучше / так же / хуже». Каждая группа необязательна.
- «Готово» без оценок — успешное завершение. Отсутствующие оценки не исключают прогулку
  из количества и времени, но исключают из парных сравнений состояния.
- Итог можно дополнить или исправить позднее с проверкой версии записи.
- Исключение совместимости: у старой записи с reentry нельзя очистить сохранённый impact,
  пока старый контракт требует эту оценку. Другие поля редактируются; интерфейс объясняет
  ограничение. Для новых записей reentry не создаётся и оценки остаются необязательными.
- Повтор завершения после потерянного ответа не меняет конечное время и не создаёт второй факт.
- Прерывание сохраняет историю и мысли, но не считается завершённой прогулкой.
- В первом выпуске уже есть список последних прогулок и читаемые детали;
  расширенные фильтры появляются позже.

## 6. Осмысление и связь с жизнью

### Необязательные подсказки

Пять существующих шаблонов: решение, проблема, цель, стратегия, свободная мысль.
Пользователь выбирает шаблон сам; на экране один вопрос и действия «Дальше» / «Без подсказок».
Ответ не обязателен. Пропуск, выключение подсказок и возврат после refresh безопасны.
Существующий список domain-этапов переиспользуется; тексты вопросов хранятся отдельно от JSX.

### Разбор мыслей

Открыть мысль → исправить текст → оставить обработанной либо создать черновик действия.
Исходная мысль сохраняется и получает ссылку на результат. Повтор операции возвращает
то же действие. UI не запускает две независимые записи без защиты от частичного успеха.
Не создавать отдельную копию мысли во «Входящих» автоматически.

### Связи

- Запуск из «Сегодня», цели или действия сохраняет исходный контекст.
- Завершение прогулки не закрывает цель/действие и не увеличивает прогресс автоматически.
- «Вернуться к действию» открывает текущую карточку, а не старый удалённый экран.
- Если объект удалён, прогулка и мысли остаются доступны; предлагается переход в раздел.
- Старые связи decision/project/routine читаются как исторический контекст без возврата
  этих подсистем в runtime. Новые связи создаются только с актуальными goal/lifeAction.
- Дневник показывает производный факт: число прогулок и минуты за день; текст пользователя
  не перезаписывается. Итог переносится в запись только по явному действию и с preview.
- «Сохранить в память жизни» готовит редактируемый черновик через существующий Memory API.
  Никакого автоматического копирования каждой прогулки в память.

## 7. Полная история, фото и управление записями

История: период, намерение, статус, сфера, поиск по вопросу/итогу; 30 элементов на страницу,
стабильная сортировка по дате/времени/ID. Фильтры отражаются в URL.
Детали показывают активные минуты, интервалы пауз, итог, состояние, мысли и связи.
Список не загружает base64 всех фото; фото загружается только для открытых деталей.

В первом расширении — одно фото на прогулку, существующий лимит 5 МиБ.
Добавление/замена/удаление проходят существующий attachment pipeline. Не создавать новый
blob storage. Ошибка загрузки фото не отменяет завершение прогулки.

Удаление завершённой/прерванной записи — мягкое с восстановлением. Активную сначала
нужно завершить/прервать. Связанные мысли остаются доступны в общем списке с отметкой
«Прогулка удалена»: это сохраняет существующий orphan-safe контракт sync. При восстановлении
возвращается переход к родителю; созданные из мысли действия не удаляются. Физическая очистка данных
и массовое удаление не входят в первые выпуски.

## 8. Планирование и регулярность

Предлагается использовать существующие действия и повторения LifeOS как источник расписания.
Не заводить второй календарь повторений в прогулках. Раздел показывает связанные действия
и даёт запланировать разовую/повторяющуюся прогулку через действующие команды planner.

Нужна типизированная связь действия с прогулочным сценарием, сохраняемая и синхронизируемая.
Совпадение текста «Прогулка» не является связью. При старте создаётся фактическая прогулка;
перенос плана не меняет её дату. Завершение действия после прогулки — отдельный явный выбор.
Старые `Walk.status=planned` видны как исторические планы и могут быть запущены;
новые повторения в этом формате не создаются.

Цель регулярности в первой версии — выбранные пользователем прогулки/минуты в неделю,
без штрафов, рейтингов и принудительного streak. Настройка включается добровольно.
Пропущенная прогулка не становится просроченным «долгом» без существующего решения planner.

## 9. Аналитика с проверяемыми числами

- Периоды: 7, 30, 90 дней и произвольный диапазон включительно.
- Основные метрики: завершённые прогулки, активные минуты, дни с прогулками,
  медианная длительность. Прерванные показаны отдельно.
- Дата группировки — сохранённая локальная дата прогулки. Переход через полночь не
  разбивает одну прогулку на две и не меняет её историю при смене timezone.
- Минуты агрегируются из миллисекунд и округляются только при отображении.
- Для сравнений состояния берутся только записи с обеими тройками оценок.
  Показываются число пар и средние изменения энергии, напряжения, ясности.
- Рост напряжения не окрашивается как улучшение. `impact` — субъективный ответ,
  он не подменяет вычисленные изменения.
- При менее чем 5 парных записях — «Пока мало оценок для сравнения»; это предлагаемый
  порог интерфейса, не статистическая значимость.
- Формулировки описательные: «В 6 из 8 оценённых прогулок напряжение стало ниже».
  Никаких диагнозов, причинных обещаний или автоматических медицинских рекомендаций.
- Из любой метрики можно открыть именно те прогулки, на которых она рассчитана.
- Личные цели и аналитические настройки не меняют прошлые результаты.

## 10. Владение состоянием и совместимость

`Walk` — владелец факта, времени и итога; `WalkCapture` — владелец мысли; planner —
владелец расписания и действий; diary/memory — владельцы своих записей.
UI хранит только черновик формы и состояние отображения. Query-модели производные.

Новый API: `PlannerServices.walks: WalkServices`, собираемый в composition.
Отдельные application-порты для repository, атомарных операций и уведомлений о commit.
Domain не получает browser API; часы и ID передаются через существующие порты.
Сохранение и outbox атомарны; успешное уведомление UI приходит только после commit.

Расширения: необязательный вопрос; независимый редактируемый итог; durable request ID;
ссылка результата обработки мысли; soft-delete и прогулочная связь действия.
Старые значения не переименовываются массово. Новые optional-поля имеют явные defaults.
Старые `recordOutcome/reentry` читаются; новый итог не требует устаревшего возвратного flow.

Перед записью нового формата проверить чтение старым sync-клиентом, snapshot/recovery,
soft-delete и attachment refs. Если старый клиент теряет новые поля, выпуск записи
блокируется до совместимого protocol/version gate; нельзя молча считать проблему решённой.

| Нет прогулок         | Одно объяснение и «Начать прогулку»                                    |
| Нет совпадений       | Показать фильтры и «Сбросить»                                          |
| Ошибка чтения        | Понятное сообщение и retry; существующая сессия не заменяется пустотой |
| Ошибка записи        | Черновик сохранён в форме, нет ложного success                         |
| Версионный конфликт  | Предложение обновить данные, локальный текст можно скопировать         |
| Успех                | Спокойное подтверждение и обновлённая история                          |
| Offline              | Основной сценарий работает, sync-статус следует общей оболочке         |
| Refresh/закрытие     | Восстанавливается подтверждённая прогулка и сохранённые мысли          |
| Отсутствует микрофон | Ручной ввод доступен                                                   |
| Mobile/keyboard      | Нет перекрытых CTA, focus виден, sheet возвращает focus инициатору     |

Первый рабочий выпуск готов, когда пользователь проходит старт → пауза → refresh →
продолжение → мысль → завершение → история без потери данных, и отдельный сценарий
быстрого старта/завершения не требует вопроса или оценок.

Полный раздел готов после расширений истории, осмысления, связей, планирования, аналитики,
совместимости и browser QA. Проверки каждого этапа описаны в
[плане реализации](../../superpowers/plans/2026-10-01-walks-development.md).

## 12. Последующие расширения с отдельным решением

GPS/карты, шаги, Health-интеграции, автоматическое определение прогулки, offline-карты,
гарантированные фоновые уведомления, погода, социальные функции и AI-разбор мыслей
не включены в базовый контракт. Для каждого нужны отдельная ценность, поддерживаемые
платформы, разрешения, стоимость и проверка хранения данных. «Полное развитие» в этом
плане означает законченный раздел LifeOS, а не реализацию всех возможных интеграций.

## 13. Сравнение подходов

| Подход                                                | Выгода                                           | Ограничение                                         |
| ----------------------------------------------------- | ------------------------------------------------ | --------------------------------------------------- |
| Вернуть прежний runtime                               | Часть старых идей уже описана                    | Возвращает удалённые зависимости и второй интерфейс |
| Сделать только таймер                                 | Быстро получить работающий минимум               | Не решает историю, мысли, связи и полный запрос     |
| Новый раздел на сохранённых domain/storage контрактах | Сохраняет данные и вписывается в нынешний LifeOS | Требует application API и проверки совместимости    |

Рекомендован третий подход с промежуточными работающими выпусками. Все предложенные
defaults, этапы и UX-решения подлежат пользовательскому review; подтверждено пока направление
«полное развитие», а не каждый отдельный пункт этого документа.
