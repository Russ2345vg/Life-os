# Надёжное завершение действия

Дата: 30.09.2026. Статус: реализовано в активном worktree по разрешению пользователя.
Проверки и ограничения: [отчёт](../../architecture/2026-09-30-reliable-action-completion-verification.md).

## Цель

Одно нажатие «Выполнить» надёжно сохраняет действие. Ошибка последующего обновления экрана
или передачи на другое устройство не превращает сохранённое выполнение в неуспешное.
Восстановление повторяет нужный этап и не создаёт новое выполнение или повторный вклад в цель.

Первый этап охватывает два существующих входа: «Сегодня» и завершение через
`PlannerLibraryWorkspace` (список, карточка действия, фокус и представления библиотеки).
Сохранение необязательного итога остаётся отдельной командой.

## Исходное состояние до реализации

Планирование выполнено read-only в активном `D:/LifeOS-App`, исходный worktree был чистым.
К началу реализации незакоммиченными были только этот контракт и план. Ниже сохранены
причины изменения; результаты реализации и проверок приведены в отдельном отчёте.

- `CompleteLifeAction.execute` уже использует `JournalUnitOfWork` в production composition.
  Транзакция сохраняет действие, Journal, contributions, balance и существующий sync outbox.
- Повторное последовательное выполнение уже завершённого действия — no-op без новой записи.
  `completionKey` определяет поколение выполнения; «Вернуть в работу» увеличивает generation.
- Конкурентные транзакции защищены version check. Проигравший запрос сейчас получает
  `persistence.transaction_failed`, внутри которого находится `persistence.version_conflict`.
- `PlannerWorkspace.run` помещает команду и `load()` в один `try/catch`.
  `PlannerLibraryReadModel` уже сохраняет последние данные при ошибке и сообщает её в snapshot.
  `whenSettled()` не бросает эту ошибку. `PlanningContext.refresh()` также поглощает ошибку.
- Sync запускается после commit независимо от UI: recorder → coordinator, а также lifecycle.
  Есть persistent outbox, lease, backoff, авторизация и обработка конфликтов.
- `IndexedDbPilotMutationRecorder.notifyCommitted` вызывает callback без изоляции исключения.
  В automatic capture такой callback может создать unhandled rejection после commit.

## Выбранный подход

Сохраняем локальную транзакцию и существующую доставку. Добавляем узкий общий controller
завершения в Presentation для двух UI-входов и явные результаты обновления представлений.
Предметные изменения по-прежнему выполняет application-команда.

Альтернативы: исправить только сообщения в двух обработчиках — меньше изменений, но сохраняет
дублирование recovery; создать общий persistent workflow engine — существенно увеличивает
объём, дублирует outbox и требует миграций. Для этого сценария выбран общий controller без
новой схемы хранения, event bus, зависимостей или общей переработки команд.

Логическая граница:

```text
CompleteLifeAction → атомарный локальный commit
                    ├─ сохранённый результат → обновление представлений
                    └─ существующий outbox → независимая доставка
```

Отправка не ждёт окончания обновления экрана. «Сохранено» означает локальное сохранение;
оно не означает, что другое устройство уже получило запись.

## Контракт выполнения и восстановления

1. UI передаёт `actionId` и `expectedCompletionKey` из показанного действия. Команда проверяет
   ключ после чтения записи. Несовпадение возвращает `action.completion_changed`: требуется
   обновить список и заново принять решение, автоматического выполнения нового поколения нет.
2. Новый параметр команды необязателен для совместимости существующих callers; оба UI-входа
   этого этапа передают его обязательно. Последовательный повтор того же поколения остаётся no-op.
3. При version conflict команда один раз перечитывает запись. Успех допустим только если запись
   уже completed и её `completionKey` равен ключу, прочитанному перед исходной попыткой.
   Другой статус, новое поколение, удаление или ошибка перечитывания не дают ложного успеха.
   Повторной записи при reconciliation нет. Прочие storage errors не маскируются.
4. После подтверждённого сохранения controller хранит временный receipt с `actionId`,
   `completionKey` и возвращённым `LifeAction`. Это результат операции для UI, не второй
   источник предметного состояния. Receipt фиксируется до запуска обновления экрана.
5. Обновления имеют раздельные результаты и учитывают зависимости: Today выполняет workspace,
   затем planning; библиотека — planning, затем library settlement. Ошибка одного этапа не
   отменяет последующие попытки. Последующее чтение библиотеки учитывает записи, созданные
   materialize внутри planning, даже если planning затем завершился ошибкой.
6. «Повторить загрузку» начинает с первого неуспешного обновления и повторяет его зависимые
   последующие этапы, без `CompleteLifeAction`. Успешные предшествующие этапы не повторяются.
   Успех команды остаётся успехом даже после нескольких ошибок чтения. Параллельный retry
   объединяется; бесконечного автоматического retry нет.
7. Существующие loaders могут материализовать повторения и импортировать legacy focus.
   Этот этап не объявляет их чистыми queries и не переписывает их бизнес-логику. Гарантия retry:
   не повторять completion, не менять его generation/date, не дублировать его Journal/contributions.
8. Необязательный prompt появляется из сохранённого receipt один раз на completionKey.
   Ошибка обновления экрана не уничтожает введённый итог. Отмена prompt не отменяет выполнение.
9. После navigation, смены даты/services или unmount поздний результат старого controller
   не публикуется в новом экране и не открывает там prompt. Уже начатый commit не отменяется.
   Если refresh вытеснен новым refresh в той же активной сессии, ожидается актуальный результат:
   завершение старого запроса не означает ready. Ошибка нового запроса остаётся видимой.
10. После перезапуска receipt не восстанавливается отдельным журналом: экран читает базу,
    существующий outbox продолжает доставку. Потеря несохранённого текста итога при закрытии
    приложения не решается этим этапом.
11. Ошибка callback уведомления после commit изолируется в recorder. Она не отменяет сохранение,
    не создаёт unhandled rejection и не удаляет очередь. Следующий разрешённый lifecycle trigger
    может продолжить доставку. Ошибки записи outbox до commit по-прежнему откатывают транзакцию.
12. Sync status остаётся агрегатным статусом существующей системы. Не показываем неподтверждённое
    «это действие синхронизировано». Offline, отсутствие настройки, pause/authorization и conflict
    сохраняют текущие различия; автоматический обход этих ограничений запрещён.

## Поведение существующего интерфейса

Это функция существующих страниц без изменения композиции. До изменения UI сохранён browser
baseline «Сегодня», библиотеки и формы итога на 1440×900 и 390×844, маршрут и computed styles.
Использованы изолированные тестовые данные активного приложения. Данный документ не утверждает новый макет.
`LifeOS_DESIGN_RULES_v1.md` прочитан полностью; исторические glass/gold примеры не заменяют
действующий Premium UI.

- FEATURE → согласованное завершение действия и восстановление обновления экрана.
- USER GOAL → один раз выполнить действие и понимать, что уже сохранено.
- EXISTING LOGIC → CompleteLifeAction, JournalUnitOfWork, completionKey, read models, sync outbox.
- PAGE/COMPONENT ARCHETYPE → существующие «Сегодня» и библиотека планирования.
- SECTION COLOR → текущая Premium тема: graphite, jade для основного действия, gold для приоритета.
- ATMOSPHERIC MOTIF → существующая рабочая поверхность; новый фон не проектируется.
- MAIN VISUAL CENTER → текущий список/действие; статус остаётся вторичным.
- COMPONENTS TO REUSE → planner-notice, planner-error, retry button, PlannerSheet, CompletionResultPrompt.
- MOBILE BEHAVIOR → существующая компоновка; сохранение фокуса, текста и доступности retry.
- APPROVED REFERENCE → новый макет не требуется для стандартных состояний; visual approval не заявляется.
- TEST SCOPE → command/persistence/controller tests, scoped browser flow desktop/mobile, verify.

Состояния: saving блокирует повторную отправку; success подтверждает локальный commit;
refresh pending не удерживает видимость успеха до сетевой доставки; refresh error сохраняет
последние данные и даёт retry; empty следует существующим фильтрам после успешного обновления.

Тексты для изменяемого сценария:

- Локальный успех: «Действие выполнено».
- Сбой после сохранения: «Действие выполнено. Не удалось обновить данные на экране.»
- Восстановление представления: «Повторить загрузку».
- Устаревшее поколение: «Действие изменилось. Обновите список перед выполнением.»

Для ошибки до commit показывается соответствующая предметная/storage ошибка. Кнопка повторной
загрузки не обозначается как повтор сохранения. Новое нажатие «Выполнить» после актуализации
списка является новым осознанным запросом пользователя.

## Критерии приёмки

- Последовательные и конкурентные повторы одного поколения дают один completion Journal fact
  и один вклад на связь с целью; повтор не добавляет новые outbox events завершения.
- Pre-commit failure откатывает action/Journal/contributions/outbox; последующая явная попытка
  сохраняет их один раз.
- Commit + failure одного loader показывает saved + refresh error; retry не вызывает команду
  и не повторяет успешные loaders до первого failure. Зависимые последующие чтения обновляются.
- Planning создаёт поздний commit после материализации: controller ждёт последующее library
  чтение и замечает его failure. Refresh A, вытесненный B в той же сессии, не даёт ready до B.
- Reopen между кликом и выполнением/повтором не позволяет старому ключу завершить новое поколение.
- Callback failure после commit не портит сохранённый результат; очередь доступна следующему trigger.
- Offline и недоступный sync не мешают локальному завершению; запреты передачи соблюдаются.
- Retry после полуночи сохраняет completedOn/effectiveDate; количественный факт не придумывается
  за пользователя; пропуск итога допустим.
- Desktop/mobile, keyboard/focus, сохранность prompt draft, navigation cleanup и browser console
  проверяются на затронутых маршрутах.

## Границы

Нет массового перевода всех команд на новый controller, миграции схемы данных, переработки
conflict resolution, нового синхронизируемого статуса операции или фонового исполнения после
закрытия приложения. Общая реактивность «Сегодня» и очистка всех loaders от side effects —
отдельные задачи. План: [этапы реализации](../../superpowers/plans/2026-09-30-reliable-action-completion.md).
