LIFEOS V2 · MASTER SPEC · ONE-PROMPT NIGHT RUN
Автономная реализациявсех утверждённых экранов
Единое задание для Codex: последовательно реализовать утверждённые макеты «Сферы», «Направления», «Цели», «Действия» и финально «Сегодня», с общей дизайн-системой, мобильной адаптацией, проверками и финальным verify.
Режим Codex: High
Это одна большая автономная задача. Не останавливаться после анализа, плана или одного экрана. Работать последовательно до полного завершения всех этапов или до настоящего внешнего блокера.
Главное правило ночного запуска
Не спрашивать подтверждение между этапами. Для недеструктивных неоднозначностей самостоятельно выбирать самое консервативное решение, максимально близкое к утверждённым макетам и существующей бизнес-логике.
Состав: оболочка → Сферы → Направления → Цели → Действия → Сегодня

1. Контракт автономной работы
Сначала прочитать этот документ целиком. Не начинать редактирование после первых страниц.
Затем изучить текущий проект: маршруты, компоненты, дизайн-токены, типы данных, состояние, API/хранилище и тесты.
Не переписывать работающую бизнес-логику ради визуального совпадения. Сначала переиспользовать существующее.
Не создавать параллельные сущности/вторую систему целей, действий, сфер или направлений.
Не добавлять функции, которых нет в утверждённом объёме, только потому что они красиво смотрятся в референсе.
Не делать миграцию БД ради косметики. Если без миграции невозможно сохранить функцию — не выполнять разрушительное изменение молча.
Не удалять пользовательские данные, существующие рабочие функции, файлы или несвязанные изменения.
Не делать reset/stash/clean чужих незакоммиченных изменений.
После каждого этапа запускать целевые проверки. Полный verify — после всех экранов.
Не прекращать работу из-за мелкой визуальной неоднозначности: выбрать ближайший к референсу и единый для всей системы вариант.
1.1 Когда Codex всё-таки имеет право остановиться
Требуется секрет/ключ/доступ, которого физически нет в окружении.
Требуется разрушительная миграция или действие с риском потери данных.
Сборка/тесты блокируются внешней инфраструктурой и нет безопасного локального обхода.
Два требования напрямую противоречат друг другу и выбор может изменить бизнес-смысл/данные.
Если блокер не мешает другим этапам
Зафиксировать точную причину и продолжить все независимые этапы. Не завершать весь ночной запуск из-за одного локального блокера.
2. Порядок выполнения
Снять базовую техническую точку: понять текущую архитектуру, запустить быстрые проверки/сборку, зафиксировать уже существующие ошибки.
Унифицировать только необходимые общие токены/компоненты оболочки: поверхности, радиусы, границы, акцент, поля, кнопки, меню, мобильную навигацию.
Реализовать «Сферы» и проверить.
Реализовать «Направления» и проверить.
Реализовать «Цели» и проверить.
Реализовать «Действия» и проверить.
Реализовать/довести «Сегодня» после обновления зависимых сущностей и проверить регрессии.
Пройти общую адаптивность, клавиатурные/мобильные состояния, пустые/ошибочные/загрузочные состояния.
Запустить полный verify, исправить новые ошибки, сделать финальный отчёт.
Почему «Сегодня» последним
Он использует цели/действия и общие компоненты. Финальная сборка «Сегодня» после базовых сущностей снижает повторную переделку и даёт цельный результат.

3. Общая дизайн-система LifeOS V2
Общий характер
Тёмный премиальный рабочий инструмент: спокойно, точно, дорого, без геймификационного шума.
Фон
Глубокий чёрный/графит. Поверхности различаются тонально, не сильными тенями.
Основной акцент
Приглушённый зелёный. Активное, выбранное, успех, основной CTA, прогресс.
Дополнительные цвета
Только смысловые и дозированные. Не делать статус «Сейчас» зелёным, «Квартал» синим, «Год» фиолетовым и т.п.
Статусы/горизонты
В основном нейтральные серые. Активный/выбранный может использовать зелёный.
Иконки
Единая взрослая система. Умеренные смысловые цветные пиктограммы допустимы там, где помогают различению; не превращать экран в радугу.
Типографика
Чёткая иерархия: название объекта > следующий шаг/основное действие > связь/метаданные > служебное.
Карточки
Тонкие границы, мягкие поверхности, единые радиусы. Не обводить всё зелёным.
Свечение
Минимум. Не использовать холодный синий/фиолетовый glow.
Отступы
Единая шкала 4/8/12/16/24/32/48 px. Не размещать элементы «на глаз» независимо на каждом экране.
Анимации
Короткие функциональные переходы. Не задерживать действия декоративными эффектами.
3.1 Семантика цвета
Зелёный = активное / выбранное / выполнено / основной CTA / фактический прогресс.
Серый = нейтральный статус, дата, вторичная информация, отсутствие данных.
Красный/тёплый предупреждающий = ошибка/просрочка/действительно требующее внимания; локально, не на всю карточку.
Не вводить разные цвета только для классификации сроков, если текстовой метки достаточно.
3.2 Общая оболочка
Левая навигация на компьютере должна быть единой на всех экранах.
Мобильная нижняя навигация/меню — единый паттерн, без отдельной новой навигации для каждого модуля.
Активный раздел заметен, но не ярче основного контента.
Общие popup/select/menu/input/button-компоненты должны выглядеть как часть одной системы, а не как браузерные элементы по умолчанию.

УТВЕРЖДЁННЫЙ МАКЕТ · СЕГОДНЯ

Утверждённый десктопный эталон экрана «Сегодня».
4. Экран «Сегодня»
Назначение
За 10–30 секунд собрать сегодняшний день, затем весь день работать отсюда. Список действий — главный визуальный объект.
Шапка
Крупный «Сегодня», дата вторична. Компактные вкладки Сегодня/Завтра.
Главное направление
Компактный блок, не огромная зелёная карточка. Показывать связь вида «Дом → Жильё».
Быстрое добавление
Одна строка + голосовой ввод. Не дублировать одинаковое добавление отдельной большой кнопкой и плюсиком.
Список
Чекбокс, название, вторичная связь, приоритет/главное действие при необходимости, меню.
Выполнено / Без даты
Вторичные сворачиваемые группы. Не конкурируют с текущими действиями.
Правая колонка
Прогресс дня, только реальные быстрые действия, спокойный вечерний чекпоинт. Никаких декоративных кнопок-пустышек.
4.1 Мобильный «Сегодня»
Одна колонка: Сегодня → дата → Сегодня/Завтра → главное направление → добавить → действия → Выполнено → Без даты.
Элементы правой колонки переносятся вниз только если они действительно полезны на телефоне.
Клавиатура не закрывает быстрое добавление; зоны касания ~44×44 px.
4.2 Критические правила
Toast после добавления: краткая обратная связь, не постоянная строка интерфейса.
Зелёный не использовать как декоративную рамку обычного контейнера.
Пустой день и «всё выполнено» имеют спокойные собственные состояния.
Не возвращать обязательные таймеры/сессии.
УТВЕРЖДЁННЫЕ МАКЕТЫ · СФЕРЫ · КОМПЬЮТЕР

Главный десктопный эталон «Сфер».
5. Экран «Сферы»
Главный вопрос
«Какие области моей жизни сейчас требуют внимания?» Общая картина → где проблема → детали по сфере.
Заголовок
«Сферы» / «Сферы жизни». Не конкурировать вторым названием «Состояние жизни».
Период
Сегменты Неделя / 30 дней / Квартал / Год; не стандартный браузерный select.
Колесо жизни
Подписи названиями сфер, текущий уровень + желаемый уровень; сетка спокойная.
Требует внимания
Показывать несколько наиболее важных разрывов. Не перечислять пять раз «Нет данных».
Все сферы
Карточки вместо длинной таблицы. Оценка, желаемый уровень, дефицит, направления/цели, понятный следующий переход.
Нет оценки
Отдельное нейтральное состояние «Нет оценки»/«Пока нет оценки», не 0 и не гигантский зелёный текст.
Создание
Контекстная панель: название, описание, желаемый уровень; доп. настройки скрыты.

УТВЕРЖДЁННЫЕ МАКЕТЫ · СФЕРЫ · МОБИЛЬНЫЙ

Мобильные состояния «Сфер»: основной экран, список и создание.
5.1 Мобильные правила
Колесо → «Требует внимания» → список карточек сфер.
Создание новой сферы — нижняя/полноэкранная панель, не пустая отдельная страница.
Кнопка «Новая сфера» не перекрывает последнюю карточку.
Карточки без оценки остаются спокойными серыми; предупреждающий цвет только когда есть реальная причина.
Минимальные зоны касания ~44×44 px.

УТВЕРЖДЁННЫЙ МАКЕТ · НАПРАВЛЕНИЯ

Единый эталон «Направлений»: список, создание, карточка направления и мобильные состояния.
6. Экран «Направления»
Смысл
Список отвечает «какие направления у меня есть и чему уделить внимание», карточка — «что здесь происходит и что делать дальше».
Список
Группировать по сферам. Карточки вместо строк-таблиц.
Карточка в списке
Название, сфера, короткий смысл, количество активных целей, состояние/статус, понятный переход.
Нет данных
Не доминирует. «Состояние не оценено» + небольшое действие.
Создание
Боковая панель на десктопе / мобильная панель. Название, сфера, описание; Сейчас/Хочу — необязательно.
Карточка направления
Сейчас / Хочу → Следующий шаг → Активные цели → Состояние/динамика → Показатели → вторичные разделы.
Следующий шаг
Один из центральных блоков, не прятать внутри цели.
Показатели
До 5 конкретных индикаторов; пустое состояние компактное.
Архив/будущее
Спокойные аккордеоны внизу.
6.1 Ограничение списка
Не пытаться показать в карточке списка всю аналитику направления.
Оценка состояния не должна быть самым крупным зелёным объектом.
Если нет активных целей — показать понятное действие «+ Добавить цель».

УТВЕРЖДЁННЫЙ МАКЕТ · ЦЕЛИ

Финальный утверждённый эталон «Целей»: умеренная цветность без разноцветных статусов.
7. Экран «Цели»
Главный вопрос карточки
«Чего я хочу? К какому направлению относится? Насколько продвинулся? Какой следующий шаг?»
Список
Название → направление → следующий шаг → компактный прогресс. Прогресс вторичнее названия.
Проценты
Компактные 14–16 px в списке. Не делать огромным фокусом карточки.
Полоса прогресса
Тонкая, спокойная, зелёная. Не вводить индивидуальный цвет по горизонту.
Горизонты
Сейчас / 30 дней / Квартал / Год / Без срока — нейтральные статусы; активный фильтр может быть зелёным.
Цветные иконки
Допустимы как единая взрослая система и только как небольшой идентификатор, не как цветовая тема карточки.
В фокусе
Выделенная группа приоритетных целей, но без чрезмерной визуальной драматизации.
Следующий шаг
Заметнее описания результата; доступен прямо из списка.
Создание
Быстро: название, направление, желаемый результат, горизонт, первый шаг. Всё остальное — после создания/в дополнительных настройках.
7.1 Карточка цели
Желаемый результат → прогресс → следующий шаг → действия/этапы → связь → история/заметки.
«Почему важно?» и «Почему сейчас?» не должны конкурировать с основными рабочими блоками; объединить/сделать вторичными.
Поддерживать разные типы прогресса: действия, числовой, этапный, ручной, без измерения — только если это соответствует существующей модели.
7.2 Представления
Список / Фокус / Канбан / Календарь / Древо — сохранять, если уже заложены.
Фокус показывает несколько действительно актуальных целей, а не полный список в другой обёртке.
Древо отражает Сфера → Направление → Цель; не перегружать действиями по умолчанию.
На телефоне переключение представления — отдельная компактная панель.

УТВЕРЖДЁННЫЙ МАКЕТ · ДЕЙСТВИЯ · КОМПЬЮТЕР

Утверждённый десктопный эталон «Действий».
8. Экран «Действия»
Назначение
Глобальное управление всем пулом действий: найти, отфильтровать, перенести, выполнить, создать или изменить.
Шапка
Действия + поиск + «+ Новое действие».
Быстрые фильтры
Все, Сегодня, Ближайшие, Без даты, Без цели, Выполненные.
Представления
Список / Канбан / Календарь. Не размножать представления без пользы.
Группировка
В режиме «Все»: Сегодня → Завтра → На этой неделе → Без даты.
Строка
Чекбокс → название → цель → срок → меню. Вся строка кликабельна.
Лишнее
Убрать отдельную строку «Открыть и изменить».
Просрочка
Локально на сроке/индикаторе; не красить карточку.
Создание
Боковая панель. Обязательно только название; связь с целью и дата необязательны.

УТВЕРЖДЁННЫЙ МАКЕТ · ДЕЙСТВИЯ · МОБИЛЬНЫЙ

Мобильные состояния: список, представление, фильтр, создание, карточка действия, дата.
8.1 Мобильные правила
Одна колонка; горизонтально прокручиваемые быстрые фильтры.
Создание — нижняя/полноэкранная панель: название → цель → когда → дополнительные настройки.
Дата: Сегодня / Завтра / Без даты + календарь только для конкретной даты.
Карточка действия: выполнить, дата, описание, чек-лист, метки, вложения — без горизонтального скролла.
Расширенный фильтр: статус, время, цель, сфера/направление/метки при наличии данных.
8.2 Повторяющиеся действия
Не дублировать одну повторяющуюся серию длинным списком будущих экземпляров в выборе действий.
Использовать существующую бизнес-логику повторений; визуально показывать факт повторения компактно.
Изменения серии/одного экземпляра должны следовать уже существующей модели и не создавать скрытых дубликатов.

9. Общие UX-состояния для всех экранов
Пустое состояние
Объясняет, что происходит, и предлагает одно логичное следующее действие.
Загрузка
Скелетон/стабильный placeholder без сильного прыжка компоновки.
Ошибка
Понятная причина + повторить. Не терять введённый пользователем текст.
Нет данных
Нейтральное состояние, не ноль и не ошибка.
Disabled
Понятно, почему действие недоступно; не полагаться только на opacity.
Hover / focus / pressed
Определены для интерактивных элементов, не оставлены браузерными по умолчанию.
Длинный текст
Перенос без перекрытия меню/метрик и без горизонтального скролла.
Много данных
Сканируемость сохраняется за счёт группировки, плотности и сворачивания вторичных секций.
10. Адаптивность и доступность
□ Проверить desktop минимум: 1024, 1280, 1366, 1440, 1600, 1920 px.
□ Проверить mobile минимум: 360, 375, 390/393, 412/430 px.
□ Нет горизонтального скролла основного контента.
□ Зоны касания на телефоне ~44×44 px или больше.
□ Клавиатура не перекрывает активное поле/основную кнопку без возможности прокрутить.
□ Видимый keyboard focus; Enter/Space/Escape работают ожидаемо.
□ Иконки с неочевидным смыслом имеют доступное имя/tooltip.
□ Ошибки формы объясняются текстом, а не только цветом.
□ Контраст вторичного текста остаётся читаемым на реальных экранах.

11. Сохранение данных и бизнес-логики
Иерархия — источник истины
Сфера → Направление → Цель → Действие. Не разрывать эти связи и не создавать дубль сущности только ради интерфейса.
Сохранять текущие идентификаторы, связи и данные при редизайне.
Если макет показывает информацию, которой нет в модели, не выдумывать фальшивые данные. Либо вычислять из существующих данных, либо показывать корректное пустое состояние.
«Нет оценки» не превращать в 0.
Прогресс считать только по реальной выбранной модели прогресса/существующим данным.
Ни одна видимая кнопка не должна остаться декоративной. Если функции нет и она не входит в утверждённый объём — убрать элемент.
Голосовой ввод переиспользует существующий механизм; не делать второй независимый.
Навигационные связи между обновлёнными экранами должны вести на реальные сущности и сохранять контекст.
Общие изменения компонентов обязательно регрессионно проверить на всех пяти экранах.
12. Что делать при расхождении макета и текущего кода
Сначала сохранить бизнес-смысл и данные.
Затем максимально приблизить композицию и визуальную иерархию к утверждённому макету.
Если техническая деталь макета не реализуема без новой сущности/миграции — использовать ближайший существующий паттерн.
Зафиксировать такое отклонение в финальном отчёте, но не останавливать весь запуск, если функция остаётся корректной.

13. Внутренний чек после каждого этапа
□ Экран открывается без runtime-ошибок.
□ Работают основные переходы, создание/редактирование и сохранение данных данного модуля.
□ Нет декоративных неработающих кнопок.
□ Проверены пустое, обычное и проблемное состояние.
□ Проверены хотя бы один desktop и один mobile viewport.
□ Запущены целевые unit/component/typecheck/lint проверки для изменённых файлов.
□ Ошибки, внесённые текущим этапом, исправлены до перехода дальше.
Не останавливайся на отчёте
После внутренней проверки сразу переходи к следующему этапу. Финальный ответ пользователю — только после всей последовательности.
14. Полная финальная проверка
□ Пройти сквозной сценарий: Сфера → Направление → Цель → Действие → Сегодня.
□ Создать и отредактировать объект каждого уровня.
□ Проверить, что связи корректно отражаются на соседних экранах.
□ Проверить мобильные формы: клавиатура, scroll-into-view, закрытие панелей, safe-area.
□ Проверить представления/фильтры/поиск там, где они предусмотрены.
□ Проверить повторяющееся действие и отсутствие визуального списка всех будущих повторов.
□ Проверить отсутствие горизонтального скролла и наложений.
□ Проверить общую цветовую дисциплину и отсутствие случайных разноцветных статусов.
□ Запустить существующий полный verify проекта: typecheck + lint + tests + build + format/check + git diff --check (или эквивалент текущих scripts).
□ Исправить все новые ошибки, возникшие из-за этой реализации.
14.1 Если полный verify содержит старую/внешнюю ошибку
Не маскировать её и не менять несвязанный код без необходимости.
Указать точную команду, сообщение и почему ошибка выглядит предсуществующей/внешней.
Отдельно подтвердить, какие целевые проверки изменённых модулей прошли.

15. Definition of Done — ночной запуск завершён только если
□ Все пять утверждённых модулей реализованы или для конкретного модуля зафиксирован настоящий внешний блокер.
□ Общая оболочка и визуальный язык выглядят единообразно между экранами.
□ Десктоп и мобильный вариант каждого затронутого модуля работоспособны.
□ Существующие данные и связи сохранены.
□ Нет новых дублирующих бизнес-сущностей и параллельных потоков.
□ Нет очевидных сломанных кнопок, select/menu браузерного вида и незаполненных декоративных элементов.
□ Ключевые состояния и адаптив проверены.
□ Полный verify выполнен либо точно задокументирован внешний блокер.
□ Составлен финальный отчёт с изменёнными модулями, тестами, отклонениями от макетов и остаточными блокерами.
16. Формат финального отчёта Codex
1. Выполнено
По экрану: Сферы / Направления / Цели / Действия / Сегодня.
2. Общие компоненты
Какие токены/компоненты оболочки были унифицированы.
3. Проверки
Какие команды и тесты прошли.
4. Визуальная проверка
Какие desktop/mobile размеры проверены.
5. Отклонения
Где пришлось отойти от макета и почему.
6. Блокеры
Только реальные внешние/разрушительные блокеры. Если нет — написать «нет».
7. Осталось
Только действительно незавершённое; не добавлять новые идеи/расширение объёма.
Финальное стоп-правило
После выполнения MASTER не начинать новые разделы, редизайн календаря/аналитики/заметок и не делать «ещё 100 улучшений». Остановиться на проверенном утверждённом объёме.
17. Один промпт для запуска в Codex
Работай автономно и последовательно до полного завершения задачи.Сначала полностью прочитай приложенный документ «LifeOS_V2_MASTER_автономная_реализация_для_Codex.docx». Это единый источник требований и утверждённых макетов. Не начинай редактирование, пока не прочитаешь документ целиком.После этого:1) изучи текущую архитектуру проекта, существующую бизнес-логику, данные, общие компоненты и тесты;2) реализуй MASTER по этапам и зависимостям, указанным в документе: общая основа → Сферы → Направления → Цели → Действия → Сегодня;3) не останавливайся после анализа, плана, одного экрана или промежуточного отчёта — сразу переходи к следующему этапу;4) не спрашивай подтверждение для обычных недеструктивных решений: выбирай самое консервативное решение, максимально близкое к утверждённым макетам и текущей модели данных;5) не удаляй пользовательские данные, не делай разрушительные миграции, reset/stash/clean чужих изменений;6) если один этап блокируется внешней инфраструктурой/доступом, зафиксируй точный блокер и продолжи независимые этапы;7) после каждого этапа запускай целевые проверки, после всех этапов — полный verify проекта;8) исправляй все новые ошибки, вызванные этой работой;9) в конце дай один итоговый отчёт по формату из MASTER: что сделано, что проверено, отклонения, блокеры.Цель: за один автономный проход получить максимально близкую к утверждённым макетам, цельную, рабочую и адаптивную LifeOS V2 без расширения объёма задачи.
