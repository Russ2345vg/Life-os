# AGENTS.md — LifeOS

## 1. Базовые правила проекта

1. Работать только внутри текущего проекта.
2. Не переносить старый код Obsidian.
3. Не добавлять функции вне текущего задания.
4. Не использовать `any`.
5. Не изменять предметное состояние напрямую из React-компонентов.
6. Не обращаться к инфраструктуре из предметного слоя.
7. Любое изменение предметного состояния выполнять через существующую или новую application-команду.
8. Новая функция создаётся вместе с проверками.
9. Не начинать следующий этап самостоятельно.
10. Не устанавливать новые зависимости без необходимости и объяснения.
11. Не создавать лишние отчёты в корне.
12. Не включать документацию в установочный архив приложения.

## 2. Приоритет инструкций

При конфликте использовать порядок:

1. Текущее задание пользователя.
2. Этот `AGENTS.md`.
3. Утверждённые визуальные референсы LifeOS.
4. Существующие доменные контракты и тесты.
5. Локальные соглашения конкретного модуля.

## 3. Архитектурный контракт

Рабочий поток:

```text
UI
→ Presentation / Read Model
→ Application Command / Query
→ Domain
→ Repository / Persistence
```

Запрещено:

- дублировать бизнес-правила в React;
- менять доменный статус напрямую из UI;
- обращаться к repository из presentation;
- создавать параллельную сущность, если существующая уже решает задачу;
- обходить state machine и application-команды;
- хардкодить демонстрационные данные из макетов.

Если UI не хватает данных, сначала расширить read model или presentation mapping.

## 4. Один патч — одна цель

Перед изменением определить:

- подтверждённую проблему или требование;
- первопричину;
- минимальный набор файлов;
- что не должно измениться;
- критерий приёмки;
- необходимые regression-тесты.

Не объединять в один патч независимые изменения интерфейса, домена, persistence и аналитики.

## 5. Сохранность рабочего дерева

Рабочее дерево может содержать незакоммиченные изменения пользователя.

Нельзя без прямого запроса:

- выполнять `git reset --hard`;
- удалять или откатывать чужие изменения;
- делать commit, push, merge, rebase;
- массово переписывать файлы ради удобства;
- удалять untracked-файлы.

Перед крупным патчем проверить текущий diff.

## 6. Visual source of truth

Если к задаче приложены утверждённые изображения, они являются источником истины по:

- композиции;
- порядку блоков;
- визуальной иерархии;
- относительным размерам;
- плотности;
- расположению CTA;
- цветовой семантике.

Недостаточно сделать:

```text
старый layout + похожие цвета
```

Если старая presentation-композиция мешает соответствию референсу, разрешено заменить layout, сохранив domain/application contracts.

Не копировать тестовые тексты и числа из референсов в реальные данные.

## 7. Визуальный язык LifeOS

- глубокий нейтральный графит;
- тёплое золото — выбранное, приоритетное, основная CTA;
- зелёный — только подтверждённое, завершённое, готовое;
- красный — только ошибка или destructive-действие;
- минимальное локальное свечение;
- матовые поверхности;
- тонкие границы;
- высокая информационная плотность без перегруза;
- единые радиусы, отступы и иконки;
- не использовать фиолетовый как постоянный акцент.

Разделять смысл в первую очередь отступами, типографикой и уровнями поверхности, а не множеством линий и рамок.

## 8. Evening Command Center

Маршрут:

```text
Сегодня
→ Осмысление
→ Завтра
→ Подготовка
→ Завершение
→ Восстановление
```

Обязательные правила:

- `EveningCycle` — единственный источник доменного состояния;
- выбранная вкладка просмотра — отдельное presentation-состояние;
- переход в прошлый этап не откатывает `EveningCycle`;
- `Today history` остаётся read-only без специальной корректирующей команды;
- `Reflection history` не запускает Reflection Engine повторно;
- `TomorrowPlan` и `PreparationPlan` изменяются только существующими командами;
- после `COMPLETED` повторно не показывать `Завершить день`;
- `Recovery` — экран по умолчанию для завершённого вечера.

## 9. Ошибки и состояния команд

Никаких silent failures.

Любое действие должно завершиться одним из:

1. успешный результат;
2. понятная бизнес-блокировка;
3. техническая ошибка с возможностью повторить.

Для изменяющих команд:

- показывать loading;
- блокировать повторный клик;
- обеспечивать идемпотентность;
- не терять состояние после refresh;
- не показывать пользователю stack trace или внутренние enum.

## 10. Persistence и даты

Проверять:

- rollback;
- частично сохранённые состояния;
- дубликаты;
- восстановление после перезапуска;
- согласованность `dayId` и `dateKey`;
- переход через полночь.

Уже начатый `EveningCycle` сохраняет исходный `dayId`.

Явно выбранная дата в route/query важнее текущей календарной даты для соответствующего просмотра.

## 11. Производительность

Избегать:

- N+1 чтений repository;
- повторных вычислений аналитики на каждый render;
- дублирующих listeners/subscriptions;
- stale timers/promises;
- неограниченного хранения history в React state;
- повторного создания presentation models без причины.

Не проводить оптимизацию без подтверждённой проблемы.

## 12. Responsive и длинные данные

Минимальные размеры проверки:

```text
1600×900
1440
1280
1024
390×844
360×800
```

На mobile обязательно:

- одна колонка там, где это требуется;
- отсутствие horizontal scroll;
- достаточные touch targets;
- CTA не перекрывает контент;
- клавиатура не закрывает активное поле;
- учтён `safe-area-inset-bottom`;
- focused input можно доскроллить.

Проверять длинные реальные данные:

- заголовок 120+ символов;
- длинный вопрос и ответ;
- длинный insight/recommendation;
- длинный `firstAction`;
- несколько supporting items.

Не полагаться только на тестовые значения `11` и `111`.

## 13. Accessibility

Не ломать:

- keyboard navigation;
- `focus-visible`;
- `aria-label` у icon-only controls;
- контраст;
- disabled-state;
- `prefers-reduced-motion`.

Не удалять outline без эквивалентного focus-state.

## 14. Тестовая стратегия

Для bugfix:

1. воспроизвести дефект;
2. добавить regression-тест;
3. исправить;
4. подтвердить прохождение.

Для новой функции:

1. определить контракт;
2. добавить или обновить тест;
3. реализовать;
4. проверить соседние сценарии.

Не адаптировать тесты под заведомо неправильное поведение.

## 15. Browser QA

Если встроенный браузер доступен:

- открыть реальный route;
- проверить desktop и mobile;
- пройти основной пользовательский сценарий;
- сравнить с визуальным референсом.

Если браузер недоступен из-за trusted-path:

- не блокировать работу;
- использовать render/CSS-контракты;
- честно указать ограничение;
- не объявлять pixel-perfect соответствие.

Формулировка в отчёте:

```text
Требуется ручная визуальная проверка.
```

## 16. Обязательный quality gate

Перед завершением выполнить:

```bash
npm run typecheck
npm run lint
npm run test
npm run build
npm run format:check
git diff --check
```

Если хотя бы одна команда не проходит, задача не считается завершённой.

## 17. Финальный отчёт

После патча сообщить кратко:

### Что исправлено

- ...

### Первопричина

- ...

### Изменённые файлы

- ...

### Проверки

- typecheck
- lint
- test
- build
- format:check
- git diff --check

### Осталось

- только реальные ограничения и необходимая ручная QA.

Не повторять полностью исходное задание.

## 18. Стоп-правило

Если задача ограничена конкретным этапом, не начинать следующий самостоятельно.

Сначала:

1. завершить текущий;
2. пройти quality gate;
3. показать результат;
4. остановиться.

## 19. Главный принцип LifeOS

Каждое изменение должно делать систему:

- понятнее;
- стабильнее;
- последовательнее;
- проще в использовании;
- визуально цельнее;

без необоснованного роста архитектурной сложности.

> Сохраняй сильную доменную архитектуру и упрощай пользовательский опыт.
