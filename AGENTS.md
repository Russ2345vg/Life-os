# AGENTS.md — LifeOS

Эти правила обязательны для всех задач в репозитории LifeOS.

## Работа с Astra и приоритет инструкций

- Цель и уже выданные разрешения пользователя сохраняются на протяжении задачи. Просьбы
  «сделай», «исправь», «помоги внедрить» означают выполнение до результата с необходимой проверкой.
- В рамках системных правил и разрешений среды явное указание пользователя имеет приоритет над
  проектными соглашениями и рекомендациями навыков. Этот файл задаёт политику LifeOS;
  `docs/codex/TEST_MATRIX.md` — выбор команд, `docs/codex/CODEX_WORKFLOW.md` — практические сценарии.
- Самостоятельно находи недостающий контекст в текущем проекте и принимай обратимые технические
  решения в согласованном scope. Сначала выполни доступную независимую работу. Уточняй только
  выбор, который существенно меняет результат, полномочия, архитектуру или пользовательские данные.
- Уже согласованные дизайн, план и разрешения не запрашивай повторно. Продолжай разрешённые
  этапы до результата; остановись на явно заданной пользователем границе или реальном блокере.
- Новое сообщение во время работы дополняет текущую задачу, пока пользователь явно не отменил
  или не заменил её. На вопрос о статусе ответь кратко и продолжи выполнение.
- Перед действием, которому действительно нужно новое разрешение, подготовь конкретный результат
  для проверки: diff, макет, план миграции или публикации. Автономность не разрешает push,
  публикацию, внешние сообщения, потерю данных или обход sandbox без соответствующих полномочий.
- Навык выбирай по его пользе для задачи, читай перед применением; не загружай цепочку навыков
  только из-за совпадения слов. Общие workflow-навыки применяй соразмерно задаче по правилам ниже.
  Для ясной небольшой правки достаточно краткого плана; отдельная сессия согласования не нужна.
- Если навык действительно вынуждает остановиться, укажи ссылку на прочитанный `SKILL.md`, точную
  цитату и её применимость. Отличай обязательное требование от своей интерпретации. Само наличие
  рекомендации «спросить пользователя» не отменяет уже выданное разрешение.

## Общение

Пиши по-русски, сначала сообщай результат или главное наблюдение. Используй короткие связные
абзацы; списки и таблицы нужны для последовательности или сравнения. Обновления во время работы
содержат новые факты, решения и следующий шаг. Финал содержит результат, выполненные проверки
и реальные ограничения, без повторения всей истории инструментов.

## Область работы

- Работай только внутри активного LifeOS worktree; перед изменениями проверь корень Git и `git status --short`.
- Не открывай и не используй старые копии LifeOS или Obsidian-версию проекта.
- Не меняй стек и не добавляй зависимости без подтверждённой необходимости и объяснения.
- Не расширяй задачу и не меняй пользовательские данные без прямого запроса.

## Перед изменением

Сначала:

1. найди существующую реализацию;
2. определи авторитетный источник состояния;
3. найди связанные тесты и контракты;
4. перечисли затрагиваемые модули;
5. проверь, не существует ли уже нужная функция.

## Архитектура

- Поток зависимостей: UI → Presentation → Application → Domain; Infrastructure реализует application-порты; App связывает слои.
- Не используй `any`.
- Не изменяй предметное состояние из React-компонентов: изменения проходят через application-команды.
- Domain не зависит от React, browser API, Application, Infrastructure или Presentation.
- Presentation не обращается к конкретным Infrastructure-адаптерам.
- Не дублируй бизнес-правила и не создавай параллельный источник предметного состояния.

## Процесс работы

- Новая функция: прояснение цели (brainstorming при неопределённости) → дизайн-контракт → план
  → реализация с проверками поведения → проверка результата. Используй уже согласованный дизайн.
- Исправление ошибки: воспроизведение → первопричина → регрессионный тест → минимальное исправление → соседние проверки.
- Не исправляй симптом без подтверждённой первопричины.
- Один патч решает одну цель; не смешивай независимые изменения.
- Практические сценарии и роли описаны в `docs/codex/CODEX_WORKFLOW.md`.
- Документация и настройки рабочего процесса без изменения продукта не являются новой UI-функцией:
  для них достаточно определить scope, внести правку и проверить её согласно матрице.

## New Feature Design Gate

Этот gate обязателен до реализации любой новой пользовательской функции, раздела, страницы,
пользовательского сценария или UI-компонента LifeOS.

1. Сначала классифицируй изменение:
   - новый раздел;
   - новая страница;
   - новый пользовательский сценарий;
   - новая функция существующей страницы;
   - новый UI-компонент;
   - изменение только бизнес-логики без нового UI.
2. Если изменение затрагивает UI, обязательно полностью прочитай
   `LifeOS_DESIGN_RULES_v1.md` до проектирования и реализации.
3. До реализации определи и зафиксируй:
   - раздел LifeOS;
   - section accent (общий тёплый акцент темы, без отдельной декоративной палитры раздела);
   - атмосферный мотив;
   - главный визуальный центр;
   - page archetype;
   - необходимые существующие UI-компоненты;
   - responsive/mobile-поведение;
   - состояния loading / empty / error / success.
4. До создания нового компонента проверь существующие shared components и design tokens. Не
   создавай дубликат существующего компонента или параллельный визуальный паттерн.
5. Для крупного или уникального интерфейса определи необходимость approved visual reference.
   Approved-макет обязателен для:
   - главной страницы нового крупного раздела;
   - уникального ключевого пользовательского сценария;
   - интерфейса, композиция которого не покрывается существующим архетипом;
   - экрана, который пользователь явно попросил сначала утвердить визуально.

   Approved-макет не обязателен для небольших внутренних форм, обычных таблиц, настроек, простых
   модалок, стандартных списков и экранов, полностью собираемых из уже утверждённых компонентов.

6. Для значимой новой функции создай design specification в `docs/design/features/` или page
   specification в `docs/design/pages/`. Approved references храни или документируй в
   `docs/design/references/`.
7. До начала реализации покажи пользователю краткий дизайн-контракт:

   ```text
   FEATURE
   → USER GOAL
   → EXISTING LOGIC
   → PAGE/COMPONENT ARCHETYPE
   → SECTION COLOR
   → MAIN VISUAL CENTER
   → COMPONENTS TO REUSE
   → MOBILE BEHAVIOR
   → APPROVED REFERENCE: YES/NO
   → TEST SCOPE
   ```

8. Начинай реализацию только после того, как дизайн-контракт определён. Если для задачи требуется
   предварительное визуальное утверждение, дождись approved reference до реализации.
   Для стандартного интерфейса на существующих компонентах, когда цель и критерии уже заданы,
   покажи контракт и продолжай без отдельного подтверждения. Для обязательного visual approval
   сначала подготовь макет и вопрос по нему; утверждённый ранее reference используй повторно.
9. Не меняй существующую бизнес-логику ради визуального оформления, если задача явно этого не
   требует. Сохраняй авторитетный источник состояния и существующие application-контракты.
10. После реализации выполни targeted/scoped tests, а для значимых UI-задач также visual review,
    чек-лист Правила №38 из `LifeOS_DESIGN_RULES_v1.md` и desktop/mobile-проверку.
11. Full regression всего LifeOS не является стандартной проверкой отдельной новой функции.
    Запускай его только согласно общей testing strategy и `docs/codex/TEST_MATRIX.md`.
12. Не помечай новый экран или компонент как `APPROVED` или `LOCKED`, пока пользователь явно не
    утвердил визуальный результат, если для задачи предусмотрен visual review.

## Интерфейс

- Главный визуальный эталон приложения: [«Новое направление»](docs/design/references/2026-09-09-shared-glass/new-direction.png).
  Он охватывает общую оболочку, меню, шапку и рабочие поверхности. Постоянное дымчатое стекло
  разрешено по Design Rules v1.2. Старые task-local запреты менять shell не распространяются
  на согласованный этап общего редизайна. Состав навигации, маршруты и бизнес-логика сохраняются.

- Для визуальных задач сначала изучи Figma или утверждённый референс и текущий компонент.
- Проверяй реальное приложение, а не только JSX/CSS: desktop, необходимые mobile-размеры, состояния, keyboard/focus и browser console.
- Рабочий цикл: Figma/reference → implementation → browser check → comparison → refinement.
- Сохраняй визуальный язык LifeOS: графитовая база, золото для приоритета, зелёный для подтверждённого/успешно завершённого, красный для ошибки/destructive; без постоянного фиолетового акцента.

## Git и параллельная работа

- Сохраняй чужие и незакоммиченные изменения; не используй destructive Git и не выполняй push без прямого разрешения.
- Главный агент — единственный исполнитель изменений. Субагенты преимущественно исследуют и проверяют.
- Делегируй конкретное независимое исследование или review, когда оно ускоряет работу или снижает
  существенный риск, а у главного агента есть полезная параллельная работа. Небольшую линейную
  задачу выполняй самостоятельно. Роли и выбор модели описаны в `docs/codex/CODEX_WORKFLOW.md`.
- Передавай субагенту ограниченный вопрос, нужные файлы и запрет записи. Учитывай его результат
  без повторного полного исследования; уточняй спорные факты. Не запускай конкурентные gate,
  browser-серверы или диагностику одного ресурса. Соблюдай более строгие ограничения текущей среды.
- Не допускай одновременного изменения одних файлов несколькими агентами.
- Перед завершением проверь `git diff --check`, изучи `git diff` и выполни `git status --short`.

## Testing Stage Gate

Объём проверки определяется изменениями этой задачи и её риском, а не всем dirty worktree.
Предсуществующие изменения фиксируй отдельно. Их ошибки нельзя скрывать или исправлять вне scope.

### Документация и настройки агента

- Для Markdown, навыков и `.codex` без изменения исполняемого продукта проверяй diff, ссылки,
  формат затронутых файлов, синтаксис конфигурации и соответствие команд реальному `package.json`.
- При изменении правил принятия решений проверь несколько реалистичных сценариев; независимый
  read-only review полезен для межфайловых конфликтов. Тесты, повторяющие текст правил, не нужны.
- `npm run verify` и полный E2E для такого патча не требуются. Изменения build/test scripts,
  runtime config, зависимостей и CI относятся к исполняемой инфраструктуре и проверяются по риску.

### R1 — аудит

- Выполняй targeted read-only checks при необходимости.
- Полный E2E не запускай.
- Если файлы не менялись, `npm run verify` не обязателен.

### R2–R8 — обычные этапы реализации

После изменения:

```text
targeted tests
→ npm run verify
→ handoff или следующий уже разрешённый этап
```

Полный E2E не запускай автоматически.

### R9 — migration/backward compatibility

После targeted migration tests:

```text
npm run verify
→ npm run test:e2e
```

Полный E2E обязателен, потому что этап затрагивает persistence и совместимость.

### R10 — Visual Fidelity + Mobile

Обязательны:

```text
targeted visual/render tests
→ npm run verify
→ npm run test:e2e
```

Полный E2E обязателен из-за browser/mobile flows.

### R11 — Analytics

По умолчанию:

```text
targeted analytics tests
→ npm run verify
```

Полный E2E запускай только при реальном изменении пользовательского сквозного flow.

### R12 — Final Regression / Release

Обязательно:

```text
npm run verify
→ npm run test:e2e
```

Для R9, R10 и R12 можно использовать эквивалентный полный gate `npm run verify:full`.

### Полный E2E вне R9/R10/R12

Запускай полный E2E раньше только если текущий патч реально затрагивает:

- маршрутизацию;
- navigation state;
- IndexedDB/persistence;
- migration;
- browser interaction;
- desktop/mobile responsive flow;
- сквозной Evening journey;
- critical application startup/recovery.

Перед запуском кратко объясни, почему полный E2E нужен именно этому этапу.

Не запускай полный E2E «на всякий случай» после каждого небольшого UI/domain/application патча.
Не запускай повторно уже зелёный полный suite без изменения кода, которое могло повлиять на него.

### Hang handling

Если E2E действительно завис:

1. Не перезапускай весь suite автоматически несколько раз.
2. Определи последний запущенный scenario/project.
3. Запусти конкретный зависший тест отдельно.
4. Найди root cause.
5. Только после исправления повтори полный gate.

Если progress/heartbeat продолжает двигаться, это не считается зависанием.

## Проверка

- Канонический порядок для кода: `npm run test:target -- <File.test.ts|tsx>` → при изменении
  общего контракта `npm run test:fast` → после стабилизации один `npm run verify` перед handoff.
  `verify` уже включает typecheck, lint, unit/integration, infra, alpha, build, формат и Git hygiene;
  отдельно дублировать эти этапы без диагностической причины не нужно. E2E запускай через
  `npm run test:e2e` или `npm run verify:full` только по правилам `Testing Stage Gate`.
- Новый тест проверяет наблюдаемое поведение или инвариант. Для обратимой правки без изменения
  поведения используй существующие проверки; не добавляй тест, который лишь повторяет реализацию.
- Свежий успешный прогон остаётся доказательством, пока последующие изменения не затрагивают
  проверенный контракт. Расширяй или повторяй проверки при новом риске, изменении кода или failure;
  не перезапускай зелёный gate ради нового сообщения, review или финального отчёта.
- Не запускай голые `vitest`, `npx vitest` или `npm run dev` как проверку: это watch/долгоживущие
  режимы. Не передавай каноническому E2E `--ui`, `--debug`, `--headed` или `--config`.
- Используй только bounded npm-команды из `docs/codex/TEST_MATRIX.md`; их process-level timeout
  является ошибкой с кодом `124`, а не поводом считать тест успешным или бесконечно повторять его.
- При подозрении на зависание не жди молча: зафиксируй текущий этап, команду, elapsed time и
  последний вывод. После deadline проверь освобождение owned-портов/процессов и локализуй проблему
  минимальной targeted-командой. Никогда не завершай чужой процесс только из-за занятого порта.
- Новая функция поставляется с проверками своего уровня; bugfix — с регрессионным тестом.
- Не утверждай, что задача выполнена или проверка прошла, без свежего фактического результата команды или browser QA.
- В финальном отчёте перечисляй выполненные проверки, реальные ограничения и ручную QA, которая ещё требуется.
