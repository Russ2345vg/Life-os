# AGENTS.md — LifeOS

Обязательная политика проекта. Команды и выбор проверок — в
[TEST_MATRIX.md](docs/codex/TEST_MATRIX.md), практические сценарии — в
[CODEX_WORKFLOW.md](docs/codex/CODEX_WORKFLOW.md). Читай дополнительные документы по задаче,
не загружай всю документацию перед каждой правкой.

## Цель, полномочия и общение

- В рамках системных правил и разрешений среды явное указание пользователя имеет приоритет
  над проектными соглашениями и навыками. Цель, согласованный дизайн и разрешения сохраняются;
  «сделай» означает реализацию до результата с необходимой проверкой.
- Самостоятельно находи контекст и принимай обратимые решения в согласованном scope.
  Уточняй только существенный выбор результата, архитектуры, полномочий или пользовательских
  данных, который нельзя разрешить из доступного контекста. Продолжай независимую работу.
- Новое сообщение дополняет задачу, пока пользователь явно не отменил или не заменил её.
  На вопрос о статусе ответь кратко и продолжи. Останавливайся на явной границе или реальном блокере.
- До запроса нового разрешения подготовь конкретный diff, макет или план для проверки.
  Автономность не разрешает push, публикацию, внешние сообщения, потерю данных или обход sandbox
  без соответствующих полномочий. Уже выданное разрешение не запрашивай повторно.
- Навыки выбирай по пользе и читай перед применением; не запускай цепочку по совпадению слов.
  Для ясной небольшой правки достаточно краткого плана. Если навык вынуждает остановиться,
  укажи ссылку на прочитанный `SKILL.md`, точную цитату и её применимость.
- Пиши по-русски короткими связными абзацами, начиная с результата или главного наблюдения.
  Обновления содержат новые факты и следующий шаг; финал — результат, проверки и реальные ограничения.

## Область работы и архитектура

- Перед изменениями проверь корень Git и `git status --short`. Работай только в активном LifeOS
  worktree; старые копии LifeOS и Obsidian-версию не открывай и не используй.
- Сохраняй чужие и незакоммиченные изменения. Не используй destructive Git. Один патч решает
  одну цель; не расширяй scope и не меняй пользовательские данные без прямого запроса.
- Не меняй стек и не добавляй зависимости без подтверждённой необходимости и объяснения.
- Перед изменением продукта найди существующую реализацию, авторитетный источник состояния,
  контракты и ближайшие тесты; назови затрагиваемые модули и проверь, нет ли уже нужной функции.
- Зависимости: UI → Presentation → Application → Domain. Infrastructure реализует
  application-порты; App связывает слои. Не используй `any`.
- Предметные изменения из UI проходят через application-команды. Presentation не обращается
  к конкретным Infrastructure-адаптерам. Domain не зависит от React, browser API или других слоёв.
- Не дублируй бизнес-правила и не создавай параллельный источник предметного состояния.

## Процесс работы

- Новая функция: цель → дизайн-контракт → план → реализация с проверками поведения → проверка
  результата. Brainstorming нужен при существенной неопределённости; используй принятые решения.
- Bugfix: воспроизведение → подтверждённая первопричина → падающий регрессионный тест → минимальное
  исправление → соседние проверки. Не маскируй симптом и не ослабляй тест ради зелёного результата.
- Для документации и настроек агента достаточно определить scope, изменить авторитетные файлы
  и проверить их по матрице; это не новая пользовательская функция.
- Главный агент — единственный исполнитель изменений. Делегируй ограниченное read-only
  исследование или review, когда это ускоряет работу или снижает существенный риск и есть
  полезная параллельная работа. Небольшую линейную задачу выполняй самостоятельно.
- Передай субагенту вопрос, нужные файлы и запрет записи; используй его выводы без повторного
  полного исследования. Не запускай конкурентные gate, browser-серверы или диагностику одного
  ресурса. Соблюдай более строгие ограничения среды. Роли описаны в `CODEX_WORKFLOW.md`.

## New Feature Design Gate

До реализации новой функции классифицируй изменение: раздел, страница, сценарий, функция
существующей страницы, UI-компонент или только бизнес-логика без UI.

Для изменения только бизнес-логики зафиксируй цель, существующие контракты, владельца состояния
и проверки без визуальных полей. Для любой значимой новой функции нужна specification в
`docs/design/features/` или `docs/design/pages/`.

Для нового UI:

1. Полностью прочитай [LifeOS_DESIGN_RULES_v1.md](LifeOS_DESIGN_RULES_v1.md) до проектирования
   и реализации. Проверь существующие shared components и эффективные design tokens.
2. Определи раздел, общий акцент темы без отдельной декоративной палитры раздела, атмосферный
   мотив, главный визуальный центр, page archetype, переиспользуемые компоненты, mobile-поведение
   и состояния loading / empty / error / success. Не создавай дубликаты компонентов или паттернов.
3. Покажи краткий контракт до кода:

   ```text
   FEATURE → USER GOAL → EXISTING LOGIC → PAGE/COMPONENT ARCHETYPE → SECTION COLOR
   → MAIN VISUAL CENTER → COMPONENTS TO REUSE → MOBILE BEHAVIOR
   → APPROVED REFERENCE: YES/NO → TEST SCOPE
   ```

4. Для главной страницы нового крупного раздела, уникального ключевого сценария, композиции
   вне существующего архетипа или явного запроса предварительного утверждения подготовь макет
   и дождись visual approval. Используй уже утверждённый для задачи reference повторно.
   Стандартные формы, таблицы, настройки, модалки и списки из утверждённых компонентов при
   ясных критериях реализуй после определённого контракта без отдельного подтверждения.
5. Approved references храни или документируй в `docs/design/references/`, ссылайся на них из specification.
6. Сохраняй business/application-контракты при оформлении, если их изменение не входит в задачу.
   Для значимого UI выполни visual review, desktop/mobile QA и чек-лист Правила №38 из
   `LifeOS_DESIGN_RULES_v1.md`. Не ставь `APPROVED`/`LOCKED` без явного пользовательского approval,
   если для задачи предусмотрен visual review. Объём тестов выбирай по Testing Stage Gate.

## Интерфейс

- До любой визуальной задачи, включая макет, открой текущую страницу активного worktree:
  зафиксируй route и desktop/mobile-снимки, изучи компоненты, подключённый CSS, порядок каскада
  и вычисленные стили. Цикл: baseline → макет/правка → browser check → comparison → refinement.
- Приоритет: явное указание/approved reference текущей задачи → актуальный UI и shared components
  → общие дизайн-правила → исторические референсы. Новизна файла не означает approval;
  известный дефект текущего UI не становится эталоном и исправляется только в scope.
- Утверждённое 25.09.2026 направление — [«Единая рабочая поверхность»](docs/design/references/2026-09-25-premium/approved-direction.png),
  контракт — [Premium all screens](docs/design/features/2026-09-24-premium-all-screens.md).
  Графитовая база, jade для выбора/основного действия, золото только для приоритета,
  зелёный для успеха, красный для ошибки/destructive; без постоянного фиолетового акцента.
- Каскад: tokens.css → planner-v2.css → planner-master.css → planner-premium.css.
  Переиспользуй текущую оболочку, controls и эффективные токены с локальными overrides даже
  для макета. Референс от 2026-09-09 исторический: не возвращай его стекло, фон, шрифты или меню
  в противоречие текущему UI без запроса пользователя. Примерные данные референса не заменяют реальные.
- Проверь приложение на desktop/mobile, состояния, keyboard/focus и browser console.
  Если браузер недоступен, изучи компоненты и каскад, явно отметь отсутствие baseline/QA;
  не подменяй его старым изображением и не заявляй визуальное соответствие. Существенный
  неразрешимый конфликт источников покажи конкретным сравнением. Детали — в `docs/codex/UI_RULES.md`.

## Testing Stage Gate

Проверяй изменения этой задачи и их риск. Предсуществующий dirty baseline учитывай отдельно:
не скрывай его ошибки, не исправляй вне scope и не объявляй весь worktree проверенным.
Команды, селекторы, deadlines и диагностика — в [TEST_MATRIX.md](docs/codex/TEST_MATRIX.md).
Для локального browser-риска добавляй scoped E2E затронутых сценариев и проектов.
Новые тесты проверяют наблюдаемое поведение или инварианты, а не повторяют реализацию;
для обратимой правки без изменения поведения используй существующие проверки.

| Scope                                                 | Обязательная проверка                                                                                                                                |
| ----------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------- |
| Документация, навыки, `.codex` без изменения продукта | Свой diff, ссылки, формат, TOML/YAML, соответствие npm-команд; реалистичные сценарии решений. Без `verify`/E2E и тестов на совпадение текста правил. |
| R1, read-only аудит                                   | Targeted read-only checks по необходимости; без полного E2E, `verify` не обязателен без изменения файлов.                                            |
| R2–R8, обычный код                                    | Targeted tests → при общем domain/application/shared-контракте `test:fast` → один `verify` после стабилизации.                                       |
| R9, migration/compatibility                           | Targeted migration tests → `verify`; для локального persistence добавить scoped E2E при browser-риске.                                               |
| R10, visual/mobile                                    | Targeted visual/render tests → `verify`; desktop/mobile QA, scoped E2E при изменении browser-поведения.                                              |
| R11, analytics                                        | Targeted analytics tests → `verify`; scoped E2E при изменении сквозного flow.                                                                        |
| R12, явно запрошенная финальная регрессия/релиз       | `verify` → полный `test:e2e`, либо `verify:full`. Уже актуальный зелёный `verify` не повторять.                                                      |

Изменения build/test scripts, runtime config, зависимостей и CI — исполняемая инфраструктура,
а не исключение для документации. Проверяй их по риску. Завершение задачи/commit/handoff не
превращает обычную правку в R12; R9/R10 сами по себе не требуют полного E2E.

### Когда нужен полный E2E

Полный `test:e2e` без селекторов или `verify:full` запускай только при одном из оснований:

- прямой запрос полного E2E/финальной регрессии или подготовка релиза;
- общая схема хранения, миграция или восстановление данных нескольких разделов;
- общий routing/navigation, startup/recovery, shell или browser-инфраструктура влияют на несколько
  независимых flows, которые нельзя надёжно покрыть scoped-проверками;
- targeted/scoped проверки выявили межсценарную регрессию с неясными после диагностики границами.

Перед запуском назови общий контракт/релизный критерий и почему scoped-проверок недостаточно.
Локальный UI, маршрут, IndexedDB-адаптер или mobile-патч сам по себе не основание для полного suite.
В финале укажи выбранный объём и причину запуска/пропуска полного E2E.

### Доказательства и зависания

- Используй bounded npm-команды из матрицы; `verify` уже содержит typecheck, lint, unit/integration,
  infra, alpha, build, формат и Git hygiene. Не дублируй их отдельно без диагностической причины.
- Успешный прогон остаётся доказательством, пока релевантный код/среда не изменились. Новый отчёт
  или reviewer не повод повторять его. Повтор/расширение нужны при влияющей правке, failure или
  новом риске; для timing-sensitive дефекта проверяй конкретную гипотезу отдельным тестом.
- Не используй watch/interactive-команды как gate. Timeout `124` — failure, не успех.
  При подозрении на hang сообщи этап, команду, elapsed и последний вывод; движущийся heartbeat
  означает прогресс. После deadline проверь cleanup только owned-процессов/портов, выдели последний
  scenario/project и воспроизведи отдельным тестом. Не перезапускай весь suite автоматически;
  повтор полного gate — после исправления причины. Чужие процессы по занятому порту не завершай.
- Перед завершением изучи `git diff`, выполни `git diff --check` и `git status --short`.
  Не заявляй успех без фактического результата команды/browser QA. Укажи невыполненные обязательные
  проверки и необходимую ручную QA; при отсутствии rendered comparison — «Требуется ручная визуальная проверка».
