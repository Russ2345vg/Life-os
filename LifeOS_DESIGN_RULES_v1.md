# LifeOS — Design Rules v1.2

**Статус:** утверждённая базовая дизайн-система LifeOS  
**Дата:** 9 сентября 2026

**Назначение:** обязательные правила для проектирования и реализации новых экранов, компонентов и состояний LifeOS.

> LifeOS должен ощущаться как персональный премиальный центр управления жизнью: тёмный, глубокий, спокойный, материальный, функциональный. В покое интерфейс сдержан; при взаимодействии он оживает светом, глубиной и движением.

## Актуальность визуального источника

25.09.2026 пользователь утвердил [Premium, вариант 2](docs/design/references/2026-09-25-premium/approved-direction.png)

явное указание пользователя для задачи → текущий интерфейс активного worktree и его компоненты
→ общие правила → исторические референсы. Перед проектированием обязателен browser baseline
затронутой страницы и проверка реально подключённого CSS-каскада.

[«Новое направление»](docs/design/references/2026-09-09-shared-glass/new-direction.png) —
исторический референс от 2026-09-09. Упоминания лесной сцены, постоянного стекла и атмосферы

Для оболочки, материалов, шрифтов, навигации и плотности используй действующую реализацию,
если пользователь явно не задал новое направление. Семантика цветов, доступность,
переиспользование компонентов и требования к проверке остаются действующими.

# 0. Главные принципы

1. **Смысл важнее декора.** Каждый визуальный эффект должен помогать понять приоритет, состояние или действие.
2. **Один экран — один главный визуальный центр.** Вторичные элементы не конкурируют с главным.
3. **Цвет = смысл.** Цвет определяется семантикой, а не типом компонента и не желанием украсить экран. Единый тёплый акцент связывает разделы; семантические состояния сохраняют свои значения.
4. **Интерфейс должен работать без цвета.** Размер, положение, типографика и пространство создают иерархию; цвет только усиливает её.
5. **Свечение — редкий акцент.** Свет показывает активность, выбранность, фокус или важность, но не используется как постоянный декор всего экрана.
6. **Материальность дозирована.** Графит, матовое золото, дымчатое стекло, мягкие тени и локальный свет создают премиальность без игрового неона.
7. **Мобильная версия перестраивается, а не уменьшается.** Приоритеты сохраняются, композиция меняется.
8. **Одинаковая функция = одинаковый компонент.** Не создавать разные виды кнопок, вкладок, статусов или фильтров без необходимости.
9. **Пустой или загружающийся экран — это тоже спроектированное состояние.**
10. **Новые экраны обязаны использовать дизайн-токены и существующие компоненты.** Случайные значения запрещены.

# 1. Цветовая система LifeOS

## 1.1. Базовая палитра

```css
--bg-canvas: #101619;
--bg-sidebar: rgb(18 25 29 / 30%);
--surface-1: #1b2225;
--surface-2: #252c2f;
--surface-3: #30373a;
--border-soft: rgb(218 226 229 / 18%);
--border-strong: rgb(225 232 235 / 32%);

--text-primary: #f3f4f3;
--text-secondary: #b6c0c7;
--text-muted: #a4afb6;

--gold-main: #edbc8c;
--gold-soft: #ffdab0;

--success: #62a86b;
--warning: #c98a3d;
--danger: #e58484;
--info: #5c728a;
```

### Правило №1 — Семантический цветовой код

- **Графит / почти чёрный** — фон и основные поверхности.
- **Мягкий молочный** — основной текст.
- **Нейтральный графит / серый** — будущее, неактивность, вторичный уровень, metadata, disabled, разделители.
- **Золото** — текущее, primary, приоритет, главный CTA, выбранный важный объект.
- **Зелёный** — завершение, success, recovery, подтверждённое положительное состояние.
- **Синий / сине-серый** — информация, guidance, аналитика и информационная навигация.
- **Янтарный / оранжевый** — pending, внимание, ожидание, начало процесса.
- **Красный** — ошибка, критический риск, destructive action.
- **Фиолетовый** — insight, reflection и идеи, только в специальных контекстах.

> **Жёсткое правило: COLOR MUST COME FROM SEMANTICS, NOT FROM COMPONENT TYPE OR DECORATION.** Сначала определяется смысл элемента, затем цвет. Карточка, кнопка, иконка или шаг не получают цвет только потому, что это другой тип компонента или соседний объект нужно визуально отличить.

### Каноническая иерархия состояний

| Смысл                                                               | Цвет                                        |
| ------------------------------------------------------------------- | ------------------------------------------- |
| Current / primary / priority / main CTA / selected important object | золото                                      |
| Completed / success / recovery / positive confirmed state           | зелёный                                     |
| Future / inactive / secondary / metadata / disabled                 | нейтральный графит / серый                  |
| Information / guidance / analytics / informational navigation       | синий / сине-серый                          |
| Pending / attention / waiting / process start                       | янтарный / оранжевый                        |
| Error / critical risk / destructive action                          | красный                                     |
| Insight / reflection / ideas                                        | фиолетовый, только в специальных контекстах |

Для guided flow: текущий шаг — золотой, завершённый — зелёный, будущий — нейтрально-серый, шаг с ошибкой — красный.

### Запрещено

- фиолетовый как глобальный brand-, navigation- или системный цвет;
- розовый как основной акцент;
- кислотные оттенки;
- яркий неон на больших площадях;
- синий только ради визуального разнообразия;
- случайные фиолетовые акценты вне insight / reflection / ideas;
- использование цвета только ради украшения.

### Баланс

- 80–90% экрана — нейтральная тёмная база;
- 5–10% — общий тёплый акцент;
- остаток — семантические состояния и редкие акценты.

# 2. Поверхности и навигация

### Правило №2 — Поверхности и боковое меню

Разделение интерфейса создаётся прежде всего:

- расстоянием;
- иерархией;
- минимальной разницей яркости поверхностей;
- тенью;
- локальным светом.

Рамки используются только там, где без них теряется структура.

### Каноническая система материалов

В LifeOS ровно пять базовых материалов. Названия описывают роль материала, а не новый тип компонента.

| Материал            | Назначение                                                        | Ограничение                                                       |
| ------------------- | ----------------------------------------------------------------- | ----------------------------------------------------------------- |
| **Graphite Panel**  | основная структурная поверхность                                  | плотный fallback, вложенные и специальные рабочие области         |
| **Frosted Glass**   | общая оболочка, формы, карточки, modal, popover, dropdown         | постоянные поверхности допустимы; обязательны контраст и fallback |
| **Gold Edge**       | премиальная локальная кромка текущего или важного объекта         | никогда не обводить ею все карточки                               |
| **Soft Glow**       | слабый направляющий свет active / focus-состояния                 | низкая opacity; не держать постоянно на множестве элементов       |
| **Success Surface** | зелёная тонированная поверхность завершённого / success-состояния | не использовать для незавершённых или просто активных объектов    |

Сланец, латунь, дымка, тень и блик остаются допустимыми визуальными качествами этих материалов, но не образуют дополнительные базовые материалы.

### Левое меню

- спокойное стеклянное меню, компактный rail или развёрнутые подписи по существующей настройке;
- иконка + название;
- смысловые группы;
- профиль и настройки закреплены снизу;
- активный пункт получает мягкую цельную плашку и локальное свечение.

# 3. Единая цветовая идентичность

### Правило №3 — Общий акцент приложения

Все разделы используют `--gold-main` (`#edbc8c`), выбранные состояния — `--gold-soft`.
`section accent` в дизайн-контрактах означает общий акцент темы, а не отдельную палитру раздела.
Зелёный — success/completed, красный — error/destructive; текущие предметные цвета сфер и
семантические цвета графиков не переписываются визуальным редизайном.
Не окрашивать меню, заголовки и фоны разных разделов в разные декоративные цвета.

---

# 4. Атмосферные фоны

### Правило №4 — Общая природная сцена

Один статичный лесной пейзаж с горами, туманом и тёплым закатом расположен за всей оболочкой.
Меню, шапка и рабочая область видят одну сцену. Не заводить копию фона для каждой страницы.
На mobile меняется кадрирование; контраст текста важнее видимости пейзажа. Специализированные
ритуальные сцены переводятся на основу отдельным этапом, без изменения их пользовательских flow.

- Тёмный центр и мягкий scrim обеспечивают читаемость.
- Не добавлять анимацию фона или постоянные движущиеся частицы.
- Не смешивать фото, мультяшную иллюстрацию, 3D и абстракцию на равных.

# 5. Карточки

### Правило №5 — Гибридная система карточек

#### Обычная карточка

- дымчатое стекло на общем фоне, графитовый fallback без blur;
- тонкая граница или отсутствие рамки;
- без свечения;
- слабая тень;
- плотная, но не тесная.

#### Важная карточка

- поверхность немного светлее;
- больше воздуха;
- мягкая глубина;
- семантически обоснованный локальный акцент;
- слабое свечение или блик.

#### Главная карточка страницы

- на экране обычно одна;
- максимальный визуальный приоритет;
- допускается материальная окантовка, локальный свет, атмосферный фон.

> Чем важнее информация, тем больше воздуха, глубины и композиционного веса — а не толще рамка.

---

# 6. Скругления и геометрия

### Правило №6

```css
--radius-sm: 8px;
--radius-md: 12px;
--radius-lg: 16px;
--radius-xl: 20px;
```

- 8–10 px — поля, маленькие кнопки, компактные контролы;
- 12–14 px — стандартные карточки и панели;
- 16–20 px — крупные смысловые и атмосферные поверхности.

Не использовать чрезмерно круглые «пузырьковые» формы.

---

# 7. Тени и свечение

### Правило №7

- обычные карточки — почти без тени;
- важные блоки — мягкая глубокая тень;
- active / focus-элементы — локальный **Soft Glow** семантически подходящего цвета;
- главная карточка может сочетать тень и слабый внутренний свет;
- завершение может дать короткий зелёный свет;
- предупреждение и ошибка обозначаются цветом, а не сильным неоном.

```css
--shadow-soft: 0 6px 20px rgba(0, 0, 0, 0.22);
--shadow-deep: 0 16px 40px rgba(0, 0, 0, 0.32);
--glow-opacity-soft: 0.1;
--glow-opacity-active: 0.16;
```

> Тень создаёт глубину. Свечение показывает активность и смысл.

---

# 8. Типографика

### Правило №8 — Гибридная типографика

**Основной интерфейсный шрифт:** `Manrope`, fallback `Inter, system-ui, sans-serif`.  
**Выразительный display-шрифт:** `Cormorant Garamond` — только для крупных атмосферных заголовков, если поддержка и читаемость достаточны.

### Иерархия

- **Display / Hero** — главный смысловой заголовок раздела;
- **H1** — заголовок страницы;
- **H2** — крупный блок;
- **H3** — карточка / секция;
- **Body** — основной текст;
- **Meta** — подписи, даты, вторичные сведения.

Ориентиры:

```css
--font-display: 44-56px;
--font-h1: 32-40px;
--font-h2: 22-28px;
--font-h3: 16-18px;
--font-body: 14-16px;
--font-meta: 12-13px;
```

Не использовать множество случайных размеров. Выразительность допускается только в крупных смысловых зонах.

---

# 9. Статусные метки

### Правило №9 — Статусные капсулы

Статус = компактная капсула с тёмной полупрозрачной базой, тонкой семантической рамкой, иконкой, текстом и крайне мягким внутренним свечением.

| Статус                   | Цвет                                        |
| ------------------------ | ------------------------------------------- |
| Completed / Выполнено    | зелёный                                     |
| Pending / Ожидает        | янтарный                                    |
| Information / Информация | синий                                       |
| Error / Ошибка           | красный                                     |
| Insight / Идея           | фиолетовый, только в специальных контекстах |
| Neutral / Future         | графит / серый                              |

Высота: 28–34 px. Свечение остаётся крайне слабым во всех состояниях. Конкретные доменные названия статусов сопоставляются с ближайшей канонической семантикой; не создавать уникальные цвета для десятков статусов.

# 10. Сетка, плотность и отступы

### Правило №10 — Гибридная плотность

Ключевые зоны — воздушные. Рабочие списки — плотнее.

```css
--space-1: 4px;
--space-2: 8px;
--space-3: 12px;
--space-4: 16px;
--space-5: 24px;
--space-6: 32px;
--space-7: 48px;
--space-8: 64px;
```

- 8 px — связанные мелкие элементы;
- 12–16 px — компактные компоненты;
- 20–24 px — внутренняя область обычной карточки;
- 32 px — между смысловыми блоками;
- 48–64 px — между крупными зонами.

> Связанные элементы ближе. Разные смысловые группы разделяются воздухом.

---

# 11. Кнопки

### Правило №11 — Иерархия действий

#### Primary

- одна сильная кнопка на смысловой экран / блок;
- золото для главного CTA;
- мягкое свечение;
- высокий контраст.

#### Secondary

- графитовая поверхность;
- тонкая рамка;
- без постоянного свечения.

#### Tertiary / text action

- текст или иконка без тяжёлой плашки.

#### Destructive

- красный только для реально опасного действия;
- в покое может быть нейтральным, красным становиться при наведении / подтверждении.

Размеры: S / M / L. Случайные высоты запрещены.

---

# 12. Материальность

### Правило №12 — Премиальные материалы

Визуальный язык строится на пяти канонических материалах из Правила №2: **Graphite Panel**, **Frosted Glass**, **Gold Edge**, **Soft Glow**, **Success Surface**.

Постоянные поверхности оболочки, форм и каталога используют Frosted Glass. Graphite Panel служит плотным fallback и вложенной рабочей поверхностью. Материальность усиливается только у ключевых блоков и только материалом, соответствующим их роли: Gold Edge — у текущего / важного объекта, Soft Glow — у active / focus, Success Surface — у completed / success.

---

# 13. Иконки и световые плитки

### Правило №13

Контурные монохромные иконки — default. Их цвет следует семантическому состоянию: future / inactive — нейтральный, current important — золотой, completed — зелёный; синий и фиолетовый допустимы только при соответствующем информационном или insight-смысле.

Быстрые действия, режимы и специальные инструменты могут использовать специальные световые плитки:

- графитовая подложка;
- 14–18 px радиус;
- цветная иконка;
- мягкий локальный свет;
- слабая стеклянная глубина.

---

# 14. Поля ввода и формы

### Правило №14 — Гибридные поля

#### Default

- графитовая поверхность;
- тонкая малоконтрастная рамка;
- без свечения.

#### Hover

- немного светлее;
- рамка заметнее.

#### Focus

- высококонтрастный нейтральный или золотой контур по уровню важности;
- тонкий световой контур;
- мягкий внешний glow.

#### Error

- красная рамка / иконка;
- короткое объяснение;
- без агрессивного свечения.

#### Success

- зелёная иконка / лёгкая рамка при необходимости.

Подпись поля располагается над полем. Placeholder не заменяет label.

Формы делятся на смысловые группы, а не на длинные бесконечные колонки.

---

# 15. Световой контур

### Правило №15

Яркий световой контур используется преимущественно у:

- активных вкладок;
- выбранных фильтров;
- focus-состояний;
- переключателей;
- компактных активных контролов.

Крупная главная карточка не получает полный неоновый обвод: она «ловит свет» через тонкую металлическую кромку, локальный блик и слабый glow.

---

# 16. Объёмные иконки-плитки

### Правило №16

Премиальный акцентный компонент для:

- быстрых действий;
- категорий;
- режимов;
- специальных виджетов.

Не использовать как основной тип иконок в длинной навигации, таблицах и плотных списках.

---

# 17. Стеклянные поверхности

### Правило №17 — Dark Frosted Glass

Frosted Glass — общий материал постоянной оболочки и рабочих поверхностей, а также overlays.

- Меню, шапка, inline-формы и строки каталога используют единые surface tokens.
- Полупрозрачная заливка пропускает реальную общую сцену; blur сам по себе не создаёт стекло.
- Blur размещается на декоративном псевдоэлементе, когда контейнер содержит dropdown/fixed dialog.
- Не применять filter/transform/backdrop-filter к общим предкам fixed overlays.
- Текст, границы и controls не размываются. Dropdown/modals используют более плотное стекло.
- Предусмотреть непрозрачный Graphite fallback при отсутствии backdrop-filter.
- Не накладывать несколько независимых blur-слоёв без необходимости; проверить mobile performance.

---

# 18. Модальные окна, меню и всплывающие панели

### Правило №18

Единый слой тёмного матового стекла:

- дымчатая полупрозрачность;
- умеренный blur;
- тонкая световая кромка;
- мягкая глубокая тень;
- 16–20 px радиус у модалок;
- 10–12 px у компактных меню;
- 90–95% поверхности остаётся графитовой.

Общий тёплый акцент — только слабый отблеск.

Модалки не используются для мелких действий, которые можно выполнить inline.

---

# 19. Управляемые сценарии

### Правило №19

Многошаговые процессы визуализируются как путь:

`завершённый шаг → текущий шаг → будущий шаг → итог`

- текущий шаг — максимальный акцент;
- текущий шаг — золотой; во всех разделах используется общий тёплый акцент;
- завершённые — зелёные и явно отмечены как completed;
- будущие — нейтральные графитовые / серые и приглушённые;
- ошибка шага — красная;
- pending / waiting / process start — янтарный, если это отдельное от current состояние;
- этапы могут соединяться нейтральной или семантически окрашенной световой нитью;
- пользователю показывается прежде всего текущий выбор;
- после завершения — итоговый экран.

Подходит для ритуалов, создания цели, принятия решения, настройки привычки, onboarding.

---

# 20. Компактные метрики

### Правило №20

Ключевые числовые показатели могут отображаться в компактных капсулах:

- кольцевой индикатор;
- крупное значение;
- короткая подпись;
- тёмная спокойная поверхность;
- мягкий внутренний свет.

Использовать ограниченно: обычно 2–4 ключевые метрики на экран.

---

# 21. Сетка и шаблоны экранов

### Правило №21

Основная desktop-область строится на 12-колоночной сетке.

#### Шаблон A — Центр управления

`8 + 4`

Подходит: Сегодня, Финансы, Аналитика.

#### Шаблон B — Рабочий экран

`3 + 6 + 3`

Подходит: Проекты, Решения, Цели.

#### Шаблон C — Глубокий фокус

Один доминирующий объект.

Подходит: активная сессия, выполнение действия, вечерний ритуал, глубокая запись.

#### Шаблон D — Аналитический

KPI сверху → основной график → контекст → подробности.

### Размеры виджетов

S / M / L / XL.

Размер отражает смысловой приоритет, а не случайное содержимое.

---

# 22. Структура без цвета

### Правило №22

Любой экран должен сохранять понятную иерархию в монохромном виде.

Структуру создают:

- размер;
- расположение;
- типографика;
- пространство;
- глубина;
- последовательность.

Цвет и glow только усиливают её.

Во время загрузки использовать skeleton-состояния, повторяющие реальную геометрию будущего интерфейса.

---

# 23. Информационные панели

### Правило №23

Аналитические и обзорные экраны строятся вокруг одного главного показателя или визуального объекта.

Детализация сверху вниз:

`состояние → ключевые показатели → динамика → подробности`

Вторичные метрики компактны, графики могут быть интегрированы в поверхность страницы без лишних контейнеров.

Мобильная версия: 4–5 основных пунктов нижней навигации + при необходимости контекстное центральное действие.

---

# 24. Иконографика

### Правило №24

Основной язык — минималистичные контурные пиктограммы единого семейства.

- одинаковая толщина линий;
- одинаковая геометрия;
- одинаковый визуальный вес;
- один смысл = одна иконка во всём приложении.
- монохромный outline — default;
- цвет иконки следует семантическому состоянию, а не типу компонента;
- future / inactive — нейтральный серый;
- current important — золото;
- completed — зелёный;
- синий и фиолетовый — только при реальном значении information / insight;
- illuminated icon tiles — специальные компоненты, не default-подача иконок.

Размеры:

- 16 px — служебные;
- 20 px — большинство интерфейса;
- 24 px — навигация / кнопки;
- 28–32 px — специальные функции;
- 40+ px — крупные визуальные плитки.

---

# 25. Интерактивные состояния

### Правило №25

Единый набор состояний:

`default → hover → pressed → selected/active → focus → disabled → loading → success/error`

- default — спокойный графит;
- hover — немного ярче без назначения нового семантического цвета;
- pressed — лёгкое «утапливание»;
- selected important — золото + тонкий контур + мягкий glow; вторичный selection может оставаться нейтральным;
- focus — отдельная внешняя линия;
- disabled — читаемый, но без свечения;
- loading — геометрия не прыгает;
- success — короткий зелёный отклик;
- error — красный акцент + понятное восстановление.

---

# 26. Вкладки, фильтры и переключатели

### Правило №26

- крупные вкладки — линейные;
- компактные режимы — капсульные;
- segmented control — общая графитовая капсула;
- выбранный важный элемент получает золото, тонкий контур и мягкий свет; вторичный выбор может использовать нейтральный контраст;
- фильтр становится акцентным только если реально активен;
- category chips спокойнее статусных меток;
- период располагается рядом с данными, которые меняет;
- toggle не передаёт смысл только цветом;
- radio / checkbox унифицированы.

---

# 27. Графики и аналитика

### Правило №27

- фон графиков почти совпадает с поверхностью страницы;
- сетка и оси минимальны;
- основная серия = общий акцент; дополнительные серии различаются по смыслу;
- семантические цвета оценивают результат;
- вверх не всегда означает хорошо, вниз не всегда плохо;
- 1–3 серии одновременно;
- сравнение периода — приглушённая серия;
- прогноз — пунктир;
- tooltip — компактное тёмное стекло;
- кольца — только для ограниченного прогресса;
- sparklines допустимы внутри KPI;
- важные события могут отмечаться на временной линии.

Запрещены 3D-графики, радуга, сильный постоянный неон и декоративная аналитика без смысла.

---

# 28. Анимации и переходы

### Правило №28

```css
--motion-micro: 100-160ms;
--motion-component: 160-240ms;
--motion-page: 220-320ms;
```

- hover — мягкое усиление;
- press — scale 0.98–0.99;
- карточки могут подниматься на 1–2 px;
- модалки: dim + blur + opacity + scale 0.98→1;
- вкладки: короткий fade и минимальное смещение;
- guided-flow: линия процесса плавно заполняется;
- прогресс анимируется только при реальном изменении;
- завершение действия — короткий зелёный отклик;
- общий фон остаётся статичным;
- график мягко появляется при первом показе / смене периода;
- skeleton без яркого shimmer;
- удаление — fade + collapse;
- левое меню не перерисовывается при смене страницы.

Поддерживать `prefers-reduced-motion`.

# 29. Пустые состояния

### Правило №29

Пустота — осмысленное состояние интерфейса.

#### Первый запуск

- атмосферный визуал;
- короткий заголовок;
- одно объяснение;
- один CTA.

#### Нет результатов фильтра

- компактное состояние;
- действие: сбросить / изменить фильтр.

#### Поиск ничего не нашёл

- показать запрос;
- предложить изменить или очистить.

#### Всё выполнено

- позитивное завершённое состояние;
- мягкий зелёный акцент.

> Пустая карточка либо ведёт к действию, либо не показывается.

# 30. Уведомления и системная обратная связь

### Правило №30

LifeOS использует 4 уровня системного сообщения:

1. **Toast** — короткое подтверждение, исчезает автоматически.
2. **Inline feedback** — сообщение рядом с элементом, где возникло состояние.
3. **Banner** — важное состояние страницы, требующее внимания.
4. **Blocking dialog** — только если действие опасно или невозможно продолжить.

### Toast

- компактный;
- тёмное стекло;
- иконка + короткий текст;
- 2.5–4 сек для обычного подтверждения;
- не перекрывает основные кнопки;
- не использовать для ошибок, которые требуют действия.

### Banner

Для незавершённого дня, потери связи, конфликтов, важных предупреждений.

- тонкая горизонтальная полоса / карточка;
- семантический цвет;
- одно основное действие;
- не конкурирует с главным контентом.

### Тексты

Хорошо: `Не удалось сохранить. Повторить`  
Плохо: `Error 500`.

---

# 31. Списки, таблицы и плотные данные

### Правило №31

Плотные данные должны быть функциональными, а не превращаться в набор тяжёлых карточек.

#### Списки

- высота строки ориентировочно 44–56 px;
- разделители минимальны;
- hover показывает интерактивность;
- selected отличается не только цветом;
- быстрые действия появляются по hover / focus или через `•••`.

#### Таблицы

- sticky header при длинном скролле;
- числа выравниваются по правому краю;
- текст — по левому;
- одинаковые форматы дат и денег;
- сортировка видима;
- активная строка получает мягкую подложку;
- массовые действия появляются только после выбора строк.

Не оборачивать каждую строку таблицы в отдельную карточку.

# 32. Адаптивность и мобильная версия

### Правило №32

LifeOS имеет три режима компоновки:

- **Desktop** — 12 колонок, фиксированная боковая навигация;
- **Tablet** — сокращённая навигация, 8 колонок, правая колонка может уходить вниз;
- **Mobile** — единый вертикальный поток, нижняя навигация 4–5 пунктов.

### Mobile-first ограничения

- минимальная touch-zone: 44×44 px;
- главная кнопка доступна без точного попадания;
- модалки превращаются в full-height / bottom-sheet при необходимости;
- таблицы преобразуются в карточный / list-представление или горизонтальный скролл только если это оправдано;
- графики перестраиваются, легенды упрощаются;
- secondary sidebar уходит вниз по приоритету;
- атмосферный фон становится компактнее и темнее.

Нельзя просто уменьшить desktop-экран до ширины телефона.

---

# 33. Доступность

### Правило №33

- текст и интерактивные элементы должны иметь достаточный контраст;
- смысл состояния не передаётся только цветом;
- у клавиатурного фокуса есть видимый focus-ring;
- touch-zone минимум 44×44 px;
- важные иконки сопровождаются label / tooltip;
- все controls доступны с клавиатуры;
- drag & drop имеет альтернативу кнопками;
- анимации поддерживают reduced motion;
- ошибки сообщаются текстом, а не только красной рамкой;
- placeholder не является единственной подписью поля.

---

### Правило №33.1 — Голосовой ввод

Свободный человеческий текст и поиск используют единую систему Voice Input. Существующие и
будущие поля подключают `VoiceTextInput` / `VoiceTextArea`, передавая `value` и существующий
`onValueChange`. Для подписи, оборачивающей поле, применяется `VoiceField` с первым `span` в роли
подписи: названия кнопок и сообщения распознавания не должны попадать в доступное имя поля.
Отдельный `<label htmlFor>` также поддерживается. Явное исключение — `voiceInput={false}`.

- Микрофон — компактное контурное tertiary-действие рядом с полем; одна общая панель `endActions`
  резервирует место и исключает перекрытие текста, очистки и счётчиков.
- Покой — нейтральный графит/серый; listening — матовое золото; success — короткий зелёный отклик;
  error — сдержанный красный и понятный текст. Processing, disabled и unsupported различимы.
- Кнопка `type="button"`, доступна с клавиатуры, имеет `aria-label`, tooltip, видимый focus-ring,
  состояние активности и touch-zone не меньше 44×44 px. Reduced motion отключает пульсацию.
- Речь вставляется в актуальную позицию курсора или заменяет выделение через тот же callback,
  что клавиатура. Промежуточный результат не сохраняется в форму. Ошибки не уничтожают текст;
  `maxLength` ограничивает только вставку. Сохранение, валидация и submit не меняются.
- Разрешение запрашивается только после нажатия микрофона. Отказ, отсутствие устройства/API,
  сетевой сбой и прерывание оставляют ручной ввод доступным. Автоматического повторного запроса нет.
- На приложение действует один координатор с одной активной сессией; смена поля и unmount
  отменяют старую запись и игнорируют поздние результаты.
- Presentation зависит от application-порта `SpeechRecognitionProvider`; браузерный API находится
  только в Infrastructure. Будущие native/cloud adapters заменяют provider, а не формы.
- По умолчанию язык `ru-RU`, настройка — `voiceLanguage`. LifeOS не хранит аудио и не отправляет
  его в свой backend; браузерный движок может использовать службу производителя браузера.
- Исключаются пароли/PIN, числа и единицы измерения, даты/время, select/checkbox/radio/switch/slider,
  файлы, цвета, emoji/icon, секреты восстановления и точные pairing payloads.
- Не создавать локальные микрофоны для отдельных экранов, глобальные DOM-вставки кнопок,
  дополнительные tooltip-компоненты, голосовые команды или автоматическое заполнение предметных полей.

Контракты и аудит: [Voice Input System](docs/design/features/2026-09-04-voice-input-system.md).

# 34. Атмосферные изображения и декоративные элементы

### Правило №34

Художественный слой LifeOS должен быть единым.

#### Разрешено

- тёмные кинематографичные ландшафты;
- абстрактная архитектура;
- тонкие линии и сетки;
- дымка;
- световые пятна;
- очень слабые частицы;
- локальный градиент общего тёплого акцента.

#### Не разрешено

- яркие стоковые фото;
- мультяшные иллюстрации;
- случайный 3D;
- fantasy / gaming-декор;
- постоянно летящие частицы;
- крупный текст поверх сложного изображения без затемнения.

### Техническое правило

Под текстом всегда должен быть достаточный затемняющий gradient / scrim.

# 35. Текст интерфейса и микрокопирайтинг

### Правило №35

Тексты LifeOS короткие, конкретные, спокойные.

#### Кнопки

Начинать с действия:

- `Начать день`
- `Создать цель`
- `Сохранить`
- `Продолжить`
- `Завершить`

Не использовать:

- длинные канцелярские формулировки;
- технический жаргон без необходимости;
- искусственно-мотивационные лозунги;
- англицизмы, если есть естественный русский эквивалент.

#### Ошибки

Формула:

`что произошло → что делать`

Например: `Не удалось сохранить изменения. Повторить`.

#### Пустые состояния

Формула:

`что здесь будет → зачем → одно действие`.

---

# 36. Поиск, палитра команд и быстрые действия

### Правило №36

Для большого LifeOS предусмотреть глобальную палитру команд (`Ctrl/Cmd + K`).

Она может искать:

- разделы;
- цели;
- проекты;
- решения;
- действия;
- записи дневника;
- настройки;
- быстрые команды.

### Визуально

- тёмное стеклянное окно;
- крупная строка поиска;
- результаты группируются по типу;
- клавиатурная навигация;
- активная важная строка получает золотой, а вторичная — нейтральный мягкий контур;
- последние / частые действия показываются только если полезны.

Быстрые действия не должны дублировать десятки кнопок на главной странице.

---

# 37. Drag & Drop и прямое управление

### Правило №37

Перетаскивание используется только там, где оно реально упрощает работу:

- порядок задач;
- этапы;
- приоритеты;
- расписание;
- карточки доски.

#### Во время drag

- объект слегка приподнимается;
- тень усиливается;
- появляется grip / понятный handle;
- место вставки явно обозначается;
- остальные элементы не прыгают хаотично;
- текущее место вставки обозначается золотом или высококонтрастным нейтральным цветом; новый декоративный цвет не вводится.

Обязательно иметь альтернативу без drag & drop: кнопки перемещения / меню.

---

# 38. Финальный чек-лист качества экрана

### Правило №38 — Экран не считается готовым, пока не пройдёт проверку

#### Иерархия

- [ ] Есть один главный визуальный центр.
- [ ] Главное действие понятно за 2–3 секунды.
- [ ] Вторичные элементы не конкурируют с главным.
- [ ] Экран понятен в монохроме.

#### Цвет

- [ ] Общая палитра и материалы используются последовательно, включая меню и шапку.
- [ ] Семантические цвета не перепутаны.
- [ ] Цвет каждого элемента объясняется смыслом, а не типом компонента или декором.
- [ ] Current / primary — gold; completed — green; future / inactive — neutral gray.
- [ ] Blue используется только для information / guidance / analytics / informational navigation.
- [ ] Violet используется только для insight / reflection / ideas.
- [ ] Нет лишнего неона.
- [ ] Свечение используется только там, где есть смысл.

#### Карточки и сетка

- [ ] Нет карточки вокруг каждого текста.
- [ ] Размер блоков соответствует важности.
- [ ] Соблюдается 4px spacing scale.
- [ ] Используется утверждённый шаблон страницы.

#### Компоненты

- [ ] Кнопки используют общую иерархию.
- [ ] Статусы используют общую систему.
- [ ] Иконки из одного семейства.
- [ ] Tabs / filters / toggles не изобретены заново.
- [ ] Все интерактивные состояния предусмотрены.

#### Состояния

- [ ] Есть loading.
- [ ] Есть empty state.
- [ ] Есть error / retry.
- [ ] Есть success feedback.
- [ ] Disabled-состояние понятно.

#### Mobile

- [ ] Экран перестроен, а не уменьшен.
- [ ] Touch-zone ≥ 44×44 px.
- [ ] Главные действия доступны большим пальцем.
- [ ] Нет горизонтального скролла без необходимости.

#### Доступность

- [ ] Смысл не зависит только от цвета.
- [ ] Видим keyboard focus.
- [ ] Контраст достаточный.
- [ ] Reduced motion поддерживается.

#### Финальный визуальный тест

- [ ] Убрать цвет: структура остаётся понятной.
- [ ] Убрать glow: интерфейс остаётся качественным.
- [ ] Убрать рамки: композиция не разваливается.
- [ ] Уменьшить экран: главный приоритет сохраняется.

# 39. Дизайн-токены — обязательный технический слой

Все новые компоненты должны использовать токены. Не вводить случайные значения напрямую, если существует соответствующий token.

## 39.1. Цвета

Использовать канонические переменные tokens.css; старые --color-* являются aliases той же палитры.

Пример:

```css
--section-accent: var(--section-today);
--section-accent-soft: color-mix(in srgb, var(--section-accent) 16%, transparent);
--section-accent-glow: color-mix(in srgb, var(--section-accent) 12%, transparent);
```

## 39.2. Радиусы

```css
--radius-sm: 8px;
--radius-md: 12px;
--radius-lg: 16px;
--radius-xl: 20px;
```

## 39.3. Отступы

```css
--space-1: 4px;
--space-2: 8px;
--space-3: 12px;
--space-4: 16px;
--space-6: 24px;
--space-8: 32px;
--space-12: 48px;
```

## 39.4. Высоты контролов

```css
--control-sm: 44px;
--control-md: 44px;
--control-lg: 48px;
```

## 39.5. Blur

```css
--blur-popover: 12px;
--blur-modal: 16px;
--blur-hero: 20px;
```

Blur не должен ухудшать читаемость и производительность.

## 39.6. Z-index

Рекомендуемая шкала:

```text
0    base
10   sticky content
20   sidebar/topbar
30   dropdown/popover
40   tooltip
50   modal backdrop
60   modal
70   toast
```

# 40. Архетипы страниц LifeOS

## Сегодня

- цвет: золото;
- фон: общая лесная атмосфера оболочки;
- шаблон: 8+4;
- главный объект: следующее важное действие / главный фокус;
- верх: дата + состояние дня + компактные метрики;
- центр: 3 главных решения;
- справа: Сейчас / быстрые действия / фокус;
- дополнительные решения и действия ниже.

## Распорядок

- цвет: общий тёплый акцент;
- фон: общая лесная атмосфера оболочки;
- главный объект: текущий этап дня;
- ритуалы — управляемые сценарии;
- текущий этап — общий тёплый акцент;
- завершённые этапы — зелёные;
- будущие — нейтральные графитовые / серые;
- blue / violet запрещены, если элемент не означает information / guidance или insight / reflection;
- не назначать каждому этапу отдельный декоративный цвет.

## Цели

- цвет: общий тёплый акцент;
- фон: общая лесная атмосфера оболочки;
- главный объект: главная активная цель;
- прогресс через кольцо / линию;
- связи с направлениями и проектами видимы, но вторичны.

## Проекты

- цвет: общий тёплый акцент;
- фон: общая лесная атмосфера оболочки;
- шаблон: 3+6+3;
- главный объект: текущий активный проект / этап;
- плотные списки без лишних карточек.

## Финансы

- цвет: общий тёплый акцент;
- фон: общая лесная атмосфера оболочки;
- главный объект: финансовое состояние;
- аналитика занимает высокий приоритет;
- позитивная/негативная динамика определяется смыслом метрики.

## Дневник

- цвет: общий тёплый акцент;
- фон: общая лесная атмосфера оболочки;
- главный объект: запись;
- интерфейс максимально тихий;
- минимум KPI и декоративного шума.

## Аналитика

- цвет: общий тёплый акцент;
- фон: общая лесная атмосфера оболочки;
- главный объект: выбранный индекс / график;
- детализация: состояние → динамика → причины → события.

# 41. Контракт для Codex / разработчика

При создании или изменении интерфейса LifeOS разработчик обязан:

1. Сначала определить тип страницы и главный визуальный центр.
2. Определить семантическое состояние каждого цветного элемента до выбора цвета.
3. Применить каноническую иерархию: gold = current, green = completed, gray = future; остальные семантические цвета — только когда их значение действительно применимо.
4. Использовать общий theme accent; семантические success/error состояния сохранять.
5. Использовать существующие tokens и компоненты.
6. Не создавать новый визуальный паттерн, если есть утверждённый аналог.
7. Не использовать случайные значения отступов, радиусов, теней и размеров.
8. Проверить default / hover / pressed / focus / disabled / loading / success / error.
9. Проверить desktop и mobile.
10. Проверить экран в монохроме.
11. Проверить reduced motion и keyboard focus.
12. Пройти чек-лист Правила №38.
13. Не считать экран готовым только потому, что он «красиво выглядит» на одном размере.

# 42. Антипаттерны LifeOS

Не допускается:

- интерфейс как «админка из одинаковых карточек»;
- толстые рамки вокруг всего;
- один и тот же glow на каждом компоненте;
- несколько главных CTA одновременно;
- яркий фиолетовый как системный цвет;
- декоративный синий на обычных будущих элементах;
- декоративный зелёный на объектах, которые не completed / success / recovery;
- многоцветные списки шагов;
- цвет только для того, чтобы соседние карточки выглядели разными;
- одновременные blue / gold / green без семантической причины;
- фиолетовый вне insight / reflection / ideas;
- большое количество неона;
- случайный glassmorphism на всех поверхностях;
- карточка вокруг каждого текста;
- UI, который понятен только благодаря цвету;
- различные иконки для одного смысла;
- десятки статусов с уникальными цветами;
- 3D-графики;
- конфетти и bouncing после обычных действий;
- длинные анимации;
- белые системные dropdown / calendar / modal в тёмном приложении;
- desktop-макет, просто сжатый до ширины телефона;
- технические тексты вместо понятного пользовательского языка.

# 43. Короткая формула визуального языка LifeOS

**Тёмный графит → единый тёплый акцент → один главный объект → много воздуха вокруг важного → плотность в рабочих списках → единое дымчатое стекло → мягкий локальный свет → плотные читаемые overlays → контурные иконки → быстрые спокойные анимации → системные цвета только по смыслу.**

# 44. Definition of Done для дизайн-реализации

Экран LifeOS можно считать визуально готовым, если:

- он сразу узнаётся как часть LifeOS;
- главный объект понятен без чтения всей страницы;
- общая природная атмосфера и тёплый акцент связывают страницу, меню и шапку;
- интерфейс остаётся сильным без свечения;
- нет визуально случайных компонентов;
- все состояния предусмотрены;
- mobile-композиция спроектирована отдельно;
- экран доступен с клавиатуры;
- пустые / loading / error состояния не выглядят недоделанными;
- все размеры, цвета, радиусы и motion используют токены;
- экран проходит чек-лист №38.
